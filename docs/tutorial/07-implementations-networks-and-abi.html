Part I · Chapter 7

Implementations, networks and the ABI problem

Every program in this tutorial so far ran on one MPI library. This chapter covers the libraries that implement the standard and how they differ, how a message moves within a node and across a network, and why a program compiled against one library does not run with another: the ABI problem, which decides how ferrompi is built.

By the end of the chapter you can tell the MPI library families apart, handle an error or a missing feature the same way on every library, measure what a message costs, choose a transport, and explain why ferrompi compiles a small C layer against the library’s own mpi.h instead of declaring MPI’s types in Rust. It ends Part I; Part II takes ferrompi apart.

A standard and its libraries

Chapter 1 said that MPI is a standard, and that what you install is an implementation of it. Most implementations in use come from one of two open-source code bases. MPICH, developed at Argonne National Laboratory, has tracked the standard since its first version. Open MPI began in 2004, when several earlier MPI projects merged into it. Vendors build their libraries from one of the two and add support for their own networks, launchers and compilers:

Mpi::library_version, from chapter 1, names the library a program runs with. The libraries’ own tools tell more: MPICH’s mpichversion prints its release, its device and the options it was configured with, and Open MPI’s ompi_info prints its release and one line for each of its components. On a laptop the library usually comes from a package. On a cluster it is usually the vendor’s, built for that cluster’s network and loaded with a module.

What differs between libraries

The standard fixes the names of the functions and constants and what each call does. It leaves the rest to each library: the numbers behind the constants, how a message travels, which algorithm a collective uses, how the launcher starts processes, how the library is tuned, and how much of the newest standard it implements. A program that keeps to the standard gets the same results with every library. The differences decide how fast it runs, and what it sees when something fails:

The rest of this section shows how a program can handle the two differences it sees most directly: what an error looks like, and a feature the library does not have.

Error codes and classes

An MPI call that fails returns an error code. The standard names a set of error classes, such as MPI_ERR_RANK for a rank that does not exist. A library can return any code it likes, as long as MPI_Error_class turns the code into its class. ferrompi’s Error::Mpi carries the class, as an MpiErrorClass, along with the library’s code and message. This program sends to a rank that does not exist:

use ferrompi::{Error, Mpi};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // No process has rank `size`, so MPI refuses the send.
    match world.send(&[rank], world.size(), 0) {
        Err(Error::Mpi {
            class,
            code,
            message,
            ..
        }) => {
            // The class is the standard's; the code and message are the
            // library's own.
            println!("rank {rank}: the send failed with class {class}");
            eprintln!("rank {rank}: code {code}: {message}");
        }
        Err(other) => return Err(other),
        Ok(()) => println!("rank {rank}: the send succeeded"),
    }
    Ok(())
}

With two processes it prints, on standard output:

rank 0: the send failed with class ERR_RANK
rank 1: the send failed with class ERR_RANK

The class is the part to match on. The code and the message are the library’s own, and go to standard error. With MPICH 4.2.3, rank 0 writes:

rank 0: code 135423750: Invalid rank, error stack:
internal_Send(63826): MPI_Send(buf=0x7fff5bfad0a0, count=1, dtype=0x4c000439, 2, 0, MPI_COMM_WORLD) failed
internal_Send(63780): Invalid rank has value 2 but must be nonnegative and less than 2

MPICH packs the class into the code, along with an index into its stack of messages: 135423750 is 0x8126706, and its low seven bits, 6, are the value of MPI_ERR_RANK. The message is that stack. Each line names a function inside MPICH, and the first shows the arguments of the call as MPICH received them, including 0x4c000439, MPICH’s handle for the datatype MPI_INT32_T that ferrompi passed for an i32. Open MPI, according to its source, returns the class itself as the code, 6 for this error, with the message MPI_ERR_RANK: invalid rank.

The classes’ numbers differ between libraries too: MPI_ERR_TRUNCATE, for a message longer than the receive buffer, is 14 in MPICH and 15 in Open MPI. ferrompi compares the class with the linked library’s own constants, in its C layer, so MpiErrorClass::Rank means MPI_ERR_RANK whatever its number:

int32_t ferrompi_error_class_index(int error_class) {
    if (error_class == MPI_SUCCESS) return 0;
    if (error_class == MPI_ERR_BUFFER) return 1;
    if (error_class == MPI_ERR_COUNT) return 2;
    /* ... one line per class ... */
}

Match on the class, and log the code and the message: they help whoever reads the log, and they change from one library, and one release, to the next.

Features a library lacks

A library may implement only part of the newest standard. Open MPI 4.1 has none of MPI-4.0’s persistent collectives (chapter 3). ferrompi still builds against it: its C layer compiles each persistent collective to a stub that returns an error, and the Rust call returns Error::NotSupported. A program that should run on every library can try the persistent collective and fall back to the plain one:

use ferrompi::{Error, Mpi, ReduceOp};

const STEPS: u32 = 3;

fn value(rank: i32, step: u32) -> i64 {
    i64::from(rank + 1) * 10i64.pow(step)
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    let mut totals = Vec::new();
    match world.allreduce_init(vec![0i64], vec![0i64], ReduceOp::Sum) {
        Ok(mut sum) => {
            eprintln!("rank {rank}: persistent allreduce");
            for step in 0..STEPS {
                sum.send_buffer_mut()?[0] = value(rank, step);
                sum.start()?;
                sum.wait()?;
                totals.push(sum.buffer()?[0]);
            }
        }
        // Built against an MPI without persistent collectives, such as Open
        // MPI 4.1. Every process takes this branch, since they all run the
        // same binary.
        Err(Error::NotSupported(what)) => {
            eprintln!("rank {rank}: {what} not supported, using allreduce");
            for step in 0..STEPS {
                totals.push(world.allreduce_scalar(value(rank, step), ReduceOp::Sum)?);
            }
        }
        Err(other) => return Err(other),
    }
    println!("rank {rank}: totals {totals:?}");
    Ok(())
}

It prints:

rank 0: totals [3, 30, 300]
rank 1: totals [3, 30, 300]

With MPICH and with Open MPI 5, the program takes the persistent branch; with Open MPI 4.1, the fallback. ferrompi decides which when it is built, against one library, so every process of a job takes the same branch, and the collectives stay matched. Choosing the branch from Mpi::version() instead would be wrong: Open MPI 5 reports MPI 3.1, and has persistent collectives.

How a message moves

Where the two processes run decides how a message gets from one to the other. On one node they share the node’s memory, and the library passes messages through a segment of memory that both processes map. Between nodes the message crosses a network, through a network interface card (NIC) on each node. Over TCP, the message passes through the kernel on both nodes. Networks built for HPC, such as InfiniBand, RoCE, HPE Slingshot and AWS EFA, let the NIC read the message straight from the sender’s buffer and write it into the receiver’s, which is called remote direct memory access (RDMA):

A few details change the picture. For a large message on one node, a library can skip the segment and copy once, from the sender’s memory straight into the receiver’s, with a kernel facility such as CMA, XPMEM or KNEM; which one Open MPI uses depends on how it was built and on what the machine allows. A buffer must be registered with the NIC before RDMA can use it: the kernel pins the buffer’s pages, so they stay put while the NIC reads them. Registering is slow, so libraries remember which buffers they registered, and a program that sends from the same buffer again pays for it once. And the eager and rendezvous protocols of chapter 2 run on top: with RDMA, the rendezvous lets the NIC write a large message straight into the receive buffer, once the receiver has posted it.

Each library splits the work into a layer for messages within a node and one that drives the network, and usually drives the network through a separate network library: libfabric, also called OFI, or UCX. A network library has a backend for each kind of network; libfabric calls them providers.

LibraryWithin a nodeBetween nodes
MPICH 4 (its ch4 device)its shared-memory moduleone network module, chosen when MPICH is built: ofi (libfabric) or ucx
Open MPI 5the ob1 PML with the sm BTL, called vader before 5.0ob1 with the tcp BTL; the ucx PML for InfiniBand and RoCE; the cm PML with the ofi MTL for libfabric’s networks

In Open MPI, a PML carries point-to-point messages, and drives the network either through BTLs, which move bytes, or through an MTL, which hands whole messages to a network library. With the ucx PML, UCX carries the messages within a node as well. The networks and the backends that drive them:

Measuring the cost of a message

A message costs a fixed latency, paid by every message however small, plus a time per byte, set by the bandwidth. A ping-pong measures both: process 0 sends a message to process 1, which sends it back, many times for each size. Half the time of a round trip is the time one message takes:

use ferrompi::{Communicator, Mpi};

const SIZES: [usize; 9] = [8, 64, 512, 4096, 16384, 65536, 262144, 1048576, 4194304];

// Process 0 sends the buffer to process 1, which sends it back.
fn round_trip(world: &Communicator, buf: &mut [u8]) -> ferrompi::Result<()> {
    match world.rank() {
        0 => {
            world.send(buf, 1, 0)?;
            world.recv(buf, 1, 0)?;
        }
        1 => {
            world.recv(buf, 0, 0)?;
            world.send(buf, 0, 0)?;
        }
        _ => {}
    }
    Ok(())
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    if world.size() < 2 {
        eprintln!("ping-pong needs two processes");
        return Ok(());
    }

    if world.rank() == 0 {
        println!("   bytes   one way (us)    MB/s");
    }
    for bytes in SIZES {
        let mut buf = vec![0u8; bytes];
        // Fewer round trips for large messages, so each size takes about as
        // long as the others.
        let trips = (20_000_000 / bytes).clamp(100, 10_000);
        // One untimed round trip first, to set up the path.
        round_trip(&world, &mut buf)?;
        world.barrier()?;
        let start = mpi.wtime();
        for _ in 0..trips {
            round_trip(&world, &mut buf)?;
        }
        let one_way = (mpi.wtime() - start) / (2 * trips) as f64;
        if world.rank() == 0 {
            let rate = bytes as f64 / one_way / 1e6;
            println!("{bytes:>8}   {:>12.2}   {rate:>6.0}", one_way * 1e6);
        }
    }
    Ok(())
}

Up to a few hundred bytes, the time barely changes with the size: the latency dominates. For large messages, it grows with the size: the bandwidth dominates. A small message took about 1 µs through shared memory and about 15 µs through TCP, and the best rates were about 9 GB/s and 2.5 GB/s. No wire was involved, so the difference is the cost of the kernel and the TCP stack alone; a real network adds its own. RDMA networks take most of that software out of the path. On InfiniBand, a small message typically takes one to two microseconds, and a large one moves at close to the link’s rate, 25 GB/s for a 200 Gb/s link.

Two lessons follow for a program. Many small messages cost a latency each, so a program that has many values to send to one process sends them in one message. And the same program can run many times faster or slower depending on which path its messages take, which is why the next section matters.

Choosing a transport

A library picks its transports when the job starts, from what it was built with and what it finds on the machine, and it usually picks the fastest. When it cannot use the fast network, for example because it was built without support for it, it falls back to TCP: the program still runs, only slower. Each library has a way to see and to change the choice:

The summary also lists the machine’s network interfaces and their addresses, so read it before you paste it into a public issue. Open MPI passes -x NAME=value on to the processes it starts, which is how UCX’s variables reach them.

The ABI problem

The standard defines MPI’s application programming interface (API): the names in mpi.h and what they mean. Source code depends on the API. A compiled program depends on more: the size and layout of each type, the number behind each constant, the name of the library file, and the names of the symbols in it. That is the application binary interface (ABI), and until MPI 5.0 the standard left all of it to each library.

MPI’s constants are macros, so their values are compiled into the program. Here is one call compiled against three mpi.h headers:

MPICH’s handles are numbers that carry information: in MPI_INT, 0x4c000405, the 04 is the type’s size in bytes, and MPI_DOUBLE is 0x4c00080b. Open MPI’s MPI_COMM_WORLD is the address of ompi_mpi_comm_world, a global in libmpi.so.40, which the dynamic loader fills in when the program starts. A program built against one library and run with the other would pass numbers where the library expects pointers, or the reverse. In practice it gets no further than the loader, which looks for the library file the program was linked with:

target/debug/examples/pingpong: error while loading shared libraries: libmpi.so.12: cannot open shared object file: No such file or directory

The other constants differ too:

MPICH’s MPI_ANY_SOURCE is Open MPI’s MPI_PROC_NULL. A receive that passed −2 to mean “from any process” would, with the other library, mean “from no process”, and return at once with no data. Three consequences follow:

  • A binary runs only with libraries of the ABI it was built against. Moving a program to a cluster with an MPI of the other family means building it again there.
  • A container image that brings its own MPI cannot use the host’s fast network unless that MPI was built for it. The usual fix is to build the image against an MPI with the host’s ABI and to mount the host’s library in place of the image’s at run time. Container runtimes for HPC such as Sarus and Shifter do this, and it works only when the two libraries share an ABI, which in practice means the MPICH ABI.
  • Another language cannot declare MPI’s types and constants once for every library. Rust that declared type MPI_Comm = i32 and const MPI_ANY_SOURCE: i32 = -2 would match MPICH, and break with Open MPI. A binding has two ways out: generate its declarations from the installed mpi.h each time it is built, as bindgen does, or compile a small C layer against mpi.h and give the other language that layer’s own types.

How ferrompi builds against one library

ferrompi takes the second way. Its build script, build.rs, finds an MPI installation, compiles the C layer, csrc/ferrompi.c, with the installation’s mpi.h, and links the library. Rust never sees an MPI type: the C layer’s functions take and return fixed-width integers, and the C layer keeps the library’s handles in tables, which Rust refers to by index. Chapter 10 covers the C layer; this section covers how it deals with the differences above.

The wildcards. Rust passes ferrompi’s own codes, which are the same for every library: Source::Any becomes −1 and Source::ProcNull −2. The C layer swaps in the linked library’s values:

static int source_to_mpi(int32_t s) {
    if (s == FERROMPI_ANY_SOURCE) return MPI_ANY_SOURCE;
    if (s == FERROMPI_PROC_NULL) return MPI_PROC_NULL;
    return s;
}

static int tag_to_mpi(int32_t t) {
    return (t == FERROMPI_ANY_TAG) ? MPI_ANY_TAG : t;
}

With MPICH, source_to_mpi swaps −1 and −2; with the MPI 5.0 ABI, it turns −2 into −3, and tag_to_mpi turns −1 into −2. A receive’s status comes back through the same translation in reverse, and a count of MPI_UNDEFINED comes back as −1.

Flags. A few values are flags a program passes through to MPI, such as the assertions of window synchronization in chapter 5. ferrompi asks the C layer for them the first time it needs them, and keeps them:

void ferrompi_win_fence_mode_values(int32_t* out) {
    out[0] = MPI_MODE_NOSTORE;
    out[1] = MPI_MODE_NOPUT;
    out[2] = MPI_MODE_NOPRECEDE;
    out[3] = MPI_MODE_NOSUCCEED;
}

Error classes are compared with the library’s own constants, as the error section showed.

Missing features. The C layer tests the version that mpi.h reports, and Open MPI’s own version macro, since Open MPI 5 reports MPI 3.1:

#if MPI_VERSION >= 4 || (defined(OMPI_MAJOR_VERSION) && OMPI_MAJOR_VERSION >= 5)
#define FERROMPI_HAVE_MPI4_COLLECTIVES 1
#endif

Without it, each persistent collective compiles to a stub that returns ferrompi’s private code for an unsupported operation, which Rust turns into Error::NotSupported: the error the fallback program handles. Counts above i32::MAX need MPI-4.0’s large-count functions, such as MPI_Send_c:

    if (count > INT_MAX) {
#if MPI_VERSION >= 4
        return MPI_Send_c(buf, (MPI_Count)count, dt, mpi_dest, tag, comm);
#else
        return MPI_ERR_COUNT;
#endif
    }
    return MPI_Send(buf, (int)count, dt, mpi_dest, tag, comm);

Against a library without them, such as Open MPI 5, a call with more than i32::MAX elements fails with class Count.

What this means when you build and run:

  • The same Rust source builds against any supported library, and the binary runs with the library it was built against, or one with the same ABI. ferrompi gives source portability, not binary portability.
  • build.rs looks for MPI in a fixed order. The first of MPI_PKG_CONFIG, MPICC and CRAY_MPICH_DIR that is set wins, and if its probe fails the build stops instead of trying the others. With none of them set, it tries the pkg-config packages mpich, ompi and mpi, then mpicc on the PATH, then the usual prefixes. Where several libraries are installed, set one of the three variables to choose.
  • Cargo runs build.rs again when one of those variables changes, or PATH does, so loading another MPI module rebuilds ferrompi against it.
  • The binary does not record where the library is (it has no rpath), so the library must be found when the program starts: on the default library path, through LD_LIBRARY_PATH, or by loading the same module.
  • Launch with the mpiexec of the library you built against (chapter 1).

To build against a particular library, name its compiler wrapper:

MPICC=/opt/mpich/bin/mpicc cargo build --examples

When build.rs runs, it reports which probe found MPI, in a line that starts Found MPI via; cargo build -vv shows it. Chapter 8 covers building and running in more detail, and the compatibility guide lists every probe.

The MPI 5.0 ABI

MPI 5.0, published in June 2025, adds a standard ABI. Its mpi.h declares each handle type as a pointer to an incomplete struct, such as struct MPI_ABI_Comm *, and fixes the value of every constant and predefined handle, as in the third column of the table above. Its library is libmpi_abi. A library that implements the standard ABI keeps its own as well, and a program chooses one when it is built. A program built for the standard ABI links libmpi_abi, and runs with any library that provides it.

ferrompi needs no change to build for it. The C layer uses only the names in mpi.h, so it compiles unchanged against an ABI header. Point MPICC at the ABI’s compiler wrapper, which the MPI Forum’s reference stubs install as mpicc_abi:

MPICC=/path/to/mpi-abi/bin/mpicc_abi cargo build --examples

ferrompi’s CI builds every example this way against the MPI Forum’s stubs, which declare the whole ABI and implement none of it. That checks that the C layer compiles and links against the ABI; CI does not yet run programs on a library that implements it (the decision record has the plan).

Some libraries shipped a draft of the ABI before the standard was final, such as MPICH 4.3 built with -DMPI_ABI, whose values for the error handlers and thread levels differ from the standard’s. The C layer refuses to compile against one:

#if defined(MPI_ABI_VERSION) && MPI_VERSION < 5
#error "ferrompi does not support the draft MPI ABI (MPI_ABI_VERSION with MPI_VERSION < 5, as in MPICH 4.3 built with -DMPI_ABI); build against the native MPI headers or an MPI 5.0 ABI implementation"
#endif

Once libraries ship the standard ABI, one binary will run with every library that provides it, and a container will be able to use the host’s libmpi_abi. ferrompi keeps its C layer either way: the layer still gives Rust fixed types, keeps the handle tables, and serves the libraries that offer only their own ABI.

Exercises

  1. In the error program, send to −1 instead of world.size(). Which branch of the match runs, and why does the error not come from MPI?
  2. From the two ping-pong tables, take the 8-byte time as the latency and the best rate as the bandwidth, and predict the time of a 65536-byte message as latency plus size over bandwidth. How close is each prediction? Above what size does each run spend more time on bytes than on latency?
  3. With MPICH, run the ping-pong with MPIR_CVAR_DEBUG_SUMMARY=1, then with MPIR_CVAR_NOLOCAL=1 as well, then with FI_PROVIDER=tcp added. Which libfabric provider does each run use, and how do their small-message times compare?
  4. Find the definitions of MPI_Comm, MPI_COMM_WORLD and MPI_ANY_SOURCE in your library’s mpi.h. For MPICH and Open MPI, it is in the include directory next to the bin directory that holds mpicc.
  5. Build the examples with MPICC set to a path that does not exist, and read the error. Why is it better for the build to stop than to fall back to auto-detection?
  6. In the fallback program, also print Mpi::version(). For which library would choosing the branch by the version take the wrong one, and what would happen?

Summary

  • Most MPI libraries come from MPICH or from Open MPI. The members of the MPICH ABI initiative share one binary interface, through libmpi.so.12; Open MPI has its own, through libmpi.so.40.
  • The standard fixes names and behavior. Libraries differ in the standard version they report, the MPI-4.0 features they have, their launchers, their tuning, their default binding and their error codes.
  • Match an error on its class, and log its code and message. Try an MPI-4.0 operation and fall back on Error::NotSupported, rather than testing the version.
  • Within a node a message goes through shared memory. Between nodes it goes over TCP, through the kernel, or by RDMA, where the NIC reads and writes the buffers. A message costs a latency plus a time per byte, and a ping-pong measures both.
  • MPICH drives the network through libfabric or UCX; Open MPI through its BTLs, UCX or libfabric. Environment variables and MCA parameters show and change the choice.
  • MPI’s constants and handles are compiled into a program, and their values differ per library, so a binary runs only with libraries of its own ABI.
  • ferrompi compiles a C layer against the library’s mpi.h, which translates ferrompi’s fixed codes to the library’s values. That gives source portability, not binary portability. MPI 5.0’s standard ABI fixes the values for every library that provides it; ferrompi builds against it, and CI does not yet run programs on it.
