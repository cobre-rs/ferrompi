Part I · Chapter 4

Datatypes and reductions

Every MPI message is a sequence of typed values, and every reduction combines values with an operation. This chapter covers data that is not one plain slice, such as part of a struct or a column of a grid, and reductions that MPI does not predefine.

By the end of the chapter you can describe a struct or a strided layout to MPI, find which process holds a maximum, give each process one block of a reduced result, and write a reduction of your own. The chapter assumes chapter 2 for sends and receives and chapter 3 for reductions and scans.

Types in a message

An MPI call describes a buffer with three things: its address, a count, and a datatype. The datatype says what each element is, and so how many bytes it takes. In ferrompi the slice’s element type picks the datatype, and the slice’s length is the count:

Rust typeMPI datatype
f32MPI_FLOAT
f64MPI_DOUBLE
i32MPI_INT32_T
i64MPI_INT64_T
u8MPI_UINT8_T
u32MPI_UINT32_T
u64MPI_UINT64_T

These are the types that implement MpiDatatype. The trait is sealed, so no other type can claim an MPI datatype that does not describe it.

MPI defines a message by its type signature: the sequence of basic types it holds, such as two MPI_DOUBLE. A receive matches the message only if its own datatype and count give the same sequence, or a longer one that starts with it (chapter 2). The rule is about types, not bytes. Two f64 and two i64 are both 16 bytes, but their signatures differ, and receiving one as the other is an error. The libraries do not check it, and When types do not match shows what happens instead.

Types, not bytes, because a library may have to convert. MPI allows a job to span machines that store numbers differently, in another byte order say, and the datatype is what tells the library how to translate each value. Few clusters mix such machines today; on the common ones the bytes arrive as they were sent.

One datatype carries no meaning: MPI_BYTE, a byte that is never converted. ferrompi uses it in allreduce_bytes(send, recv, op), a BitwiseOr, BitwiseAnd or BitwiseXor reduction on slices of any BytePermutable type. Those are the integer types, including i8, i16 and u16, which have no MPI datatype in ferrompi, and arrays of them. A bitwise operation treats each bit on its own, so it gives the same result on the bytes as on the integers they make up.

Derived datatypes

A slice of f64 is one basic type, repeated, with no gaps. Much real data is not like that. A struct mixes types and may hold fields that should not travel, and a column of a grid stored row by row is spread through memory at a fixed stride. You could copy such data into a contiguous buffer, send that, and copy it out again on the other side. A derived datatype describes the layout to MPI instead, and the library reads the values from where they are and writes them where they belong.

A derived datatype is a type map: a list of basic types, each at a byte displacement from the start of the element. Its type signature is the list of types without the displacements. Its lower bound and upper bound are where its data begins and ends, the upper bound rounded up for alignment, and its extent is the distance between them. When a buffer holds several elements of the type, element k starts k extents after the first. CustomDatatype builds them:

ConstructorMPI functionType map
contiguous::<T>(count) MPI_Type_contiguous count values of T in a row
vector::<T>(count, blocklength, stride) MPI_Type_vector count blocks of blocklength values of T, each block starting stride values after the one before
create_struct(&fields) MPI_Type_create_struct for each StructField::new::<T>(blocklength, displacement), blocklength values of T at displacement bytes
dt.resized(lb, extent) MPI_Type_create_resized dt’s type map, with a new lower bound and extent, in bytes

Every base type T is an MpiDatatype: a struct field cannot be another derived type. Each constructor commits the type (MPI_Type_commit) before it returns, and dropping the CustomDatatype frees it (MPI_Type_free). A process can hold 64 at a time; one more returns Err(Error::ResourceExhausted).

send_custom(buf, &dt, dest, tag) and recv_custom(buf, &dt, source, tag) send and receive with a derived datatype, and isend_custom and irecv_custom are their nonblocking forms. The datatype describes one element of the slice, whose element type T is yours to choose, and the count is the slice’s length. Before it calls MPI, ferrompi checks that the datatype fits that element: its extent must be size_of::<T>(), and its data must lie within one T. Otherwise the call returns Err(Error::InvalidArgument) with arg: "datatype". MPI reads and writes the buffer wherever the type map points, element after element, and the two checks keep every one of those places inside the slice. Derived datatypes work with these point-to-point calls only; ferrompi’s collectives take slices of MpiDatatype types.

The element type must implement PlainData, an unsafe trait that promises every bit pattern is a valid value, because a receive writes whatever bytes arrive. Numbers qualify, and so do #[repr(C)] structs and arrays of numbers. A reference, a Box or Vec, a bool, a char, an enum or a NonZero integer does not: some of its bit patterns are not values. The primitive types, and arrays of PlainData types, implement it already. For a struct of your own you write the unsafe impl, with a comment that says why it holds.

Sending part of a struct

A particle simulation moves particles between processes as they cross from one process’s region into another’s. The new owner needs each particle’s position and id, but not the force on it, which it recomputes. This program sends three particles without their forces:

use std::mem::{offset_of, size_of};

use ferrompi::{CustomDatatype, Mpi, PlainData, StructField};

#[repr(C)]
#[derive(Clone, Copy, Debug)]
struct Particle {
    pos: [f64; 3],
    id: i64,
    // Recomputed by the process that owns the particle, so never sent.
    force: [f64; 3],
}

// SAFETY: Particle is #[repr(C)] and holds only f64 and i64 values, for which
// every bit pattern is valid.
unsafe impl PlainData for Particle {}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // The fields to send, at their byte offsets in a Particle.
    let fields = CustomDatatype::create_struct(&[
        StructField::new::<f64>(3, offset_of!(Particle, pos) as i64),
        StructField::new::<i64>(1, offset_of!(Particle, id) as i64),
    ])?;
    // That type ends where `id` does. Stretch its extent to a whole Particle,
    // so that element k of a slice starts k Particles in.
    let particle = fields.resized(0, size_of::<Particle>() as i64)?;

    match world.rank() {
        0 => {
            let leaving: Vec<Particle> = (0..3)
                .map(|k| Particle {
                    pos: [k as f64, 0.5, 1.0],
                    id: 100 + k,
                    force: [9.9; 3],
                })
                .collect();
            world.send_custom(&leaving, &particle, 1, 0)?;
        }
        1 => {
            let empty = Particle { pos: [0.0; 3], id: 0, force: [0.0; 3] };
            let mut arriving = [empty; 3];
            let status = world.recv_custom(&mut arriving, &particle, 0, 0)?;
            println!("received {:?} particles", status.count);
            for p in &arriving {
                println!("id {} at {:?}, force {:?}", p.id, p.pos, p.force);
            }
        }
        _ => {}
    }
    Ok(())
}

With two processes it prints:

received Some(3) particles
id 100 at [0.0, 0.5, 1.0], force [0.0, 0.0, 0.0]
id 101 at [1.0, 0.5, 1.0], force [0.0, 0.0, 0.0]
id 102 at [2.0, 0.5, 1.0], force [0.0, 0.0, 0.0]

The type lists two blocks: three f64 at the offset of pos, and one i64 at the offset of id. offset_of! gives the offsets the compiler chose, and #[repr(C)] makes those the C layout, in field order. The type ends where id does, at byte 32, so as built its extent is 32 bytes, while a Particle is 56. resized(0, 56) keeps the type map and makes the extent one particle, so element 1 starts where the second particle does.

Pass fields instead of particle, without the resize, and both processes stop at the check, before either calls MPI:

Error: InvalidArgument { arg: "datatype", reason: "extent differs from the element size" }
Error: InvalidArgument { arg: "datatype", reason: "extent differs from the element size" }

The receiver’s force fields kept the zeros they held: a receive writes only where the type map points. The count in the status is in elements of the datatype, three particles, not in basic values.

To send a whole struct, list every field. The upper bound is then the end of the last field, rounded up to the alignment of the most-aligned one, which for a #[repr(C)] struct usually makes the extent size_of. But each library applies its own idea of alignment, so resize to size_of::<T>() anyway. It costs nothing, and the check then passes under every library.

Sending a column

Chapter 2’s halo exchange split a line of cells among the processes, and each process sent its edge cells to its neighbors. Split a grid into blocks side by side instead, and the edge to send is a column. In a grid stored row by row, the entries of a column are one row apart in memory.

In C, the usual column type is MPI_Type_vector(rows, 1, N): one value per row, N values apart, sent as a single element that starts at the column’s first entry. In ferrompi a datatype describes one element of a slice, and a grid stored as a slice of rows has rows for elements. So the column type is one row long and holds one entry: an f64 at the column’s offset, resized to the length of a row. Element i of the slice is then row i’s entry, and the elements together make up the column:

use std::mem::size_of;

use ferrompi::{CustomDatatype, Mpi, StructField};

/// A row: a ghost entry at each end, and the two entries this process owns.
type Row = [f64; 4];

/// Column `j` of a slice of rows: the entry at column `j`, in a type one row
/// long, so element `i` of the slice is row `i`'s entry.
fn column(j: usize) -> ferrompi::Result<CustomDatatype> {
    let offset = (j * size_of::<f64>()) as i64;
    let entry = CustomDatatype::create_struct(&[StructField::new::<f64>(1, offset)])?;
    entry.resized(0, size_of::<Row>() as i64)
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank() as usize;

    // Each process owns columns 1 and 2 of three rows of a grid, stored row by
    // row; columns 0 and 3 are ghosts, for copies of the neighbors' edges. The
    // owned entry (i, j) of rank r is 100 r + 10 i + j; the ghosts start at 0.
    let mut block: Vec<Row> = (0..3)
        .map(|i| {
            std::array::from_fn(|j| match j {
                1 | 2 => (100 * rank + 10 * i + j) as f64,
                _ => 0.0,
            })
        })
        .collect();

    match rank {
        // Rank 1's block sits to the right of rank 0's, so rank 0's last owned
        // column, 2, is rank 1's left ghost column, 0.
        0 => world.send_custom(&block, &column(2)?, 1, 0)?,
        1 => {
            world.recv_custom(&mut block, &column(0)?, 0, 0)?;
            for (i, row) in block.iter().enumerate() {
                println!("rank 1, row {i}: {row:?}");
            }
        }
        _ => {}
    }
    Ok(())
}

With two processes it prints:

rank 1, row 0: [2.0, 101.0, 102.0, 0.0]
rank 1, row 1: [12.0, 111.0, 112.0, 0.0]
rank 1, row 2: [22.0, 121.0, 122.0, 0.0]

The two sides use different types, column 2 and column 0, with the same signature: three f64. That is all MPI requires; the displacements never leave the process that uses them.

A strided pattern

A vector type picks values at a fixed stride. This program sends the diagonals of two 3 × 3 matrices: three blocks of one f64, four values apart, which are entries (0, 0), (1, 1) and (2, 2). The type spans from the first entry to the end of the ninth, so its extent is already one matrix, and the check passes without a resize. The receiver uses no derived type at all:

use ferrompi::{CustomDatatype, Mpi};

type Matrix = [[f64; 3]; 3];

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // A matrix's diagonal: 3 blocks of 1 f64, each starting 4 f64 after the
    // last. The type spans from the first entry to the end of the ninth, so its
    // extent is one Matrix.
    let diagonal = CustomDatatype::vector::<f64>(3, 1, 4)?;

    match world.rank() {
        0 => {
            // Entry (i, j) of matrix m is 100 m + 10 i + j.
            let batch: Vec<Matrix> = (0..2)
                .map(|m| {
                    std::array::from_fn(|i| {
                        std::array::from_fn(|j| (100 * m + 10 * i + j) as f64)
                    })
                })
                .collect();
            world.send_custom(&batch, &diagonal, 1, 0)?;
        }
        1 => {
            // The message holds six f64, and six f64 in a row receive it.
            let mut diagonals = [0.0f64; 6];
            world.recv(&mut diagonals, 0, 0)?;
            println!("diagonals {diagonals:?}");
        }
        _ => {}
    }
    Ok(())
}

With two processes it prints:

diagonals [0.0, 11.0, 22.0, 100.0, 111.0, 122.0]

Type maps need not match, only signatures: the sender’s six f64 are spread over two matrices, the receiver’s are six in a row. A derived type on the sending side gathers scattered values into a contiguous message, and one on the receiving side scatters a message where it belongs.

When to copy instead

A derived datatype saves you a copy; it does not save the library one. To send values that are spread out, the library still has to collect them. Between nodes, most libraries pack them into a contiguous buffer of their own before the network sees them, and unpack them on the other side, though some networks can send from a list of addresses and skip that copy. So a derived type is seldom much faster than copying into a Vec yourself, and when the pieces are single values, a plain loop that copies them can be faster still. Use one when it makes the program clearer, or when a profile shows the copies. Build each type once, outside the loop that sends with it: creating and committing a type are MPI calls of their own.

Where the maximum is

A Max reduction gives the largest value, but not who has it. MPI_MAXLOC and MPI_MINLOC reduce pairs of a value and an index: the result is the largest, or smallest, value, with the index that came with it. The index is any i32 you choose, such as a global index or a rank. When several pairs hold that value, the result takes the smallest of their indices. The MPI standard fixes that rule, so every library gives the same answer.

Each kind of pair is an MPI datatype of its own, the layout of a C struct of a value and an int. ferrompi mirrors each with a #[repr(C)] struct with fields value and index, an i32:

Pair typevalueMPI datatype
FloatIntf32MPI_FLOAT_INT
DoubleIntf64MPI_DOUBLE_INT
Int2i32MPI_2INT
ShortInti16MPI_SHORT_INT
LongInti64, a C longMPI_LONG_INT
LongDoubleIntthe 16 bytes of a C long doubleMPI_LONG_DOUBLE_INT

LongInt and LongDoubleInt exist only on Linux on x86_64, aarch64 and ppc64le, where ferrompi knows how C lays them out.

allreduce_indexed(send, recv, op) reduces slices of pairs element by element and gives the result to every process. Its op is CollectiveOp::MAX_LOC or CollectiveOp::MIN_LOC: no other operation compiles with a pair type, and MAX_LOC does not compile with a plain number. This program finds the largest entry of a vector spread over four processes, and where it is:

use ferrompi::{CollectiveOp, DoubleInt, Mpi};

const PER_RANK: i32 = 3;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Entry g of a vector spread over the processes is 5 g mod 6. This process
    // holds entries 3 rank to 3 rank + 2, and finds its largest.
    let first = PER_RANK * rank;
    let mut best = DoubleInt { value: f64::NEG_INFINITY, index: -1 };
    for g in first..first + PER_RANK {
        let value = f64::from(5 * g % 6);
        if value > best.value {
            best = DoubleInt { value, index: g };
        }
    }

    // The largest entry anywhere, and its index.
    let mut found = [DoubleInt { value: 0.0, index: 0 }];
    world.allreduce_indexed(&[best], &mut found, CollectiveOp::MAX_LOC)?;
    let [top] = found;
    println!(
        "rank {rank}: here {} at {}, anywhere {} at {}, held by rank {}",
        best.value,
        best.index,
        top.value,
        top.index,
        top.index / PER_RANK
    );
    Ok(())
}

With four processes it prints:

rank 0: here 5 at 1, anywhere 5 at 1, held by rank 0
rank 1: here 3 at 3, anywhere 5 at 1, held by rank 0
rank 2: here 5 at 7, anywhere 5 at 1, held by rank 0
rank 3: here 3 at 9, anywhere 5 at 1, held by rank 0

The largest value, 5, appears twice: at index 1 on rank 0 and at index 7 on rank 2. The reduction returns index 1, the smaller. Each process’s own search keeps the first of equal values, since it replaces its best only on >, so the smallest index wins within a process too.

Reduce-scatter

reduce_scatter_block(send, recv, op) (MPI_Reduce_scatter_block) combines the processes’ send slices element by element, like an allreduce, then splits the result into one block per process, recv.len() elements each, and gives block r to rank r. send must hold recv.len() elements for each process, or the call returns an error. Use it when each process needs only its share of a result: no process needs a buffer for all of it, and the library is free to split the combining so that each process adds up only its own share.

This program builds a histogram of values spread over the processes. Each process counts its own values in every bin, and each ends up with the totals of the two bins it owns:

use ferrompi::{Mpi, ReduceOp};

const BINS_EACH: usize = 2;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank() as usize, world.size() as usize);
    let bins = BINS_EACH * size;

    // Each process counts its ten values, each a bin number, in a histogram of
    // every bin.
    let mut counts = vec![0u64; bins];
    for k in 0..10 {
        counts[(7 * rank + 3 * k) % bins] += 1;
    }

    // Process r owns bins 2 r and 2 r + 1, and receives their totals.
    let mut mine = [0u64; BINS_EACH];
    world.reduce_scatter_block(&counts, &mut mine, ReduceOp::Sum)?;
    let first = BINS_EACH * rank;
    println!("rank {rank}: bins {first} and {} hold {mine:?}", first + 1);
    Ok(())
}

With four processes it prints:

rank 0: bins 0 and 1 hold [6, 5]
rank 1: bins 2 and 3 hold [5, 5]
rank 2: bins 4 and 5 hold [4, 5]
rank 3: bins 6 and 7 hold [5, 5]

Like the reductions of chapter 3, it has a persistent form, reduce_scatter_block_init.

Operations you define

When no predefined operation fits, UserOp turns a Rust closure into one (MPI_Op_create). The closure takes two slices of equal length, by convention invec and inoutvec, and combines them element by element into the second: inoutvec[i] becomes invec[i] ∘ inoutvec[i], where ∘ is your operation and invec holds the earlier operand. A &UserOp goes wherever a reduction takes an operation: reduce, allreduce, scan, exscan, reduce_scatter_block, and their scalar, nonblocking and persistent forms.

MPI groups the operands however its algorithm needs: (a ∘ b) ∘ (c ∘ d) in one call, ((a ∘ b) ∘ c) ∘ d in another. So the operation must be associative, or its results depend on the library and the process count. Floating-point addition is associative only up to rounding, which is why chapter 3’s sums change in the last bits.

UserOp::new also declares the operation commutative, which lets MPI swap operands as well as group them. UserOp::new_noncommutative does not: MPI then keeps the operands in rank order, with the lower ranks’ values in invec. Matrix multiplication is associative but not commutative, and so is “the later value wins”, which fills gaps in data. This program fills the gaps in a time series spread over four processes:

use ferrompi::{Mpi, UserOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // A time series split over the processes, three samples each, with the
    // missing samples marked NaN.
    let gap = f64::NAN;
    let mut series = match rank {
        0 => [1.0, gap, 2.0],
        1 => [gap, gap, gap],
        2 => [gap, 5.0, gap],
        _ => [gap, 7.0, 8.0],
    };

    // `earlier` then `later` gives the later sample, or the earlier one when
    // the later is missing. That is associative, but not commutative.
    let latest = UserOp::new_noncommutative(|earlier: &[f64], later: &mut [f64]| {
        for (e, l) in earlier.iter().zip(later.iter_mut()) {
            if l.is_nan() {
                *l = *e;
            }
        }
    })?;

    // The latest sample on the lower ranks fills this process's leading gaps.
    // Rank 0 has no lower ranks, and its result is undefined.
    let last_here = series.iter().rev().copied().find(|x| !x.is_nan()).unwrap_or(gap);
    let before = world.exscan_scalar(last_here, &latest)?;
    let mut carry = if rank == 0 { gap } else { before };
    for x in &mut series {
        if x.is_nan() {
            *x = carry;
        } else {
            carry = *x;
        }
    }
    println!("rank {rank}: {series:?}");
    Ok(())
}

With four processes it prints:

rank 0: [1.0, 1.0, 2.0]
rank 1: [2.0, 2.0, 2.0]
rank 2: [2.0, 5.0, 5.0]
rank 3: [5.0, 7.0, 8.0]

Each process passes its last sample to exscan_scalar, which returns the latest sample of the lower ranks. Rank 3 gets rank 0’s 2.0, rank 1’s gap and rank 2’s 5.0 combined in that order, which is 5.0. Rank 1 has no sample, so it passes a gap, and rank 0’s 2.0 crosses it to reach rank 2. Rank 0’s exscan result is undefined, as in chapter 3, and the program does not use it.

Commutative or not

Declaring an operation commutative when it is not is an error no library detects, and what it does depends on the library’s algorithm. This program declares “the later value wins” both ways and runs an allreduce with each:

use ferrompi::{Mpi, UserOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // `earlier` then `later` gives `later`, so combining every process's value
    // in rank order gives the last rank's. Associative, not commutative.
    let keep_later = |_earlier: &[f64], _later: &mut [f64]| {};
    let in_order = UserOp::new_noncommutative(keep_later)?;
    // Wrong: the same operation, declared commutative.
    let any_order = UserOp::new(keep_later)?;

    let mine = [f64::from(rank)];
    let (mut right, mut wrong) = ([0.0], [0.0]);
    world.allreduce(&mine, &mut right, &in_order)?;
    world.allreduce(&mine, &mut wrong, &any_order)?;
    println!("rank {rank}: in rank order {}, declared commutative {}", right[0], wrong[0]);
    Ok(())
}

Under MPICH 4.2.3 with four processes it prints:

rank 0: in rank order 3, declared commutative 0
rank 1: in rank order 3, declared commutative 1
rank 2: in rank order 3, declared commutative 2
rank 3: in rank order 3, declared commutative 3

In rank order, the later value wins and the last rank’s 3 comes back everywhere. Declared commutative, every process got a different answer, its own value, and no error. For a small allreduce MPICH uses recursive doubling: in each step every process exchanges its partial result with a partner and combines the two. For a commutative operation it puts the partner’s value in invec, so “the later value wins” keeps the process’s own value at every step. For a non-commutative one it puts the lower ranks’ value there.

Another library, or another process count, can give another wrong answer, or the right one by luck. Unless swapping the operands gives the same result, use new_noncommutative. It costs only the freedom to reorder, which some algorithms need: MPICH, for example, uses its large-message allreduce, a reduce-scatter followed by an allgather, only for commutative operations.

What the closure may do

MPI calls the closure from inside the reductions that use the operation, as often as its algorithm needs, each time on part of the buffers. Three rules follow:

  • It is Fn + Send + Sync + 'static. It may run on another thread, and long after the line that created it: until the operation is freed, and a persistent reduction keeps its operation until the request is freed.
  • It must not panic. A panic cannot unwind through MPI’s C frames, so ferrompi aborts the process instead.
  • It must work element by element. Its slices are of an MpiDatatype, a single number, and MPI may call it on any part of a buffer. An operation that reads two neighboring f64 as one value, a mean and a count say, can see the pair split across two calls.

A process can hold 16 UserOps at a time; one more returns Err(Error::ResourceExhausted).

When types do not match

MPI requires a receive to name the type signature that was sent, and leaves checking that to the program. This program sends two f64 and receives them as i64:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    match world.rank() {
        0 => world.send(&[1.0f64, 0.5], 1, 0)?,
        1 => {
            // The message holds two f64. Received as two i64, it is the same
            // 16 bytes read as integers, and nothing reports an error.
            let mut ints = [0i64; 2];
            let status = world.recv(&mut ints, 0, 0)?;
            println!("received {ints:?}, count {:?}", status.count);
            let back = ints.map(|i| f64::from_bits(i as u64));
            println!("the same bits as f64: {back:?}");
        }
        _ => {}
    }
    Ok(())
}

With two processes it prints:

received [4607182418800017408, 4602678819172646912], count Some(2)
the same bits as f64: [1.0, 0.5]

Nothing failed. Both types are eight bytes, so the 16 bytes fill two i64, the status counts two elements, and the integers are the bit patterns of 1.0 and 0.5. A mismatch that keeps the size, like this one, shows only as wrong numbers.

ferrompi checks what one process can. The slice’s element type picks its datatype, so on each side the buffer and the datatype agree, and a derived datatype must fit its element type. Whether the two sides agree with each other is the program’s to ensure, as with tags. Keep the element type of each kind of message in one place, a type alias or a shared struct, and build each derived type in one function that both sides call, as the column program does. Correctness tools such as MUST check type signatures while the program runs; reach for one when a receive produces numbers that look like garbage.

Exercises

  1. In the particle program, pass fields instead of particle to both calls and read the error. Then build a type of all three fields, without resized. Does the check pass under your MPI library, and why resize it anyway?
  2. Finish the column program’s halo exchange: rank 1 also sends its column 1 to rank 0’s ghost column 3. Post both transfers on each process with isend_custom and irecv_custom in one scope (chapter 2), so that neither process waits for the other.
  3. In the diagonals program, receive with recv_custom and the same diagonal type into two matrices filled with −1. What do the entries off the diagonal hold afterwards?
  4. Change the MAXLOC program to MIN_LOC, and predict what it prints before you run it. Then pair each process’s best value with its rank instead of the entry’s index. What does the result tell you now, and what does it no longer say?
  5. In the forward-fill program, declare the operation with UserOp::new, and run it with 4 and then 8 processes. Is the result still right under MPICH? Why is the program wrong even when it is?
  6. Rewrite the histogram program with a reduce to rank 0 followed by a scatter. How many elements does each process need for the result now, and how many with reduce_scatter_block?

Summary

  • A message is a sequence of basic types, its type signature, and a receive must name the same sequence. The libraries do not check: a mismatch of the same size gives wrong numbers and no error.
  • In ferrompi the slice’s element type picks the MPI datatype. allreduce_bytes reduces any integer type bit by bit, as MPI_BYTE.
  • A derived datatype is a type map: basic types at byte displacements. Its extent is the distance from one element to the next. CustomDatatype builds contiguous, vector and struct types, and resizes them.
  • send_custom and recv_custom take a slice of a PlainData type and a datatype that describes one element, whose extent must be the element’s size. Resize a type that ends early. A column of a slice of rows is one entry, resized to a row.
  • A derived type saves your copy, not the library’s. Use one for clarity, and build it once.
  • MAXLOC and MINLOC reduce value–index pairs with allreduce_indexed; a tie gives the smallest index.
  • reduce_scatter_block gives each process one block of a reduced result.
  • A UserOp must be associative, work element by element, and not panic. Declare it with new_noncommutative unless swapping operands gives the same result: an operation wrongly declared commutative gives wrong answers, which can differ from process to process, with no error.
