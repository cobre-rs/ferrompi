Part I · Chapter 6

Threads and hybrid MPI

A hybrid program runs a few MPI processes on each node and several threads in each process. This chapter covers how a program tells MPI which of its threads will call it, what each of MPI’s four thread levels allows, the rules MPI adds when threads call it at the same time, and how to place processes and their threads on a node.

By the end of the chapter you can split a process’s work over threads between MPI calls, give communication a thread of its own, run collectives from several threads at once, and check how many CPUs the launcher gave each process. The programs start their threads with the standard library’s std::thread::scope; the rules are the same for a thread pool such as rayon’s.

Why threads in an MPI program

The programs so far ran one process per core. Each process has its own memory, so data that every process needs, such as a mesh, a lookup table or a model, is stored once per process, and every process takes part in every collective. Threads share their process’s memory. A node with eight cores can run eight processes of one thread, two processes of four threads, or one process of eight:

Fewer processes per node means fewer copies of the data and fewer ranks in every collective, and at thousands of cores both add up. One process per node is not always best, though. Each socket of a node has its own memory, and a thread reads the other socket’s memory more slowly, so one process per socket, or per NUMA domain, is a common choice. Chapter 5’s shared-memory windows are the other way to keep one copy per node; threads also share the work inside a process without sending a message.

Threads raise a question that a program with one thread per process never asks: which threads call MPI. MPI needs the answer when it starts, because a library that one thread calls can skip the locking that several threads need.

The four thread levels

Mpi::init_thread(required) (MPI_Init_thread) starts MPI at a ThreadLevel. Mpi::init() is init_thread(ThreadLevel::Single). The main thread is the one that called init_thread:

LevelMPI constantWho may call MPI
SingleMPI_THREAD_SINGLEthe process has only one thread
FunneledMPI_THREAD_FUNNELEDonly the main thread
SerializedMPI_THREAD_SERIALIZEDany thread, one call at a time
MultipleMPI_THREAD_MULTIPLEany thread, at any time

MPI may grant a lower level than the one asked for. mpi.thread_level() returns the level granted, and ThreadLevel is ordered, so mpi.thread_level() < ThreadLevel::Funneled asks whether the program got less than it needs. The rules that apply, and that ferrompi enforces, are those of the granted level.

Single means one thread, not one thread that calls MPI. A program that starts threads, even threads that never call MPI, asks for Funneled: at Single a library may leave out protections it needs when other threads run. ferrompi checks the two levels the same way, by which thread makes the call, so a program with threads at Single passes its checks while it breaks MPI’s rule.

Funneled: threads compute, one thread calls MPI

In the most common hybrid program, worker threads compute between MPI calls, and the main thread makes the calls. This program sums the first two million integers. Each process sums its million of them with four threads, and then the main thread adds up the processes’ sums with an allreduce:

use ferrompi::{Mpi, ReduceOp, ThreadLevel};

const VALUES: u64 = 1_000_000;
const THREADS: u64 = 4;

fn main() -> ferrompi::Result<()> {
    // Threads will run, but only this one calls MPI.
    let mpi = Mpi::init_thread(ThreadLevel::Funneled)?;
    if mpi.thread_level() < ThreadLevel::Funneled {
        eprintln!("MPI granted only {:?}", mpi.thread_level());
        return Ok(());
    }
    let world = mpi.world();
    let rank = world.rank() as u64;

    // This process sums its million values, from rank * VALUES on, with four
    // threads, each taking a quarter of them. The threads make no MPI call.
    let first = rank * VALUES;
    let chunk = VALUES / THREADS;
    let local: u64 = std::thread::scope(|s| {
        let workers: Vec<_> = (0..THREADS)
            .map(|t| {
                let start = first + t * chunk;
                s.spawn(move || (start..start + chunk).sum::<u64>())
            })
            .collect();
        workers.into_iter().map(|w| w.join().unwrap()).sum()
    });

    // Back on the thread that called init_thread: combine the processes.
    let total = world.allreduce_scalar(local, ReduceOp::Sum)?;
    println!("rank {rank}: local sum {local}, total {total}");
    Ok(())
}

With two processes it prints:

rank 0: local sum 499999500000, total 1999999000000
rank 1: local sum 1499999500000, total 1999999000000

std::thread::scope joins the workers before it returns, so the allreduce starts after every worker has finished. A thread pool works the same way: the pool computes, and the main thread calls MPI between the parallel parts. The workers may also keep computing while the main thread is inside an MPI call; Funneled limits which thread calls MPI, not what the other threads do in the meantime.

What ferrompi checks

A Communicator is Send and Sync, so the compiler lets a worker thread use one. ferrompi checks at run time instead. At Single and Funneled, a call from any thread but the main thread returns Err(Error::ThreadLevelViolation) without reaching MPI:

use ferrompi::{Mpi, ThreadLevel};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init_thread(ThreadLevel::Funneled)?;
    let world = mpi.world();

    // A Communicator is Send and Sync, so a worker thread can hold one. At
    // Funneled, its calls are refused before they reach MPI.
    let refused = std::thread::scope(|s| s.spawn(|| world.barrier()).join().unwrap());
    if let Err(err) = refused {
        println!("rank {}: barrier on a worker thread: {err}", world.rank());
    }

    // The thread that called init_thread can still call MPI.
    world.barrier()?;
    println!("rank {}: barrier on the main thread: ok", world.rank());
    Ok(())
}

With two processes it prints:

rank 0: barrier on a worker thread: MPI call not permitted on this thread at the provided thread level
rank 0: barrier on the main thread: ok
rank 1: barrier on a worker thread: MPI call not permitted on this thread at the provided thread level
rank 1: barrier on the main thread: ok

init_thread marks the main thread, and every call checks the mark before it calls MPI; the architecture guide’s lifecycle guard describes the mechanism. A Drop cannot return an error, so a handle whose drop calls MPI, such as a communicator from split, aborts the process when a worker thread drops it at these levels. Each process prints a line naming the type and the thread:

ferrompi: Communicator dropped on thread ThreadId(2)

Drop such handles on the main thread: a worker that creates one can return it from its closure.

Serialized: a communication thread

At Serialized any thread may call MPI, but no two calls may overlap, and the program, not MPI, keeps them apart. One use is a thread that makes all of a process’s MPI calls while the main thread computes. Here the main thread sends one value per step over a channel, and the communication thread sums each value over the processes:

use std::sync::mpsc;

use ferrompi::{Mpi, ReduceOp, ThreadLevel};

const STEPS: u64 = 4;

fn main() -> ferrompi::Result<()> {
    // One thread calls MPI, but not the one that called init_thread: that
    // needs Serialized.
    let mpi = Mpi::init_thread(ThreadLevel::Serialized)?;
    if mpi.thread_level() < ThreadLevel::Serialized {
        eprintln!("MPI granted only {:?}", mpi.thread_level());
        return Ok(());
    }
    let world = mpi.world();
    let rank = world.rank() as u64;

    let (to_comm, from_main) = mpsc::channel::<u64>();
    std::thread::scope(|s| {
        // The communication thread sums each step's result over the
        // processes, while the main thread computes the next step.
        let comm = s.spawn(|| -> ferrompi::Result<Vec<u64>> {
            let mut totals = Vec::new();
            for partial in from_main {
                totals.push(world.allreduce_scalar(partial, ReduceOp::Sum)?);
            }
            Ok(totals)
        });

        // The main thread computes and makes no MPI call until the
        // communication thread has finished.
        for step in 0..STEPS {
            let partial = (rank + 1) * 10u64.pow(step as u32);
            to_comm.send(partial).unwrap();
        }
        drop(to_comm);
        let totals = comm.join().unwrap()?;
        println!("rank {rank}: step totals {totals:?}");
        Ok(())
    })
}

With two processes it prints:

rank 0: step totals [3, 30, 300, 3000]
rank 1: step totals [3, 30, 300, 3000]

Only one thread calls MPI, but it is not the main thread, so Funneled does not allow it. The channel keeps the steps in order, so both processes make their allreduces in the same order. std::thread::scope joins the communication thread before main returns and drops mpi, which finalizes MPI.

When several threads take turns calling MPI, a Mutex usually keeps the calls apart, and two problems follow:

  • A thread that blocks in an MPI call while it holds the lock keeps the other threads out of MPI until the call returns. If the message it waits for depends on one of those threads, the call never returns.
  • A lock orders the calls of one process. On another process the threads can take their turns in a different order, and collectives on a shared communicator then match the wrong calls: the problem of the next section.

ferrompi checks Serialized in debug builds only. When two calls overlap, the later one returns ThreadLevelViolation; if it is a consuming Request::wait, a scope’s final wait or the call that closes an RMA epoch, which cannot return the error, the process aborts instead. Release builds do not check. A program that cannot keep its calls apart needs Multiple.

Multiple: any thread, at any time

At Multiple threads call MPI at the same time, and the library does the locking. Each thread here runs an allreduce, at the same time as the other two:

use ferrompi::{Mpi, ReduceOp, ThreadLevel};

const THREADS: usize = 3;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init_thread(ThreadLevel::Multiple)?;
    if mpi.thread_level() < ThreadLevel::Multiple {
        eprintln!("MPI granted only {:?}", mpi.thread_level());
        return Ok(());
    }
    let world = mpi.world();
    let rank = world.rank();

    // One communicator per thread. duplicate is collective, so the main
    // thread makes all of them, in the same order on every process.
    let comms = (0..THREADS)
        .map(|_| world.duplicate())
        .collect::<ferrompi::Result<Vec<_>>>()?;

    // Each thread runs its own allreduce, at the same time as the others.
    // Collectives on different communicators never match each other.
    let sums = std::thread::scope(|s| {
        let workers: Vec<_> = comms
            .iter()
            .enumerate()
            .map(|(t, comm)| {
                s.spawn(move || {
                    let value = (t as i32 + 1) * 100 + comm.rank();
                    comm.allreduce_scalar(value, ReduceOp::Sum)
                })
            })
            .collect();
        workers
            .into_iter()
            .map(|w| w.join().unwrap())
            .collect::<ferrompi::Result<Vec<_>>>()
    })?;
    println!("rank {rank}: thread sums {sums:?}");
    Ok(())
}

With two processes it prints:

rank 0: thread sums [201, 401, 601]
rank 1: thread sums [201, 401, 601]

Each thread uses its own communicator, made with duplicate (MPI_Comm_dup) before the threads start. duplicate is collective, so the main thread makes all three, in the same order on every process. The copies are what keep the threads’ allreduces apart.

Collectives on a shared communicator

MPI matches the collectives on a communicator in the order each process makes them, whichever thread made them and whatever operation they are. If two threads of each process share a communicator, their calls can reach MPI in a different order on each process:

Depending on the library and the calls, the mismatched program returns wrong data, reports an error or hangs. A lock does not help: it keeps two calls from overlapping, but not in the same order on every process. Give each thread its own communicator, or make all the collectives on a communicator from one thread. Communicator is Sync, so neither the compiler nor ferrompi catches the mistake.

Messages across threads

Point-to-point messages follow chapter 2’s matching rules within a communicator: by source, tag and order. When two threads of one process post receives that match the same messages, which thread gets which message depends on timing. Give each thread its own tag or its own communicator, so that a receive matches only the messages meant for its thread.

A probe followed by a receive has a race at Multiple: another thread can receive the probed message between the two calls. Chapter 2’s mprobe closes the race, and the Message it returns is Send, so one thread can probe and hand the message to another thread to receive.

What Multiple costs

At Multiple the library protects its internal state on every call, and threads that call MPI at the same time can wait for each other inside it. How much that costs depends on the library and how it was built. MPICH can spread communicators over several internal channels, which it calls VCIs, so that threads on different communicators wait for each other less; MPIR_CVAR_CH4_NUM_VCIS sets how many it uses, and the default is one. Measure before you choose: a program whose threads call MPI rarely can run as fast at Funneled.

A library can also raise the level on its own. With MPIR_CVAR_ASYNC_PROGRESS=1, MPICH starts the progress thread from chapter 5, a thread that the program did not start and that runs inside MPI, and grants Multiple whatever the program asked for. Chapter 1’s context program, which calls Mpi::init(), then prints:

MPIR_CVAR_ASYNC_PROGRESS=1 mpiexec -n 2 target/debug/examples/context
rank 0 of 2 at thread level Multiple
rank 1 of 2 at thread level Multiple

ferrompi then allows calls from every thread, because the rules follow the granted level. The progress thread needs a CPU too: MPICH’s description of the variable advises leaving a hardware thread free for it.

What may cross threads

Rust’s Send and Sync say which handles a thread may move to another thread or share with one, and so where an MPI call can come from. The thread level then decides whether that thread may make the call:

TypeSend and SyncWhy
Communicator, Groupyesan index into a table of MPI handles, with no tie to a thread
CustomDatatype, UserOpyesa user op’s closure can run on any thread, even one of MPI’s own (chapter 4)
PersistentRequest, Message, Statusyeseach owns what it refers to
Requestnorefers to the scope that started it
Mpinostays on the main thread, where dropping it finalizes MPI
Win, its epochs, WinViewnoa window stays on the thread that created it

A thread that makes nonblocking calls opens its own ferrompi::scope, and its requests stay on that thread. Placing processes and threads

The launcher decides which CPUs each process may run on, and the threads of a process share them. A program can ask how many it got with std::thread::available_parallelism, which on Linux counts the CPUs the process is bound to:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // How many CPUs the launcher left this process. This is the most threads
    // it can run at once without sharing a CPU.
    let cpus = std::thread::available_parallelism().map_or(1, |n| n.get());
    println!("rank {}: {cpus} CPUs available", world.rank());
    Ok(())
}

MPICH’s launcher, Hydra, binds nothing by default, so each process may run on every CPU of the node. On a laptop with 14 CPUs, the program prints:

rank 0: 14 CPUs available
rank 1: 14 CPUs available

-bind-to core:2 binds each process to two cores:

mpiexec -n 2 -bind-to core:2 target/debug/examples/placement
rank 0: 4 CPUs available
rank 1: 2 CPUs available

The two processes got different counts because this processor has cores with two hardware threads and cores with one, and available_parallelism counts hardware threads. Count the CPUs a process got, not the cores you asked for.

Unbound processes compete for the same CPUs. A thread pool sized to the node in each of two processes runs twice as many threads as there are CPUs, and the operating system switches them in and out. A thread that is switched out in the middle of a collective holds up every process waiting in that collective. Size each pool to its process’s CPUs: rayon reads RAYON_NUM_THREADS, OpenMP reads OMP_NUM_THREADS, and a pool sized with available_parallelism follows the binding.

Open MPI’s mpirun binds by default: each process to one core when there are at most two processes, to a socket when there are more, and to nothing when there are more processes than cores. Two processes with four threads each then run each process’s threads on a single core. The PE=n modifier of --map-by gives each process n cores, and --report-bindings (--display bind in Open MPI 5) prints what each process got. The mpirun man page of your version has the syntax.

Under Slurm, srun starts the processes. Its --cpus-per-task option gives each process that many CPUs, and --cpu-bind=cores asks for binding, which otherwise depends on how the cluster is configured. Some Slurm versions do not pass sbatch’s --cpus-per-task on to srun, so give it to srun as well. A job of two nodes, with two processes of four threads on each:

#!/bin/bash
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=2
#SBATCH --cpus-per-task=4
srun --cpus-per-task=4 --cpu-bind=cores target/release/examples/placement

Running the placement program as the first step of a job shows what each process got before the real program runs.

When threads go wrong

SymptomLikely cause
“MPI call not permitted on this thread at the provided thread level”A call from a thread the level does not allow. Check thread_level(): MPI may have granted less than the program asked for.
“ferrompi: … dropped on thread …”, then an abortA worker thread dropped a handle whose drop calls MPI, at Single or Funneled.
A collective that hangs or returns wrong data, only sometimesThreads that share a communicator made its collectives in a different order on different processes.
A receive that gets another thread’s messageTwo threads receive with the same source and tag on one communicator.
An abort in a wait at Serialized, in a debug buildTwo threads called MPI at the same time. A release build does not check.
Threads that make the program slowerMore threads than CPUs, or every thread of a process bound to one core, as Open MPI does by default for two processes.

Exercises

  1. In the funneled program, make each worker call world.allreduce_scalar on its own sum, and read the error each one returns. Then ask for Multiple instead. What else must change before the workers’ allreduces are correct?
  2. In the funneled program, sum (x as f64).sqrt() over a hundred times more values, so that the work takes a while, and time it with std::time::Instant. With MPICH, compare -bind-to core and -bind-to core:4, and print available_parallelism in each run.
  3. In the communication-thread program, send each step’s total back to the main thread over a second channel, and make each step’s value depend on the total of the step before. What is left for the two threads to do at the same time?
  4. In the Multiple program, make every thread call its allreduce on world instead of its own copy. Run it a few times with two and four processes. Which sums can a thread get, and why is the program wrong even when it prints the right ones?
  5. With MPICH, run the wrong-thread program with MPIR_CVAR_ASYNC_PROGRESS=1. Why does the line about the worker thread disappear?

Summary

  • A hybrid program runs fewer processes per node, each with several threads, which share one copy of the process’s data. One process per socket keeps each process’s memory local.
  • Mpi::init_thread asks for a thread level, and thread_level() returns the one MPI granted, which can be lower, or higher. The granted level’s rules are the ones that apply.
  • A program that starts threads asks for at least Funneled. At Funneled only the main thread calls MPI; at Serialized any thread, one call at a time; at Multiple, any thread at any time.
  • ferrompi refuses a call from the wrong thread at Single and Funneled, aborts on a wrong-thread drop there, and checks Serialized in debug builds only.
  • Collectives on a communicator match in the order each process makes them. Threads that make collectives at Serialized or Multiple each need their own communicator; a lock is not enough.
  • Communicators, groups, datatypes, user ops, persistent requests and messages may cross threads. Requests stay with their scope, and Mpi and windows stay on the thread that created them.
  • The launcher binds processes to CPUs: MPICH’s to none by default, Open MPI’s to one core for up to two processes. Size each process’s threads to the CPUs available_parallelism reports.
