Part II · Chapter 11

The safety model

A nonblocking call gives MPI the address of a buffer that Rust still owns, and until the request completes both may touch it. Nothing in Rust’s type system knows about MPI. This chapter shows how ferrompi’s safe API makes the compiler, and in a few places the run time, keep the rules the MPI standard leaves to the caller, and which rules it still leaves to you.

By the end of the chapter you can say why a request whose drop waits is not enough, read the scope’s lifetimes and the errors they produce, say what a panic does to a pending operation, explain why persistent requests and windows own their buffers and why no handle borrows Mpi, name every case in which Mpi’s drop skips MPI_Finalize, and name the unsafe calls that remain and what they ask of you.

The design is ADR 0007, and ADR 0008 for window memory. The excerpts of ferrompi’s source below name the file they come from. A comment // … marks lines left out. CI checks that every excerpt still matches its file.

Two owners of one buffer

From the moment MPI_Irecv returns until its request completes, MPI may write the receive buffer at any time: inside any later MPI call, or from a progress thread. Until an MPI_Isend completes, MPI may read the send buffer. The standard (MPI-4.1 §3.7) asks the caller not to touch either in between, and not to free them. A C program that breaks the rule compiles, and usually runs, until a message arrives at the wrong moment.

ferrompi’s nonblocking calls take the buffer as a borrow:

    pub fn isend<'s, T: MpiDatatype>(
        &self,
        s: &'s Scope<'s, '_>,
        data: &'s [T],
        dest: impl Into<Source>,
        tag: i32,
    ) -> Result<Request<'s>> {
    pub fn irecv<'s, T: MpiDatatype>(
        &self,
        s: &'s Scope<'s, '_>,
        data: &'s mut [T],
        source: impl Into<Source>,
        tag: impl Into<Tag>,
    ) -> Result<Request<'s>> {

The send buffer is shared, &'s [T], so Rust may still read it but not write it. The receive buffer is exclusive, &'s mut [T], so nothing else may read or write it. Both borrows last for 's, the lifetime of the scope s, not for the life of the returned Request<'s>. That difference is most of this chapter. The table lists what MPI forbids while an operation is pending, and what stops each in ferrompi:

Why a guard is not enough

The obvious design is the one ferrompi 0.6 had: irecv returns a request that borrows the buffer, and the request’s Drop waits. While the request lives the buffer is borrowed, and when it drops MPI is done. It fails because Rust does not promise that a value’s drop runs. std::mem::forget is a safe function: it takes a value, ends every borrow the value holds, and runs no drop.

Rust settled this weeks before 1.0. The standard library’s first scoped threads, thread::scoped, returned a guard whose drop joined the thread, and in April 2015 it was shown that forgetting the guard let the thread outlive the data it borrowed. Rust kept mem::forget safe (RFC 1066) and removed thread::scoped. std::thread::scope, which takes a closure and joins every thread before it returns, arrived in Rust 1.63. MPI has the same problem: a borrow ends when the value holding it is forgotten, not when MPI stops using the memory.

The program below forgets a pending receive on rank 0. Rank 1 sends 300 ms late, so the receive is still pending when its request is forgotten.

use std::time::{Duration, Instant};

use ferrompi::{Error, Mpi};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    if world.size() != 2 {
        return Err(Error::Internal("run with -n 2".into()));
    }
    world.barrier()?;

    if world.rank() == 0 {
        let mut buf = [0u32; 4];
        let start = Instant::now();
        ferrompi::scope(|s| {
            let request = world.irecv(s, &mut buf, 1, 0)?;
            // Safe code may forget any value. The receive is still pending.
            std::mem::forget(request);
            Ok(())
        })?;
        // The scope returned, so MPI has finished with buf.
        let waited = start.elapsed() >= Duration::from_millis(200);
        println!("rank 0: after the scope, buf = {buf:?}");
        println!("rank 0: the scope waited for the send: {waited}");
    } else {
        // Send late, so the receive is still pending when rank 0 forgets it.
        std::thread::sleep(Duration::from_millis(300));
        world.send(&[42u32, 43, 44, 45], 0, 0)?;
    }
    Ok(())
}
rank 0: after the scope, buf = [42, 43, 44, 45]
rank 0: the scope waited for the send: true

The scope did not return until the message had arrived. Under ferrompi 0.6 the same program compiled too, but nothing waited: right after the forget, buf could be read, written or freed while the receive was still pending.

The scope

ferrompi 0.7 moved the wait from the request into a function that takes a closure, the shape of std::thread::scope. A closure cannot be forgotten halfway: scope calls it, and whatever the closure does, the code after the call runs.

pub fn scope<'env, R>(f: impl for<'s> FnOnce(&'s Scope<'s, 'env>) -> Result<R>) -> Result<R> {
    let token = rt::open_scope().map_err(|code| Error::from_code_with_op(code, "scope"))?;
    let scope = Scope {
        registry: Registry::new(),
        scope: PhantomData,
        env: PhantomData,
    };
    let result = catch_unwind(AssertUnwindSafe(|| f(&scope)));
    let end = scope.registry.complete_all("scope");
    drop(token);
    match result {
        Err(payload) => resume_unwind(payload),
        Ok(Err(error)) => Err(error),
        Ok(Ok(value)) => end.map(|()| value),
    }
}
  1. rt::open_scope counts the scope as open on this thread, and refuses before init or once finalize has begun. The token lives until the requests are complete; what Mpi’s drop waits for shows why.
  2. The Scope holds a Registry, the list of requests still pending.
  3. catch_unwind runs the closure, so a panic stops here instead of unwinding past pending requests.
  4. complete_all completes every request still registered. It runs whether the closure returned Ok, returned Err or panicked.
  5. Only then does scope return: it resumes the panic, returns the closure’s error, or returns its value, unless the final wait failed.

A Request has no Drop. Dropping one, or forgetting it, leaves it in the registry, and the scope completes it. wait and test are for a program that needs the result earlier: the status of a receive, or the knowledge that a message has arrived before the next step.

Two lifetimes, both invariant

The closure takes &'s Scope<'s, 'env> for every 's, which is what for<'s> says. Its body has to compile without knowing 's, except that 's lasts beyond the closure’s end. A buffer given to irecv(s, …) is borrowed for 's, so it has to outlive the closure, and one declared inside it does not. This doctest from src/scope.rs is rejected:

/// ```compile_fail,E0597
/// # use ferrompi::Mpi;
/// # fn main() -> ferrompi::Result<()> {
/// # let mpi = Mpi::init()?;
/// # let world = mpi.world();
/// ferrompi::scope(|s| {
///     let mut buf = vec![0u8; 4];
///     world.irecv(s, &mut buf, 1, 0)?;
///     Ok(())
/// })?;
/// # Ok(())
/// # }
/// ```

'1 is the compiler’s name for the scope’s lifetime. The buffer dies at the closure’s end, on line 10, and '1 lasts longer. That the compiler cannot shorten '1 to fit the buffer comes from the scope’s two marker fields:

pub struct Scope<'s, 'env: 's> {
    registry: Registry,
    scope: PhantomData<&'s mut &'s ()>,
    env: PhantomData<&'env mut &'env ()>,
}

A type that holds &'a T is covariant in 'a: the compiler may use a value with a long 'a where a shorter one is wanted, which is what usually makes borrows convenient. Here it would be unsound. Were Scope covariant in 's, the compiler could shrink 's to the life of buf and accept the program above, and the final wait, after buf is gone, would complete a receive into freed memory. &'s mut &'s () puts 's behind a &mut, which makes the type invariant in 's: no longer and no shorter. The second field does the same for 'env, the lifetime of what the closure borrows from outside. Neither holds anything at run time. The standard library’s std::thread::Scope declares the same two fields, with a comment that the invariance is necessary for soundness.

src/scope.rs keeps a pair of doctests for each rule: a program marked compile_fail with the error code it must produce, then the same program made correct. CI runs cargo test --doc, so a change that lets a rejected program compile fails the tests.

Why the borrow does not end at the wait

The fourth row surprises people. wait takes the request by value, and once it returns MPI is done with the buffer, yet the buffer is still borrowed. A borrow tied to the request would end when the request is gone, and the compiler cannot tell a request that was waited from one that was forgotten: both are gone. That is the guard of the previous section. The scope’s lifetime is the only one that no safe code can end early, so the buffer is borrowed for all of it. wait returns only the Status; the buffer is yours again when scope returns. A program that needs the data sooner ends the scope there and starts another, as chapter 2’s halo exchange does.

Inside the scope

The registry is the list of requests the scope still has to complete:

pub(crate) struct Registry {
    /// Written by `register` and read only for a set bit of `used`.
    inline: [Cell<MaybeUninit<i64>>; INLINE],
    /// Bit `i` set: `inline[i]` is live.
    used: Cell<u64>,
    /// `-1` marks a free entry.
    spill: RefCell<Vec<i64>>,
}

It keeps up to 64 handles inline, one bit of used per slot, and spills to a Vec past that, so a scope with few requests allocates nothing. Registering a handle takes the lowest free bit:

    fn register(&self, handle: i64) -> u32 {
        let used = self.used.get();
        if used != u64::MAX {
            let slot = (!used).trailing_zeros();
            self.inline[slot as usize].set(MaybeUninit::new(handle));
            self.used.set(used | (1 << slot));
            return slot;
        }
        let mut spill = self.spill.borrow_mut();
        let index = match spill.iter().position(|&entry| entry == -1) {
            Some(index) => {
                spill[index] = handle;
                index
            }
            None => {
                spill.push(handle);
                spill.len() - 1
            }
        };
        (INLINE + index) as u32
    }

A request records its slot and a reference to the registry, so that wait, test and the batch completions can release the slot once MPI has completed the request:

pub struct Request<'s> {
    handle: i64,
    completed: bool,
    kind: RequestKind,
    registry: &'s Registry,
    // …
    slot: usize,
}

Two rules follow from these fields with no code of their own. registry: &'s Registry borrows the scope, which is why a request cannot leave the closure. And Registry is made of Cell and RefCell, so it is not Sync, which makes &Registry not Send, and Request<'s> with it. A request stays on the thread that created it, so the scope that completes it runs there too. No marker or unsafe impl says so: the compiler derives it from the fields. &Scope is not Send either, so each thread that makes nonblocking calls opens a scope of its own, as the threads program in chapter 10 does. Chapter 6 lists what else crosses threads.

The final wait

complete_all returns at once when nothing is registered. Otherwise it calls complete_pending:

    #[cold]
    fn complete_pending(&self, op: &'static str) -> Result<()> {
        let mut first = Ok(());
        loop {
            let live = self.live();
            if live == 0 {
                return first;
            }
            let (ret, progress) = if live <= INLINE {
                self.wait_pass(
                    &mut [0; INLINE][..live],
                    &mut [0; INLINE][..live],
                    &mut [0; INLINE][..live],
                )
            } else {
                self.wait_pass(&mut vec![0; live], &mut vec![0; live], &mut vec![0; live])
            };
            if !progress {
                // …
                scope_abort(op, ret);
            }
            if ret != 0 && first.is_ok() {
                first = Error::check_with_op(ret, op);
            }
        }
    }

Each pass copies the live handles, makes one MPI_Waitall over them through the C layer, and releases the slots MPI reports complete. A pass can fail and still make progress. When one request fails, Open MPI returns at the first failure with the others still pending, and MPICH returns once all have completed. Either way the loop repeats the pass for what is still registered, and returns the first error once every request has completed.

A pass that completed nothing is different: MPI refused the call, or failed without saying which requests completed. The scope cannot know whether MPI is still using the buffers. Returning would end the borrows while MPI might still write, and waiting again would wait for ever, so the scope aborts the process with a line on standard error:

ferrompi: a nonblocking scope could not complete its requests (MPI_Waitall returned N); aborting

A passive-target epoch keeps a registry of its own, for the requests of rput, rget and raccumulate, and its end runs the same wait before the unlock, with “a passive-target epoch” in the message.

Panics

A panic inside the closure unwinds into scope, which catches it before anything the requests borrow can be dropped, completes every request, and then resumes the panic. The program below panics with a receive pending, and catches the panic around the scope to look at the buffer:

use std::panic::{catch_unwind, AssertUnwindSafe};
use std::time::Duration;

use ferrompi::{Error, Mpi};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    if world.size() != 2 {
        return Err(Error::Internal("run with -n 2".into()));
    }

    if world.rank() == 0 {
        let mut buf = [0i32];
        let caught = catch_unwind(AssertUnwindSafe(|| {
            ferrompi::scope(|s| -> ferrompi::Result<()> {
                world.irecv(s, &mut buf, 1, 0)?;
                panic!("something went wrong while the receive was pending");
            })
        }));
        // The scope completed the receive before the panic left it.
        println!("rank 0: the panic was caught: {}", caught.is_err());
        println!("rank 0: buf = {buf:?}");
    } else {
        std::thread::sleep(Duration::from_millis(300));
        world.send(&[7i32], 0, 0)?;
    }
    Ok(())
}
rank 0: the panic was caught: true
rank 0: buf = [7]

Standard error has the panic message:

thread 'main' (…) panicked at examples/panic.rs:18:17:
something went wrong while the receive was pending
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

The receive completed before the panic left the scope, so buf holds rank 1’s 7. Waiting is not always possible. A fence or PSCW epoch ends with a call that is collective or synchronizing, MPI_Win_fence or MPI_Win_complete, and a panicking rank cannot take part in it alone. Leaving the epoch open would let the unwinding free buffers MPI may still read, so the epoch’s runner aborts:

        let result = match catch_unwind(AssertUnwindSafe(|| f(&epoch))) {
            Ok(result) => result,
            Err(_) => epoch_abort("a fence or PSCW epoch was still open during unwind"),
        };
        closing_result(close(self.win_handle), close_op, result)

A lock epoch closes with MPI_Win_unlock, which no other process has to take part in, so its runner completes the epoch’s requests, unlocks, and then resumes the panic:

        let outcome = catch_unwind(AssertUnwindSafe(|| f(&epoch)));
        let completed = epoch.registry.complete_all(wait_op);
        let ret = close(self.win_handle);
        match outcome {
            Err(payload) => {
                let _ = closing_result(ret, close_op, Ok(()));
                resume_unwind(payload)
            }
            Ok(result) => closing_result(
                ret,
                close_op,
                result.and_then(|value| completed.map(|()| value)),
            ),
        }

Owning instead of borrowing

A scope suits a request that lives for one step. A persistent request is made once and started many times, often for the whole run, and a window lives as long as the solver. A borrow that long would put a lifetime on the type, and on every struct that holds one. ferrompi gives these the buffer instead:

pub struct PersistentRequest<T> {
    handle: i64,
    token: Option<rt::HandleToken>,
    send: Vec<T>,
    buffer: Vec<T>,
    counts: Vec<i32>,
    pub(crate) op: Option<Arc<OpRegistration>>,
}

send_init and recv_init take a Vec<T> by value. Moving a Vec copies its pointer, length and capacity, not its elements, so the memory MPI was given stays where it is for the request’s whole life, and the caller, who no longer has the Vec, cannot reallocate it. This doctest in src/persistent.rs is rejected with E0382, use of a moved value:

/// ```compile_fail,E0382
/// # fn f(world: &ferrompi::Communicator) -> ferrompi::Result<()> {
/// let mut data = vec![0u64; 4];
/// let _p = world.recv_init(data, 1, 9)?;
/// data.reserve(4096);
/// # Ok(())
/// # }
/// ```

The request lends its buffer through buffer and buffer_mut while it is inactive, and refuses while it is active. The accessors return a slice, so no caller can reallocate through them (E0599 in the same file), and buffer_mut borrows the request mutably, so a slice cannot be held across start (E0499).

use ferrompi::{Error, Mpi};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    if world.size() != 2 {
        return Err(Error::Internal("run with -n 2".into()));
    }

    if world.rank() == 0 {
        // The request owns the Vec: MPI keeps a pointer into it until the
        // request is freed.
        let mut send = world.send_init(vec![0u64; 3], 1, 0)?;
        for round in 1..=2u64 {
            send.buffer_mut()?.fill(round);
            send.start()?;
            // Active: MPI may be reading the buffer, so the request refuses
            // to lend it.
            match send.buffer_mut() {
                Err(err) => println!("rank 0: round {round}, while active: {err}"),
                Ok(_) => println!("rank 0: round {round}, the buffer was lent"),
            }
            send.wait()?;
        }
        // Hands the buffer back; the request is freed first.
        let buffer = send.into_buffer()?;
        println!("rank 0: buffer returned: {buffer:?}");
    } else {
        let mut recv = world.recv_init(vec![0u64; 3], 0, 0)?;
        for round in 1..=2 {
            recv.start()?;
            recv.wait()?;
            println!("rank 1: round {round} received {:?}", recv.buffer()?);
        }
    }
    Ok(())
}

token is what makes a request active: start takes a token and completion gives it back, and is_active is token.is_some(). into_buffer waits if the request is active, frees it, and returns the Vec; a request dropped while active waits before MPI_Request_free. Its drop starts with the guard for drops:

Once finalizing has begun, the drop makes no MPI call, and a request still active leaks: leak forgets the buffers and the token, so the pointer MPI holds stays valid until the process exits. Forgetting on purpose is the safe answer when the wait cannot run. The program below forgets an active request itself, a receive that no send matches, and then drops Mpi:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // A receive from this process itself, which no send will match.
    let mut recv = world.recv_init(vec![0u8; 16], world.rank(), 99)?;
    recv.start()?;
    // MPI holds a pointer into the receive's buffer. Forgetting the request
    // leaks the buffer, so the pointer stays valid, and its token, so Mpi's
    // drop knows a request is still active.
    std::mem::forget(recv);

    drop(mpi);
    println!("rank {}: Mpi dropped", world.rank());
    // MPI_Finalize did not run, but Mpi is gone, so the guard refuses the
    // barrier.
    match world.barrier() {
        Err(err) => println!("rank {}: barrier after the drop: {err}", world.rank()),
        Ok(()) => println!("rank {}: barrier after the drop succeeded", world.rank()),
    }
    Ok(())
}

Each rank writes one line to standard error:

ferrompi: MPI_Finalize skipped: 1 persistent request(s) still active or matched message(s) not yet received; request buffers stay valid until the process exits

Forgetting the request leaked its Vec, so MPI’s pointer still points at memory nobody else owns, and leaked its token, so Mpi’s drop saw a request still active. Finalizing with an active request is erroneous, and an implementation may free the request’s state, or write the buffer, during MPI_Finalize, so ferrompi skips the call and lets the process exit with MPI initialized. Under MPICH the exit status stays 0. Open MPI turns an exit without MPI_Finalize into status 1, and tests/run_mpi_tests.sh accepts both for the examples it expects to skip finalize. Of the two things the barrier’s error names, only the second happened here: MPI_Finalize never ran. Error::Finalized means the Mpi handle is gone, whatever became of MPI.

Windows follow the same rule. Win::create takes a Vec<T>, and into_buffer, which is collective, returns it after a successful MPI_Win_free. A window whose free is skipped or fails leaks its buffer, so no safe code can free a window’s memory while MPI can still reach it.

Handles without a lifetime

Requests borrow for a scope. Everything else, communicators, groups, windows, persistent requests, datatypes and user operations, is 'static, and none borrows Mpi. An audit of 0.6 proposed the opposite, Communicator<'mpi> and Win<'mpi, T>, so that the compiler would reject a handle used after Mpi is dropped. ADR 0007 rejects it because of structs like this one, from examples/sddp_pattern.rs:

/// A solver keeps one boxed context for the whole run. Handles carry no borrow
/// of `Mpi`, so the context can own all of them.
///
/// Fields drop in declaration order, so the window and the communicators are
/// freed before `mpi` finalizes MPI. `mpi` must stay the last field.
struct Ctx {
    win: Win<f64>,
    node: Communicator,
    world: Communicator,
    mpi: Mpi,
}

With a lifetime on each handle, win, node and world would borrow mpi, a field of the same struct, and Rust has no way to write a struct that borrows from itself. A solver that keeps one context for the whole run would not compile. The comment on Ctx names the rule that takes the lifetime’s place: fields drop in declaration order, so mpi goes last. The program below breaks it:

use ferrompi::{Communicator, Mpi, Win};

/// Fields drop in declaration order. This one puts mpi first, so Mpi's drop
/// runs while the window is still alive.
struct Ctx {
    mpi: Mpi,
    world: Communicator,
    win: Win<f64>,
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let win = Win::<f64>::allocate(&world, 4)?;
    let ctx = Ctx { mpi, world, win };

    let rank = ctx.world.rank();
    println!(
        "rank {rank}: a context at {:?}, with {} window elements",
        ctx.mpi.thread_level(),
        ctx.win.local().len()
    );
    drop(ctx);
    println!("rank {rank}: the context was dropped");
    Ok(())
}

Each rank writes one line to standard error:

ferrompi: MPI_Finalize skipped: 1 window(s) still alive; their memory stays valid until the process exits

Mpi’s drop ran first, with the window alive, and skipped MPI_Finalize. Some MPI libraries free the memory of a window they allocated inside MPI_Finalize, and some tear down state that still tracks a buffer given to MPI_Win_create and abort; neither is safe while a Win can still reach the memory. The window’s own drop came next, found finalizing begun, and made no MPI call. Nothing crashed, but MPI was never finalized. Move mpi to the last field and the warning goes away.

The lifecycle

Without a lifetime, the compiler cannot stop a handle from being used after Mpi is gone, so every call checks at run time, in the guard chapter 9 showed. The guard reads one state per process:

StateNew callsCompletions and closing callsDrops
Uninitrefused: “MPI is not initialized”refusedno handle exists yet
Initializingrefused on every thread but the one running initthe sameno handle exists yet
Active(level)at Single and Funneled, only on the init thread; at Serialized and Multiple, on any thread, counted in flightthe samebelow Serialized, abort on a wrong thread; at or above it, counted

Initializing covers the time MPI_Init_thread runs, before the level it grants is known. Finalizing exists because Mpi’s drop cannot finalize while another thread is in the middle of a call, or inside a scope with requests pending: it refuses anything new, admits the calls that finish what is pending, and waits for them. The externs the guard leaves out are those with nothing to check: the init call itself, the lifecycle and version queries, the error-message lookup, the op-table bookkeeping that makes no MPI call, and the calls made only from a drop, which have a guard of their own because a drop cannot return an error:

pub(crate) fn drop_guard(type_name: &'static str) -> Option<InFlight> {
    // Relaxed: see `enter`'s comment.
    let state = STATE.load(Ordering::Relaxed);
    if state == FINALIZING || state == FINALIZED {
        return None;
    }
    if state == ACTIVE_SINGLE || state == ACTIVE_FUNNELED {
        if !ON_INIT_THREAD.with(Cell::get) {
            drop_abort(type_name);
        }
    } else if state == ACTIVE_SERIALIZED || state == ACTIVE_MULTIPLE {
        return enter_counted(false).ok();
    }
    Some(InFlight(None))
}

Once finalizing has begun it returns None and the drop makes no MPI call; the C layer’s finalize has freed, or will free, what is left in its tables (chapter 10). Below Serialized a drop on the wrong thread can neither call MPI nor return an error, so it aborts with ferrompi: Communicator dropped on thread …, naming the type and the thread. examples/test_drop_wrong_thread.rs checks it.

What Mpi’s drop waits for

impl Drop for Mpi {
    fn drop(&mut self) {
        // …
        if !rt::begin_finalize() {
            return;
        }
        if let Some(reason) = finalize_skip_reason() {
            // A single write so concurrent ranks' output cannot interleave mid-line.
            let msg = format!("ferrompi: MPI_Finalize skipped: {reason}\n");
            let _ = std::io::stderr().write_all(msg.as_bytes());
            return;
        }
        rt::end_finalize();
        // SAFETY: rt::begin_finalize() just returned true, so state was Active —
        // MPI_Init(_thread) succeeded and MPI_Finalize has not yet been
        // called for this process.
        unsafe {
            ffi::ferrompi_finalize();
        }
    }
}

begin_finalize moves the state to Finalizing, waits for the scopes open on other threads and for every call in flight, and returns false if MPI was not active, so there is nothing to finalize. Then finalize_skip_reason looks for anything that makes MPI_Finalize unsafe:

fn finalize_skip_reason() -> Option<String> {
    if rt::scopes_on_this_thread() > 0 {
        return Some(
            "a nonblocking scope is still open on this thread; its requests complete when the scope ends"
                .into(),
        );
    }
    let live = rt::live_handle_tokens();
    if live > 0 {
        return Some(format!(
            "{live} persistent request(s) still active or matched message(s) not yet received; request buffers stay valid until the process exits"
        ));
    }
    #[cfg(feature = "rma")]
    {
        let live = window::live_windows();
        if live > 0 {
            return Some(format!(
                "{live} window(s) still alive; their memory stays valid until the process exits"
            ));
        }
    }
    None
}

Those are all the cases in which MPI_Finalize is skipped. A communicator, group or datatype still alive is not one of them: the C layer’s finalize frees it, and its own drop later makes no MPI call. Each skip writes one line, in a single write so that lines from several ranks cannot interleave, and the state stays Finalizing until the process exits. Together these give the run-time half of the model: a handle that outlives Mpi returns Error::Finalized, and MPI_Finalize never runs under an operation in flight.

Send, Sync and the thread level

Send and Sync are fixed when the program compiles. The thread level is known only when Mpi::init_thread returns, and may be lower than the one requested (chapter 6). So ferrompi makes its handles Send and Sync, which lets them cross threads at all, and checks the level in the guard on every call. The unsafe impl on Communicator carries the argument:

pub struct Communicator {
    pub(crate) handle: i32,
    pub(crate) rank: i32,
    pub(crate) size: i32,
}

// SAFETY: Communicator handles are integer indices into a C-side table.
// Every MPI call goes through the lifecycle guard (`rt::enter`): below
// `ThreadLevel::Serialized` (Single or Funneled), it rejects a call from any
// thread other than the one that called `Mpi::init`/`init_thread`, with
// `Err(Error::ThreadLevelViolation)`, without touching MPI. A `Drop` cannot
// return `Err`, so the equivalent guard (`rt::drop_guard`) instead aborts the
// process on a wrong-thread drop below `Serialized`. At `Serialized`, the
// caller must serialize its own calls (debug builds detect two overlapping
// calls). At `Multiple`, calls from any thread may run concurrently.
//
// The C layer's handle tables claim slots lock-free: five with a C11
// atomic compare-exchange, the request table with an atomic bitmap
// (`fetch_or`), so there are no data races under MPI_THREAD_MULTIPLE.
// See docs/adr/0002-handle-tables.md for the full rationale and design.
unsafe impl Send for Communicator {}
// SAFETY: &Communicator exposes only reads of immutable fields and FFI calls
// gated by the same lifecycle guard described above, so its thread safety
// follows the requested `ThreadLevel` the same way.
unsafe impl Sync for Communicator {}

The fields are three i32, so the compiler would derive both traits anyway. The unsafe impl is there to state the argument, which rests on the guard and on the C tables, not on the fields. Group and CustomDatatype carry the same pair. Mpi is the exception:

pub struct Mpi {
    /// The thread level that was provided
    thread_level: ThreadLevel,
    /// This process's rank in `MPI_COMM_WORLD`, read once at init
    world_rank: i32,
    /// The size of `MPI_COMM_WORLD`, read once at init
    world_size: i32,
    /// Marker to make Mpi !Send and !Sync
    _marker: PhantomData<*const ()>,
}

A raw pointer is neither Send nor Sync, so PhantomData<*const ()> makes Mpi neither. The thread that initialized MPI keeps the handle, so MPI_Finalize runs on that thread, as the standard asks. Other threads borrow a Communicator.

What unsafe asks of you

Two parts of the API stay unsafe, each with a written contract. The first is PlainData, which a type implements to be sent through a derived datatype:

pub unsafe trait PlainData: Copy + 'static {}
// SAFETY: every MpiDatatype is a primitive integer or float, and any bit pattern of its size is a valid value.
unsafe impl<T: MpiDatatype> PlainData for T {}
// SAFETY: an array of plain data is plain data — its bytes are exactly N back-to-back elements, each valid for any bit pattern.
unsafe impl<T: PlainData, const N: usize> PlainData for [T; N] {}

An implementation promises that every bit pattern of the type’s size is a valid value, because MPI writes bytes and Rust then reads them as the type: a bool that receives a 2, or a Box that receives someone else’s address, is undefined behaviour. The numeric types and arrays of plain data have it already; a #[repr(C)] struct of them needs one line of unsafe impl, and chapter 12 writes one. Sending a Box through a datatype is rejected with E0277, in src/datatype.rs.

The second is the zero-copy view of window memory. WinView reads and writes each element with one Relaxed atomic, so a peer’s put arriving at the same time never makes a load undefined, only stale. A program that knows its phases can borrow the region as a slice instead:

    /// # Safety
    ///
    /// No process writes the region by store, put or accumulate while the slice
    /// lives, and the writes it must observe were published before it was created,
    /// either by a fence or `MPI_Win_wait` at this process that completed them, or
    /// by process synchronization after they completed, then `MPI_Win_sync` at this
    /// process inside a passive-target epoch.
    ///
    /// A store through any view of the region counts, this view's
    /// [`write`](Self::write) and [`copy_from_slice`](Self::copy_from_slice)
    /// included: the borrow checker does not stop them while the slice lives.
    // …
    pub unsafe fn as_slice(&self) -> &[T] {

The contract is about MPI’s memory model, which the borrow checker cannot see: no process writes the region while the slice lives, and the writes the slice must observe were published before it was made, by a fence, a wait, or a sync inside a lock epoch. ADR 0008 records the reasoning; chapter 5 shows the epochs. as_mut_slice has a contract of the same kind.

The RMA assertions are a third obligation, without the keyword. no_store, no_put, no_precede, no_succeed and no_check are safe constructors, but an assertion that is false is erroneous, and MPI may act on it, for instance by skipping work the epoch needed. ferrompi cannot check them; ADR 0007 lists them as the caller’s.

What the model does not cover

The model is about memory: no buffer is freed, aliased or reused while MPI may touch it, and no call reaches MPI after finalize or from a thread the level forbids. It does not make a program correct:

  • Deadlocks and mismatched collectives compile, and hang (chapter 2, chapter 3). A scope whose receive no send matches waits at its end for ever.
  • A scope that hangs on another thread keeps Mpi’s drop waiting too, without a timeout.
  • A peer that stops calling MPI, or leaks a window, leaves the others blocked in a collective free or a closing call.
  • A message received as a type other than the one sent is plain data reinterpreted: sound, and wrong (chapter 4).
  • Under panic = "abort" nothing waits.

Summary

  • A nonblocking call shares a buffer with MPI until its request completes. The standard leaves it to the caller to keep away from the buffer in between.
  • A request whose drop waits is not enough, because mem::forget is safe and ends a borrow without running the drop. ferrompi moves the wait into scope, a closure that cannot be left before every request has completed.
  • The scope’s lifetimes are invariant, so a buffer has to outlive the scope, and stays borrowed after wait. The compile_fail doctests in src/scope.rs pin each rule to an error code.
  • The final wait repeats MPI_Waitall while it makes progress, and aborts when it cannot establish completion, rather than hand back a buffer MPI may still write.
  • A panic in a scope or a lock epoch completes or unlocks, then unwinds. A panic in a fence or PSCW epoch, or in a reduction closure, aborts.
  • Persistent requests and windows own their buffers, and no handle has a lifetime, so a struct can own Mpi and its handles, with mpi as its last field.
  • A lifecycle state checked on every call replaces the lifetime. Calls after Mpi’s drop return Error::Finalized, and MPI_Finalize is skipped while a scope on the dropping thread, an active persistent request, an unreceived message or a window remains.
  • What stays with you: PlainData and the zero-copy slice contracts, the RMA assertions, and the matching and ordering that MPI always left to the program.
