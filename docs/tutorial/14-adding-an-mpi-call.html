Part II · Chapter 14

Adding an MPI call

Every MPI call ferrompi offers was added the same way: a C function and its declaration, a Rust declaration of that function, a safe method around it, and a test that runs as a job. This chapter follows one call that was added, Communicator::create_group, through each place it touched, then through what review added after its first commit.

By the end of the chapter you can say what to find out about an MPI call before writing any code for it, write its five pieces in the order the architecture guide gives, add a ferrompi error code on both sides of the boundary, order a test’s steps so that a mistake fails instead of hanging, read a call’s history in its commit messages, and say what changes when the call moves data.

The architecture guide’s entry-point pattern lists the five places, and CONTRIBUTING.md the commands to run before opening a pull request. The excerpts below name the file they come from. A comment // … or /* ... */ marks lines left out. CI checks that every excerpt still matches its file.

The call

MPI_Comm_create_group, from MPI 3.0, makes a communicator from a group of a parent communicator’s processes, as MPI_Comm_create does. The two differ in who takes part (chapter 1). MPI_Comm_create is collective over the parent: every process of the parent calls it, members of the group or not. MPI_Comm_create_group is collective over the group only. The members call it with the same group and a tag, and the other processes may call it or not: for them the call is local and returns MPI_COMM_NULL.

ferrompi had create, and 0.7.0 added create_group. It is a good call to follow: it touches every layer, it adds an object to a table, it has a value that MPI checks and a rule that no library checks, and the history of how it was added is in the repository.

Before the code

The section of the standard that defines a call answers most of the questions the code depends on. MPI_Comm_create_group is in section 7.4.2 of MPI 4.1. For each question, the answer for create_group, and what it decides:

QuestionFor create_groupWhat it decides
Which MPI version defines it?3.0No version test. A call from MPI 4.0 compiles under a version test, with a stub for older libraries (below).
Over which processes is it collective?The members of the groupWhat the method’s documentation says, and which ranks the test lets skip the call.
What does it return, and where?MPI_COMM_NULL to a process outside the group-1 in C, None in Rust.
Does it create an MPI object?A communicatorA slot in the communicator table, MPI_ERRORS_RETURN on the new communicator, and an error for a full table.
Does it move data?NoNo count, element type or buffer to check.
Which of its values does MPI check?The tagNothing to check in Rust: MPI returns an error of class Tag.
Which of its rules may a library leave unchecked?The group is a subset of the parent’s; every member passes the same group and tagWhat each library does when a rule is broken, which has to be measured.

The last row is where most of the work went, as What review added shows. The standard calls a program that breaks such a rule erroneous and lets the library do anything, and what MPICH and Open MPI do is found only by running them.

The header

The new function is declared in csrc/ferrompi.h, next to the other functions that create a communicator:


/**
 * Create a sub-communicator from a parent communicator and a group
 * (MPI_Comm_create_group). Collective over group_handle only: its members
 * call with the same group and tag. For a rank not in group_handle the call
 * is local and newcomm_handle is set to -1.
 * Returns FERROMPI_ERR_GROUP_NOT_IN_COMM, before the MPI call, when group_handle
 * has a member that is not in comm_handle.
 */
int ferrompi_comm_create_group(int32_t comm_handle,
                               int32_t group_handle,
                               int32_t tag,

It keeps the header’s rules (chapter 10): handles are int32_t, the new handle comes back through a pointer, and the return value is an MPI error code or a negative ferrompi code. The comment says over which processes the call is collective, what a process outside the group receives, and which ferrompi code it can return. The Rust declaration and the safe method repeat those facts, and the header is where a reader of the C layer finds them.

The C function

The function, in csrc/ferrompi.c, is as short as most functions there:

int ferrompi_comm_create_group(int32_t comm_h,
                               int32_t group_h,
                               int32_t tag,
                               int32_t* out_h) {
    MPI_Comm parent = get_comm(comm_h);
    MPI_Group g = get_group(group_h);
    if (parent == MPI_COMM_NULL || g == MPI_GROUP_NULL) return MPI_ERR_ARG;
    int in_ret = check_group_in_comm(parent, g);
    if (in_ret != MPI_SUCCESS) return in_ret;
    MPI_Comm new_comm;
    int ret = MPI_Comm_create_group(parent, g, tag, &new_comm);
    if (ret != MPI_SUCCESS) return ret;
    return store_comm(new_comm, out_h);
}

It turns the two handles into MPI objects through the tables (chapter 10). A handle that names no object returns MPI_ERR_ARG; safe Rust cannot pass one, since a Communicator and a Group each own their handle until they are dropped. It then checks the group, calls MPI with the tag unchanged, and hands the result to store_comm, which every function that gets a communicator from MPI shares (chapter 10): it writes -1 for MPI_COMM_NULL, installs MPI_ERRORS_RETURN on the new communicator, and takes a slot for it. When the table is full, it returns the full-table code and leaves the communicator allocated, since freeing it is collective over its members.

A check MPI does not make

The standard requires the group to be a subset of the parent’s group, and the libraries do not check it. The C layer does, before the call:

/* MPI_SUCCESS if every member of `group` is in `comm`, FERROMPI_ERR_GROUP_NOT_IN_COMM
 * if one is not, or the error of a group call. MPI requires the subset
 * (MPI-4.1 7.4.2) and need not check it: with a group that has a member outside
 * the communicator, MPI_Comm_create_group ends the process in MPICH 4.2 and in
 * Open MPI 4.1 and 5.0, and MPI_Comm_create returns a communicator in Open MPI.
 * The group calls go through GROUP_CALL, and they leave two things built
 * before the creating call of MPICH 4.2: the communicator's group, which its
 * MPI_Comm_create_group reads without building and without which it ends the
 * process for any group of two or more members, and the ordered member lists
 * of both groups, which it would otherwise build on first use inside the
 * call. The work is local: in MPICH 4.2 it is linear in the two group sizes
 * once the lists exist; in Open MPI it is the product of the two sizes. */
static int check_group_in_comm(MPI_Comm comm, MPI_Group group) {
    MPI_Group comm_group, outside;
    int ret;
    GROUP_CALL(ret, MPI_Comm_group(comm, &comm_group));
    if (ret != MPI_SUCCESS) return ret;
    GROUP_CALL(ret, MPI_Group_difference(group, comm_group, &outside));
    MPI_Group_free(&comm_group);
    if (ret != MPI_SUCCESS) return ret;
    int outside_size = 0;
    ret = MPI_Group_size(outside, &outside_size);
    if (outside != MPI_GROUP_EMPTY) MPI_Group_free(&outside);
    if (ret != MPI_SUCCESS) return ret;
    return outside_size == 0 ? MPI_SUCCESS : FERROMPI_ERR_GROUP_NOT_IN_COMM;
}

MPI_Group_difference gives the members of the group that are not in the communicator, which is empty exactly when the group is a subset. MPI_Comm_group and MPI_Group_difference go through GROUP_CALL, the one lock in the file (chapter 10), because MPICH builds a group’s member list on first use without locking the group. They also leave built what MPI_Comm_create_group would otherwise build inside the call. The check is local and runs on every caller, member or not, so a rank that passes such a group is refused whether or not it is in it.

A new error code

No MPI error class says “a member outside the communicator”, so the check returns a ferrompi code. A new code is written twice. The header defines it:

/* Returned by ferrompi_comm_create and ferrompi_comm_create_group, before the
 * MPI call, for a group with a member that is not in the communicator.
 * src/error.rs maps it to Error::InvalidArgument. This MUST stay in sync with
 * the mirrored const in src/error.rs. */
#define FERROMPI_ERR_GROUP_NOT_IN_COMM (-7009)

and src/error.rs defines the same number and maps it to a variant:

// Returned by the `ferrompi_comm_create` and `ferrompi_comm_create_group`
// shims, before their MPI call, for a group with a member that is not in the
// communicator. Intercepted in [`Error::from_code`] and mapped to
// [`Error::InvalidArgument`]. This MUST match
// `FERROMPI_ERR_GROUP_NOT_IN_COMM` in `csrc/ferrompi.h`.
const FERROMPI_ERR_GROUP_NOT_IN_COMM: i32 = -7009;
        if code == FERROMPI_ERR_GROUP_NOT_IN_COMM {
            return Error::InvalidArgument {
                arg: "group",
                reason: "member outside the communicator",
            };
        }

Each definition names the other in a comment, and that is all that ties them: no build step compares the two numbers. A unit test in src/error.rs checks that the Rust constant maps to Error::InvalidArgument, which runs without MPI (chapter 13). The C layer’s codes run from -7001 to -7009; those from -7101 on are the guard’s, defined in Rust alone, since C never returns them.

The Rust declaration

src/ffi.rs declares the function again, in Rust:

    pub fn ferrompi_comm_create_group(
        comm: int32_t,
        group: int32_t,
        tag: int32_t,
        newcomm: *mut int32_t,
    ) -> c_int;

The declaration sits inside the guarded_extern! block, so the macro declares the C function in a module of its own, raw, and gives the crate a wrapper of the same name that enters the lifecycle guard first (chapter 9). A function goes in the unguarded block above it only if it is one of the kinds the comment there lists: one that is legal before init or after finalize, one that makes no MPI call, wtime, one called only from a Drop, or the op-table calls of UserOp.

Nothing checks this declaration against the header. Rust takes an extern block on trust: with a wrong type or a missing argument, the crate compiles, links and passes garbage to the C function. The reviewer compares the two by eye, argument by argument, and the MPI tests catch a mismatch only when it makes a result wrong.

The safe method

The method is in src/comm/mgmt.rs, with the other ways to make a communicator:

    /// Create a sub-communicator from a group, collectively over the members
    /// of the group only (`MPI_Comm_create_group`).
    ///
    /// `group` must be a subset of `self`'s group. Every member of `group`
    /// must invoke the call, with a group of the same members in the same
    /// order and with the same `tag`; the other ranks of `self` take no part.
    /// A rank that is not a member may still make the call: it is then local
    /// and returns `Ok(None)`, as it does for the empty group.
    // …
    /// # Errors
    ///
    /// Returns [`Error::InvalidArgument`](crate::Error::InvalidArgument) if
    /// `group` has a member that is not in `self`, to a member of `group` and
    /// to any other caller alike; [`Error::Mpi`] with class
    /// [`MpiErrorClass::Tag`](crate::MpiErrorClass::Tag) if `tag` is negative
    /// or above the library's tag limit; or
    /// [`Error::ResourceExhausted`](crate::Error::ResourceExhausted) if the
    /// communicator table is full.
    // …
    pub fn create_group(&self, group: &Group, tag: i32) -> Result<Option<Communicator>> {
        let mut new_handle: i32 = -1;
        // SAFETY: self.handle is owned by this Communicator; group.handle is owned by the Group
        // argument and remains valid for the duration of this call.
        let ret = unsafe {
            ffi::ferrompi_comm_create_group(self.handle, group.handle, tag, &mut new_handle)
        };
        Error::check_with_op(ret, "comm_create_group")?;
        Self::from_optional_handle(new_handle)
    }

The body is the pattern every method follows: an out-value set to -1, one unsafe call with its SAFETY comment, which clippy requires, the return code checked by Error::check_with_op under the name of the C function without its ferrompi_ prefix, and the handle turned into the value Rust returns:

    /// Convert a communicator-handle result into `Option<Self>`, treating a
    /// negative handle as `MPI_COMM_NULL` (used by split, split_type, create,
    /// create_group and `Mpi::create_from_group`).
    pub(crate) fn from_optional_handle(new_handle: i32) -> Result<Option<Self>> {
        if new_handle < 0 {
            Ok(None)
        } else {
            Self::from_handle(new_handle).map(Some)
        }
    }

The method checks nothing itself. It has no rank, count or buffer to check, MPI checks the tag, and the C layer checks the group. A method checks in Rust what MPI does not check, or would check only after a collective had started (chapter 9).

Most of the method is its documentation. It says over which processes the call is collective, what a process outside the group gets, what the C layer checks and what that costs, which rules nobody checks and what breaking them does, and what threads must do with the tag. Its # Errors section names each error and when it comes. The example is compiled by cargo test --doc and not run, since it needs a job; the missing_docs lint, which CI turns into an error, refuses a public item with no documentation at all.

A program that reaches four of the outcomes, on three processes:

use ferrompi::{Error, Mpi};

fn main() -> Result<(), Error> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();
    let world_group = world.group()?;
    let pair = world_group.include(&[0, 1])?;

    // Every rank calls. For rank 2, outside the pair, the call is local.
    match world.create_group(&pair, 7)? {
        Some(sub) => println!("rank {rank}: rank {} of {}", sub.rank(), sub.size()),
        None => println!("rank {rank}: not a member, None"),
    }

    // A tag MPI refuses. The group of this rank alone: no other rank takes part.
    let alone = world_group.include(&[rank])?;
    match world.create_group(&alone, -5) {
        Err(Error::Mpi { class, .. }) => println!("rank {rank}: tag -5: class {class:?}"),
        other => println!("rank {rank}: tag -5: {:?}", other.map(|c| c.is_some())),
    }

    // A communicator of one rank, and a group of two: the C layer refuses it.
    let single = world.split(Some(rank), 0)?.expect("every rank has a color");
    match single.create_group(&pair, 8) {
        Err(e) => println!("rank {rank}: the pair on a communicator of one: {e}"),
        Ok(c) => println!(
            "rank {rank}: the pair on a communicator of one: {}",
            c.is_some()
        ),
    }
    Ok(())
}

The test

The test is a program in examples/ with a directive, which the runner finds and runs as a job (chapter 13). Its head and first two steps:

//! Run with: mpiexec -n 4 ./target/debug/examples/test_comm_create_group
// mpi-test: np=2.. timeout=30
// …
    // 1. A tag MPI does not accept. With the group of this rank alone, no
    //    other rank takes part in the call.
    let alone = world_group.include(&[rank]).expect("include failed");
    let ok = common::class_of(&world.create_group(&alone, -5)) == Some(MpiErrorClass::Tag);
    common::check(&world, ok, "create_group refuses a negative tag");

    // 2. Only the members call.
    let mut ok = true;
    if member {
        ok = match world.create_group(&group, 3) {
            Ok(Some(sub)) => {
                sub.size() == members
                    && sub.rank() == rank / 2
                    && sub.allreduce_scalar(1i32, ReduceOp::Sum).ok() == Some(members)
            }
            _ => false,
        };
    }
    common::check(&world, ok, "create_group among the members of the group");

np=2.. runs it at every process count in MPI_NP_LIST from 2 up, and each step ends in common::check, which gives every rank the same verdict (chapter 13).

The tag check comes first on purpose. Step 2 has only the members call. If the C function were collective over the parent, as MPI_Comm_create is, the members would wait in step 2 for ranks that had gone on to the check, and the job would hang until the runner’s timeout. Such a function would also ignore the tag, so step 1 catches it first, and the test fails on every rank at once with the name of the step. A test of a collective call orders its steps so that a likely mistake fails before a step where it would hang.

The other four steps have every rank call, pass the empty group, create a communicator from a communicator made by split, and pass a group with a member outside the communicator. Two of them were added by review.

The fix came from the review’s probes of a group that is not a subset. A member’s call with such a group ended its process with a segmentation fault inside MPI_Comm_create_group, on all four stacks probed. The probes also found a crash with a valid group: on MPICH 4.2, a group of two or more members on a communicator whose group nothing had asked for, such as one just made by split, made the call read a null pointer. The commit messages record this, and follow a practice the history keeps. A message names the section of the standard, says what was measured, on which library and how, and, for a fix, lists the mutants under “Red”: each a part of the change undone or altered, with the test it turned red and how. Removing the two check lines from the C function, for one, made the test end with exit status 139 at step 5. “Green” lists the tests that passed, at which process counts. When the call moves data

create_group moves no data. A call with a buffer has more to get right on each side, and exscan shows most of it. The C function:

int ferrompi_exscan(
    const void* sendbuf,
    void* recvbuf,
    int64_t count,
    int32_t datatype_tag,
    int32_t op,
    int32_t comm_handle
) {
    MPI_Comm comm = get_comm(comm_handle);
    MPI_Datatype dt = get_datatype(datatype_tag);
    if (dt == MPI_DATATYPE_NULL) return MPI_ERR_TYPE;
    MPI_Op mpi_op = get_op(op);
    if (count > INT_MAX) {
        if (is_user_op(op)) return MPI_ERR_COUNT;
#if MPI_VERSION >= 4
        return MPI_Exscan_c(sendbuf, recvbuf, (MPI_Count)count, dt, mpi_op, comm);
#else
        return MPI_ERR_COUNT;
#endif
    }
    return MPI_Exscan(sendbuf, recvbuf, (int)count, dt, mpi_op, comm);
}

The count crosses as int64_t. Up to INT_MAX it goes to the classic call; above, to the _c call where the library has MPI 4.0, and is refused with MPI_ERR_COUNT where it has not (chapter 7). A reduction above INT_MAX with a user-defined operation is refused on every version, since the operation takes an int length (chapter 12). An element-type tag that names no datatype returns MPI_ERR_TYPE.

The method checks the buffers before the call:

    pub fn exscan<'a, T: MpiDatatype>(
        &self,
        send: &[T],
        recv: &mut [T],
        op: impl Into<CollectiveOp<'a, T>>,
    ) -> Result<()> {
        let op = op.into().code(tag_of::<T>())?;
        check_same_len("recv", send.len(), recv.len())?;
        let (sp, n, dt) = buf(send);
        let (rp, _, _) = buf_mut(recv);
        // SAFETY: send.len() == recv.len() is verified above; the two slices cannot alias
        // (&[T] vs &mut [T]). MPI leaves recv undefined on rank 0, documented above.
        let ret = unsafe { ffi::ferrompi_exscan(sp, rp, n, dt, op, self.handle) };
        Error::check_with_op(ret, "exscan")
    }

MPI cannot check a buffer’s length, so every method that passes one checks it first, with the validators of src/comm/mod.rs and src/comm/v_collective.rs:

ValidatorChecksUsed by, for example
check_same_lentwo buffers that must have the same lengthallreduce, scan, exscan
check_rank_slotsa buffer with one block for every rankthe root’s buffer of gather and scatter
rank_blocka buffer that splits evenly across the ranks, and the block sizealltoall
check_v_argsthe counts and displacements of a v-collective against the buffergatherv, alltoallv

The operation is checked too: code refuses a predefined operation that MPI does not define on the element type, such as a bitwise one on f64. A nonblocking call adds a slot in the request table and a buffer that must outlive the request, which is what the scopes of chapter 11 are for.

A call that MPI 4.0 added compiles only where the library has it. The C function then has a stub for older libraries, which returns ferrompi’s code for an unsupported call, and Rust maps it to Error::NotSupported:

int ferrompi_comm_create_from_group(int32_t group_h,
                                    const char* stringtag,
                                    int32_t* out_h) {
#ifdef FERROMPI_HAVE_MPI4_COLLECTIVES
    /* ... */
#else
    (void)group_h; (void)stringtag; (void)out_h;
    return FERROMPI_ERR_NOT_SUPPORTED;  /* needs MPI 4.0, or Open MPI 5 */
#endif
}

A one-sided call belongs to the rma feature: its Rust side is compiled under #[cfg(feature = "rma")], and its test needs an [[example]] entry in Cargo.toml with required-features = ["rma"], or cargo builds it without the feature and fails.

What a reviewer checks

The architecture guide says that leaving out any of the five places is a scope violation. What a reviewer reads in each:

PlaceWhat is checked
csrc/ferrompi.hFixed-width types and an int result. The comment says over which processes the call is collective, what a process outside it gets, and which ferrompi codes it returns.
csrc/ferrompi.cHandles decoded through the tables, and one that names nothing refused. Every value MPI does not fix translated here. MPI_ERRORS_RETURN on a new communicator before Rust sees it. The large-count branch, or the reason there is none. A call from MPI 4.0 under the version test, with its stub. The group lock around a local group call only, never around a collective. No new compiler warning.
src/error.rsA new code defined with the same number as in the header, a comment on each side naming the other, an arm that maps it, and a unit test.
src/ffi.rsThe same types in the same order as the header. Inside the guarded block, unless the function is one of the kinds outside it.
The methodEvery buffer, rank and count that MPI cannot check, checked before the call. A SAFETY comment that says why the call is sound. The name given to check_with_op. -1 mapped to None. Documentation that says who calls, what is checked, and each error.
The testA directive. Steps ordered so that a likely mistake fails before a step where it would hang. Every step through common::check. Runs at each process count the directive allows, on MPICH and Open MPI in CI.
CHANGELOG.mdAn entry under [Unreleased] that says what a user can now do.

The commands in CONTRIBUTING.md run all of this as CI does, the MPI tests included; check-no-plan-leaks.sh among them keeps work-item identifiers out of the shipped files.

Exercises

  1. Add Communicator::compare for MPI_Comm_compare. Its four results, MPI_IDENT, MPI_CONGRUENT, MPI_SIMILAR and MPI_UNEQUAL, have values the standard does not fix. Where are they translated, and into what? Is the call collective? Write the test’s steps: the world against itself, against a duplicate, and against one half of a split.
  2. Add Mpi::wtick for MPI_Wtick. Does its declaration go in the guarded block or the one above it, and why is wtime where it is?
  3. Add Communicator::ssend for MPI_Ssend. Which parts of send can it copy, and what is its large-count call? Write a test step that shows it differs from send, and make sure the step cannot hang when the call is wrong.
  4. In the program, let rank 2 skip the first create_group call. Does the output change? Then have every rank call world.create(&pair) instead, let rank 2 skip it, and run the program under timeout 20. What happens to ranks 0 and 1?
  5. Remove the two lines that call check_group_in_comm from ferrompi_comm_create_group, and run test_comm_create_group at 4 processes under timeout 30. Which step ends it, and how? Compare what you see with the “Red” list of ac6f523, then put the lines back and run it again.

Summary

  • A new call touches five places in order: the header, the C function, the Rust declaration, the safe method and a test, plus a changelog entry. Leaving one out is a scope violation.
  • The standard’s section answers most questions before the code: the MPI version, who takes part, what comes back where, what object is created and what data moves. What a library does with a rule it need not check has to be measured.
  • The C function decodes handles, checks what MPI will not, translates the values MPI does not fix, and hands a new communicator to store_comm. A new ferrompi code is defined in the header and in src/error.rs, tied only by comments and a unit test.
  • Nothing checks the Rust declaration against the header; the reviewer does, by eye.
  • The method checks in Rust what MPI cannot, through the validators, documents who calls and each error, and maps the code with check_with_op.
  • The test orders its steps so that a likely mistake fails before it can hang. Review of create_group added a check, a code and two steps, and the commit messages record what was measured and which mutants turned the tests red.
