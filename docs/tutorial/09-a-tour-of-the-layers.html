Part II · Chapter 9

A tour of the layers

Every ferrompi call crosses the same layers on its way to MPI: the method you call, a guard, a C function and the MPI library. This chapter follows one allreduce down through all of them and back, in a debugger and in the source, then looks at what each layer refuses, what the layers cost, and where each one’s code lives.

By the end of the chapter you can name the layer of each frame in a backtrace, follow any call through ferrompi’s source, tell from an error which layer refused a call, and find the file to change for each part of the crate. The chapters after this one take the layers one at a time.

The excerpts of ferrompi’s source below name the file they come from. A comment // … or /* ... */ marks lines left out. CI checks that every excerpt still matches its file.

Six layers

A ferrompi program holds code from three places in one process: your Rust, ferrompi’s Rust and C, and the MPI library. ferrompi’s part is three layers thick, and the call that goes through them starts in your program and ends in the other processes of the job:

  • The public API is the methods of Mpi, Communicator, Win and the other types, in src/ outside ffi.rs and rt.rs. It checks what the types cannot express, and takes each argument apart into values C can take.
  • The guard is a wrapper that src/ffi.rs puts around each C function, with its checks in src/rt.rs. It refuses a call from the wrong thread, before init or after finalize.
  • The C layer is one file, csrc/ferrompi.c, compiled against the MPI library’s mpi.h (chapter 8). It turns ferrompi’s integers into MPI’s handles and calls the library.
  • The MPI library, MPICH or Open MPI or another, is loaded when the program starts, and does the communication.

The architecture guide’s layer diagram draws the same six layers and gives the rules for crossing each boundary. This chapter shows the layers at work.

One call, layer by layer

Besides init and finalize, this program makes one MPI call:

use ferrompi::{Mpi, ReduceOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Each process contributes four values, and every process gets the sums.
    let send = [f64::from(rank + 1); 4];
    let mut recv = [0.0f64; 4];
    world.allreduce(&send, &mut recv, ReduceOp::Sum)?;
    println!("rank {rank}: {recv:?}");
    Ok(())
}

With two processes it prints:

rank 0: [3.0, 3.0, 3.0, 3.0]
rank 1: [3.0, 3.0, 3.0, 3.0]

In a debugger

gdb can stop the program where it enters the MPI library and print the path the call took to get there. MPICH’s allreduce starts at PMPI_Allreduce; the section on the library, below, says why it has that name. The library is not loaded yet when gdb starts, so the breakpoint has to be allowed to wait for it. One process is enough, since an allreduce over one process is still a call to the library:

mpiexec -n 1 gdb -q -batch -ex 'set breakpoint pending on' -ex 'break PMPI_Allreduce' -ex run -ex bt --args target/debug/examples/one_call

Without its startup messages, gdb prints:

Read it from the bottom, one frame for each layer: your main, at the line of the call; the public API, Communicator::allreduce, whose arguments are still Rust values, f64 slices and ReduceOp::Sum; the guard, ferrompi::ffi::ferrompi_allreduce, where they have become two addresses and four integers; the C function of the same name; and the library.

Frame 3 prints no address. Frame 2 is not a call of its own: the guard is marked #[inline(always)], so the compiler copies its code into allreduce, and gdb shows it as a frame because the debug information records where inlined code came from.

The public API

Communicator::allreduce is in src/comm/blocking.rs, with the other blocking collectives:

    pub fn allreduce<'a, T: MpiDatatype>(
        &self,
        send: &[T],
        recv: &mut [T],
        op: impl Into<CollectiveOp<'a, T>>,
    ) -> Result<()> {
        let op = op.into().code(tag_of::<T>())?;
        check_same_len("recv", send.len(), recv.len())?;
        let (sp, n, dt) = buf(send);
        let (rp, _, _) = buf_mut(recv);
        // SAFETY: send.len() == recv.len() is verified above; the two slices cannot alias
        // (&[T] vs &mut [T]).
        let ret = unsafe { ffi::ferrompi_allreduce(sp, rp, n, dt, op, self.handle) };
        Error::check_with_op(ret, "allreduce")
    }

It does three things before it calls C. op.into().code(…) turns the operation into the integer C expects, and refuses one that does not apply to the element type, such as a bitwise OR of f64 values. check_same_len refuses buffers of different lengths, which MPI would not notice: it would read count elements from one and write count into the other. And buf and buf_mut, in src/datatype.rs, take each slice apart:

pub(crate) fn buf<T: MpiDatatype>(s: &[T]) -> (*const c_void, i64, i32) {
    (
        buf_ptr(s.as_ptr(), s.len(), false),
        s.len() as i64,
        tag_of::<T>() as i32,
    )
}

A slice becomes its address, its length as an i64, and the tag of its element type, an integer that MpiDatatype gives each type ferrompi can send: 1 for f64. buf_ptr passes the address on unchanged, except for an empty slice, whose placeholder address some libraries would read as MPI_IN_PLACE. Here is everything that crosses into C:

No Rust type crosses: no slice, enum, reference or Result, only addresses and integers of fixed width, which mean the same thing to both compilers. The count is 64 bits wide whatever the library uses; the C layer decides what to do with a count too large for an int.

The last two lines of allreduce are the call and its check. The call is unsafe because the compiler cannot check a C function’s contract, and the SAFETY comment above it says how the method upholds it. Error::check_with_op turns the integer the call returns into the Result your program sees, and names the call, "allreduce", in any error. The way back, below, follows it.

The guard

In src/ffi.rs, ffi::ferrompi_allreduce is declared exactly like the C function it calls:

    pub fn ferrompi_allreduce(
        sendbuf: *const c_void,
        recvbuf: *mut c_void,
        count: int64_t,
        datatype_tag: int32_t,
        op: int32_t,
        comm: int32_t,
    ) -> c_int;

The declaration sits in a guarded_extern! block. The macro puts each declaration in an inner module, raw, which is the real extern "C" block, and defines in ffi a Rust function of the same name and arguments, with this body:

            pub unsafe fn $name($($arg: $ty),*) -> c_int {
                let _call = match $enter() {
                    Ok(token) => token,
                    Err(code) => return code,
                };
                // …
                unsafe { raw::$name($($arg),*) }
            }

$name is the function’s name, and $enter is rt::enter for most functions. The lines left out add a check to debug builds only: at Serialized, that no two calls are in MPI at once. rt::enter is in src/rt.rs:

pub(crate) fn enter() -> std::result::Result<InFlight, c_int> {
    // …
    let state = STATE.load(Ordering::Relaxed);
    if state == ACTIVE_SINGLE || state == ACTIVE_FUNNELED {
        if ON_INIT_THREAD.with(Cell::get) {
            return Ok(InFlight(None));
        }
        return Err(FERROMPI_ERR_THREAD_LEVEL);
    }
    enter_other(state)
}

It reads the process’s state, one atomic byte. At Single and Funneled, the common levels, it checks a thread-local flag, set on the thread that initialized MPI, and refuses every other thread. Every other state goes to enter_other, kept out of line: at Serialized and Multiple it counts the call as in flight, so that finalize can wait for it, and before init or once finalize has begun it refuses the call. A refusal is one of ferrompi’s own error codes, which the wrapper returns as if the C function had returned it, without calling the C function at all. The MPI standard calls a call after MPI_Finalize, or from a thread the thread level does not allow, erroneous, and does not say what happens. The guard turns both into errors.

The token, _call, lives until the wrapper returns, so at Serialized and Multiple the count ends after the C function has returned. The functions that complete a request or close an epoch use rt::enter_completion instead, which also admits them while finalize waits for the calls in flight. The architecture guide’s lifecycle guard section describes the states and the few functions that skip the guard; chapter 11 explains why ferrompi needs them.

The C layer

The function the guard calls is in csrc/ferrompi.c:

int ferrompi_allreduce(
    const void* sendbuf,
    void* recvbuf,
    int64_t count,
    int32_t datatype_tag,
    int32_t op,
    int32_t comm_handle
) {
    MPI_Comm comm = get_comm(comm_handle);
    MPI_Datatype dt = get_datatype(datatype_tag);
    if (dt == MPI_DATATYPE_NULL) return MPI_ERR_TYPE;
    MPI_Op mpi_op = get_op(op);
    const void* sb = sendbuf ? sendbuf : MPI_IN_PLACE;
    if (count > INT_MAX) {
        if (is_user_op(op)) return MPI_ERR_COUNT;
#if MPI_VERSION >= 4
        return MPI_Allreduce_c(sb, recvbuf, (MPI_Count)count, dt, mpi_op, comm);
#else
        return MPI_ERR_COUNT;
#endif
    }
    return MPI_Allreduce(sb, recvbuf, (int)count, dt, mpi_op, comm);
}

Each integer becomes an MPI value. The datatype tag goes through a switch, get_datatype, to MPI_DOUBLE, and the operation code through another, get_op, to MPI_SUM. The communicator handle is an index into a table:

static MPI_Comm get_comm(int32_t handle) {
    if (handle < 0 || handle >= MAX_COMMS) {
        return MPI_COMM_NULL;
    }
    if (handle != 0 &&
            !atomic_load_explicit(&comm_used[handle], memory_order_acquire)) {
        return MPI_COMM_NULL;
    }
    return comm_table[handle];
}

comm_table holds every communicator ferrompi has made, and an index means the same thing whatever type the library gives MPI_Comm: an int in MPICH, a pointer in Open MPI (chapter 7). Init stores MPI_COMM_WORLD at index 0. A handle out of range, or a slot not in use, gives MPI_COMM_NULL, so a stale handle never reaches MPI as another communicator.

Two more lines are the C layer’s own decisions. A null send buffer becomes MPI_IN_PLACE, which lets the in-place variants of allreduce share this function. A count above INT_MAX goes to MPI_Allreduce_c, the large-count call MPI 4.0 added, as the send in chapter 7 did. It is an error with an older library, and with a user-defined operation, whose callback takes an int count. The last line calls the library; gdb’s frame 1 stopped there.

Into the library

The breakpoint was on PMPI_Allreduce, and gdb named frame 0 that way, for a call the C layer makes to MPI_Allreduce. The library defines both names, at one address:

nm -D $PREFIX/lib/libmpi.so.12 | grep -w -e MPI_Allreduce -e PMPI_Allreduce
00000000000eeb40 W MPI_Allreduce
00000000000eeb40 T PMPI_Allreduce

This is MPI’s profiling interface. The standard requires every MPI_ function to be callable also by its PMPI_ name, so that a tool can define its own MPI_Allreduce, do its work, and call the library’s through PMPI_Allreduce. T marks a function the library defines; W marks a weak name, which another definition can replace without a duplicate-symbol error when a tool is linked statically. A shared library replaces it more simply: the loader binds each name to the first library in its search order that defines it, and a library named in LD_PRELOAD comes first.

A tool of a dozen lines shows it. It prints each allreduce it sees, then passes it on:

#include <mpi.h>
#include <stdio.h>

/* Replaces MPI_Allreduce for every caller in the process. MPI's profiling
   interface guarantees the real one is also reachable as PMPI_Allreduce. */
int MPI_Allreduce(const void *sendbuf, void *recvbuf, int count,
                  MPI_Datatype datatype, MPI_Op op, MPI_Comm comm) {
    int rank, size;
    PMPI_Comm_rank(comm, &rank);
    PMPI_Type_size(datatype, &size);
    fprintf(stderr, "rank %d: MPI_Allreduce of %d elements of %d bytes\n",
            rank, count, size);
    return PMPI_Allreduce(sendbuf, recvbuf, count, datatype, op, comm);
}

Save it as count_allreduce.c, build it as a shared library with the MPI compiler wrapper, and run the program with it. env sets LD_PRELOAD in each process the launcher starts, not in mpiexec itself:

mpicc -shared -fPIC -o libcount_allreduce.so count_allreduce.c
mpiexec -n 2 env LD_PRELOAD=$PWD/libcount_allreduce.so target/debug/examples/one_call
rank 0: MPI_Allreduce of 4 elements of 8 bytes
rank 1: MPI_Allreduce of 4 elements of 8 bytes
rank 0: [3.0, 3.0, 3.0, 3.0]
rank 1: [3.0, 3.0, 3.0, 3.0]

The tool sees the call as the C layer made it: 4 elements of MPI_DOUBLE, 8 bytes each. Neither ferrompi nor the program changed, and that is how profilers and tracers that use the profiling interface, such as mpiP and Score-P, see a ferrompi program.

Under MPI_Allreduce, the library picks an algorithm for the message size and the number of processes, and moves the data through shared memory or the network, as chapters 3 and 7 described. ferrompi has no part in that.

The way back

Every MPI function returns an int: MPI_SUCCESS, which is 0, or an error code. It returns an error only if the error handler of the communicator lets it; the default handler, MPI_ERRORS_ARE_FATAL, ends the job instead. ferrompi replaces it in ferrompi_init_thread, right after the library starts:

    int ret = MPI_Init_thread(NULL, NULL, mpi_required, &mpi_provided);
    /* ... */
        comm_table[0] = MPI_COMM_WORLD;
        atomic_store_explicit(&comm_used[0], 1, memory_order_release);
        int eh_ret = install_errors_return(MPI_COMM_WORLD);
        if (eh_ret == MPI_SUCCESS) {
            eh_ret = install_errors_return(MPI_COMM_SELF);
        }

The lines left out check that MPI_Init_thread succeeded. If either handler cannot be installed, the lines after the excerpt end the job, since MPI cannot be initialized a second time. The function that installs the handler says where else it is used:

/* Install MPI_ERRORS_RETURN on the given communicator so that MPI
 * errors are returned as codes to ferrompi rather than aborting the
 * process via MPI_ERRORS_ARE_FATAL. Called from every site that
 * creates or adopts an MPI_Comm before handing it to Rust, and also on
 * MPI_COMM_SELF at init, since MPI 4 delivers errors that are not
 * associated with any object (e.g. group construction) through
 * MPI_COMM_SELF's handler. */
static int install_errors_return(MPI_Comm comm) {
    return MPI_Comm_set_errhandler(comm, MPI_ERRORS_RETURN);
}

So an error comes back as an integer, through the C function, the guard and allreduce, to check_with_op, in src/error.rs:

    pub(crate) fn check_with_op(code: i32, operation: &'static str) -> Result<()> {
        if code == 0 {
            Ok(())
        } else {
            Err(Error::from_code_with_op(code, operation))
        }
    }

0 becomes Ok(()). Any other code goes to from_code, which is marked #[cold], so the compiler keeps it out of the way of the success path, which stays one compare and one branch. from_code turns ferrompi’s own codes into their errors first:

        if code == FERROMPI_ERR_FINALIZED {
            return Error::Finalized;
        }
        if code == FERROMPI_ERR_THREAD_LEVEL {
            return Error::ThreadLevelViolation;
        }
        // …
        let ret = unsafe {
            ffi::ferrompi_error_info(
                code,
                &mut class,
                msg_buf.as_mut_ptr().cast::<std::ffi::c_char>(),
                &mut msg_len,
            )
        };

ferrompi’s codes are the ones the guard and the C layer return without calling MPI: the guard’s refusals, a full table in the C layer, a call the library is too old for. They are negative, in the −7000s, and MPI’s never are, so the two cannot collide. Any other code is MPI’s. ferrompi_error_info, in C, asks the library for its class and message, with MPI_Error_class and MPI_Error_string, and from_code puts both in Error::Mpi, to which check_with_op adds the name of the call. Chapter 7 explains classes, and why their values differ from one library to another.

Which layer refuses what

Each layer refuses the mistakes it can see, and the error a program gets says which layer did. This program makes five calls that end in different layers, then one more after drop(mpi). Rank 0 prints the layer that answered each, and every process prints the error itself to standard error:

use ferrompi::{Error, Mpi, ReduceOp};

/// Names the layer that refused a call, from the error the call returned.
fn refused_by(result: &ferrompi::Result<()>) -> String {
    match result {
        Ok(()) => "no layer refused it".to_string(),
        Err(Error::InvalidArgument { arg, .. } | Error::BufferSize { arg, .. }) => {
            format!("the public API, over `{arg}`")
        }
        Err(Error::ThreadLevelViolation | Error::Finalized) => "the guard".to_string(),
        Err(Error::Mpi {
            class, operation, ..
        }) => {
            format!("MPI, with {class}, in {}", operation.unwrap_or("?"))
        }
        Err(other) => format!("another error: {other}"),
    }
}

/// Prints the layer on rank 0, and the error itself on every rank, to
/// standard error.
fn report(rank: i32, call: &str, result: ferrompi::Result<()>) {
    if let Err(err) = &result {
        eprintln!("rank {rank}: {call}: {err}");
    }
    if rank == 0 {
        println!("{call}: {}", refused_by(&result));
    }
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();
    let send = [1.0f64, 2.0];
    let mut recv = [0.0f64; 2];
    let mut short = [0.0f64; 1];

    // Every process makes the same calls, in the same order.
    let calls = [
        (
            "a sum of f64s",
            world.allreduce(&send, &mut recv, ReduceOp::Sum),
        ),
        (
            "a bitwise OR of f64s",
            world.allreduce(&send, &mut recv, ReduceOp::BitwiseOr),
        ),
        (
            "a short receive buffer",
            world.allreduce(&send, &mut short, ReduceOp::Sum),
        ),
        (
            "a barrier on another thread",
            std::thread::scope(|s| s.spawn(|| world.barrier()).join().unwrap()),
        ),
        (
            "a send past the last rank",
            world.send(&send, world.size(), 0),
        ),
    ];
    for (call, result) in calls {
        report(rank, call, result);
    }

    drop(mpi);
    report(rank, "a barrier after drop(mpi)", world.barrier());
    Ok(())
}

With two processes it prints:

a sum of f64s: no layer refused it
a bitwise OR of f64s: the public API, over `op`
a short receive buffer: the public API, over `recv`
a barrier on another thread: the guard
a send past the last rank: MPI, with ERR_RANK, in send
a barrier after drop(mpi): the guard

and rank 0’s lines on standard error read:

rank 0: a bitwise OR of f64s: invalid argument `op`: bitwise and logical ops do not apply to floating-point types
rank 0: a short receive buffer: buffer `recv` has 1 elements, 2 required
rank 0: a barrier on another thread: MPI call not permitted on this thread at the provided thread level
rank 0: a send past the last rank: MPI error in send: Invalid rank, error stack:
internal_Send(63826): MPI_Send(buf=0x…, count=2, MPI_DOUBLE, 2, 0, MPI_COMM_WORLD) failed
internal_Send(63780): Invalid rank has value 2 but must be nonnegative and less than 2 (class=ERR_RANK, code=…)
rank 0: a barrier after drop(mpi): MPI has been finalized
  • The bitwise OR and the short buffer never left the public API. Error::InvalidArgument and Error::BufferSize name the argument at fault.
  • The barrier on another thread stopped at the guard. Mpi::init asks for Single, so only the thread that called it may call MPI (chapter 6).
  • The send to rank 2, in a job of two, reached MPICH, which checked the rank and returned an error. MPI_ERRORS_RETURN let it come back as Error::Mpi, with the class, MPICH’s own message and error stack, and the name of the call. The code differs from run to run and from process to process, because MPICH makes a new one for each error it reports.
  • A Communicator does not borrow the Mpi, so world outlives drop(mpi), but every call it makes after finalize stops at the guard.

What a program links

The C layer is compiled into a static library, libferrompi.a, of 154 functions, most of them one for each MPI call ferrompi wraps. A program contains only the ones it uses. These are the ferrompi_ functions one_call defines:

Ten are C: the call one_call makes, and the ones init, finalize and the error path need. The other, ferrompi_op_drop_closure, is Rust, in src/op.rs. The C layer calls it when it frees a user-defined operation, as finalize does with any left in its table, so calls cross the boundary upward too. Chapter 12 follows a user-defined operation, whose function MPI calls through C into Rust. No binding generator is involved in either direction: each side declares the other’s functions by hand.

The other 144 C functions were dropped by the linker. The cc crate compiles the C file with -ffunction-sections, which puts each function in a section of its own, and rustc links with --gc-sections, which drops every section nothing refers to. What the layers cost

Each layer adds work to a call: the guard’s load and compare, the checks in the public API, the switches and the table lookup in C. benches/ffi_overhead.rs measures it, by timing each call through ferrompi against the same MPI call made directly, on one process so that no network hides the difference. Its first case times a direct call against itself, to show the noise. On the laptop this chapter was written on, at Funneled, pinned to its four fast cores:

cargo bench --bench ffi_overhead --no-run
taskset -c 0-3 mpiexec -n 1 target/release/deps/ffi_overhead-<hash>

cargo prints the path of the benchmark, with its hash, and lscpu -e shows which of your cores are fast. Three runs gave these medians, in nanoseconds per call:

A blocking call costs a few nanoseconds more, the time of a few dozen instructions. A message between two processes takes far longer, as chapter 7’s ping-pong measured, so in a real job the layers vanish in the call’s own time. The nonblocking pair costs more because ferrompi does more for it: the C layer keeps each MPI_Request in a table and returns its index, each wait looks it up, fills a Status and frees the slot, and the scope keeps track of the requests so that none outlives its buffer. The benches README records the same benchmark measured with more care, on a desktop processor where every difference is smaller, and the budgets each release is checked against.

Where the state lives

Your program’s ferrompi values hold little: a Communicator is three integers, its handle and the process’s rank and size in it, which is why world.rank() calls nothing. What the handles refer to lives in a few statics:

StateFileHolds
STATEsrc/rt.rsthe lifecycle and the thread level: the byte the guard reads on every call
ON_INIT_THREADsrc/rt.rsa thread-local flag, set on the thread that initialized MPI
IN_FLIGHTsrc/rt.rsthe calls in MPI at Serialized and Multiple, which finalize waits for, counted in shards so threads do not contend

Each C table has a fixed size, set in the source:

// Maximum number of concurrent communicators (excluding COMM_WORLD)
#define MAX_COMMS 256

// Maximum number of concurrent requests
#define MAX_REQUESTS 16384
/* ... */
// Maximum number of concurrent MPI_Group objects
#define MAX_GROUPS 64

// Maximum number of concurrent custom (derived) MPI_Datatype objects
#define MAX_DATATYPES 64

// Maximum number of concurrent RMA windows
#define MAX_WINDOWS 256
/* ... */
// Maximum number of concurrent user-defined MPI_Op objects
#define MAX_OPS 16

A program that holds more at once gets Error::ResourceExhausted. The architecture guide’s handle tables section describes how slots are claimed and freed, and chapter 10 shows how threads share the tables.

Finding the code for a call

Summary

  • A ferrompi call crosses six layers: your program, the public API in src/, the guard in src/ffi.rs and src/rt.rs, the C layer in csrc/ferrompi.c, the MPI library, and the other processes. A backtrace shows a frame for each of the first five.
  • The public API checks what the types cannot, and takes Rust values apart: a slice into its address and length, the element type into a tag, the operation into a code, a communicator into a handle. Only addresses and fixed-width integers cross into C.
  • The guard is an inlined wrapper around each C function. It reads one atomic byte and, at Single and Funneled, a thread-local flag, and returns one of ferrompi’s error codes instead of calling C when the thread or the moment is wrong.
  • The C layer turns tags, codes and handles into MPI’s own values, through switches and tables, and makes the decisions that need mpi.h, such as MPI_IN_PLACE and the large-count calls.
  • Every MPI_ function is also a PMPI_ function. A library in LD_PRELOAD can take the MPI_ calls and pass them on, which is how profilers see a ferrompi program.
  • Errors come back as integers. ferrompi installs MPI_ERRORS_RETURN so that MPI returns them, and check_with_op turns them into Error, keeping ferrompi’s own negative codes apart from MPI’s.
  • Each layer refuses its own kind of mistake, and the error variant names the layer. A mistake made on one process only can still hang a collective.
  • A program links only the C functions it uses. The layers add a few nanoseconds to a blocking call, and more to a nonblocking one, for the request table and the scope.
