Part II · Chapter 13

Testing

An MPI library is hard to test with the usual tools: MPI starts once per process, a test of communication needs several processes, and a check can fail on one of them only. This chapter shows how ferrompi’s tests are split to fit: unit tests that never start MPI, one test that does, doctests that must fail to compile, and programs that run as jobs under a runner that decides what passed.

By the end of the chapter you can say why cargo test alone cannot test ferrompi, why the one unit test that starts MPI is ignored and must run alone, why a doctest’s error code is checked on a pinned nightly, how an MPI test gives every process the same verdict, how the runner turns a run’s exit status and output into PASS, SKIP or FAIL, and where a new test belongs.

The commands CI runs are listed in CONTRIBUTING.md, with the rules for writing an MPI test. The excerpts below name the file they come from. A comment // … marks lines left out. CI checks that every excerpt still matches its file.

What cargo test cannot do

cargo test builds a test binary and runs it as one process, with its tests on a pool of threads. Three facts about MPI do not fit that model:

  • MPI starts once per process. MPI_Init may be called once, and after MPI_Finalize MPI cannot start again in that process. The tests of one binary cannot each start and stop it.
  • A job needs a launcher. A binary that cargo starts is a singleton (chapter 1): a world of one process. A test of a send or a collective needs two or more. A runner (chapter 8) can start each test binary as a job, but then every test runs in every process, the ones that need a single process too.
  • A check can fail on one process only. Each process sees its own buffers and its own results. A test whose processes decide apart can pass on one and fail on another, and leave a process waiting in a collective for a partner that has exited.

The first fact, in one process:

//! One process, one MPI: what a test binary runs into.
use ferrompi::{CustomDatatype, Mpi};

fn main() {
    // Before init, a call that would reach MPI is refused without one.
    match CustomDatatype::contiguous::<f64>(4) {
        Ok(_) => println!("before init: a datatype"),
        Err(e) => println!("before init: {e}"),
    }

    let mpi = Mpi::init().expect("MPI init failed");
    println!("init: a world of {}", mpi.world().size());

    // While an Mpi is alive, a second one cannot be made.
    match Mpi::init() {
        Ok(_) => println!("second init: ok"),
        Err(e) => println!("second init: {e}"),
    }

    // Dropping the Mpi runs MPI_Finalize, and MPI cannot start again.
    drop(mpi);
    match Mpi::init() {
        Ok(_) => println!("init after the drop: ok"),
        Err(e) => println!("init after the drop: {e}"),
    }
}
before init: invalid state: MPI is not initialized
init: a world of 1
second init: MPI has already been initialized
init after the drop: MPI has been finalized or the Mpi handle dropped

Before Mpi::init, the lifecycle guard (chapter 11) refuses the constructor, and no MPI call is made. While an Mpi is alive, a second one cannot be made. Once the drop has run MPI_Finalize, Mpi::init refuses for the rest of the process.

Unit tests: MPI never started

Many of ferrompi’s checks run before MPI is called: a buffer’s length, an argument’s range, the lifecycle state. A unit test of such a check needs no MPI, and the crate’s unit tests are written so that none starts it. A test that needs an Mpi builds one without Mpi::init. Its fields are private to the crate, and a test module inside the crate can write them:

    /// Minimal stub `Mpi` handle for tests that never call `Mpi::init`
    /// because their early-return path fires before any MPI call.
    fn stub_mpi() -> Mpi {
        Mpi {
            thread_level: ThreadLevel::Single,
            world_rank: 3,
            world_size: 8,
            _marker: PhantomData,
        }
    }

    /// `world()` on a stub handle: any MPI call here would run before
    /// `MPI_Init_thread`.
    #[test]
    fn world_is_built_from_the_rank_and_size_read_at_init() {
        let world = stub_mpi().world();
        assert_eq!((world.rank(), world.size()), (3, 8));
    }

world() reads the rank and size that init stored and makes no MPI call, so a stub with rank 3 of 8 gives a world of rank 3 of 8. A call that would reach MPI is refused before it does. The test below relies on that: a tag that passes the length check goes on to the lifecycle guard, which refuses it because MPI was never started:

    /// The longest `stringtag` the linked library allows passes the length
    /// check, and one byte more is refused by it. MPI is never initialized
    /// here: a tag that passes goes on to the lifecycle guard, which refuses
    /// the call, so no MPI call is made either way.
    #[test]
    fn create_from_group_checks_the_length_of_the_tag() {
        let mpi = stub_mpi();
        let g = group::Group { handle: 0 };
        // …
        let result = mpi.create_from_group(&g, &"t".repeat(longest));
        assert!(
            matches!(
                result,
                Err(Error::InvalidState {
                    reason: "MPI is not initialized"
                })
            ),
            "a tag of {longest} bytes passes the length check"
        );
        // …
    }

Such a test depends on a fact about its process rather than about the code under test: MPI must never have been started in it. Several of the unit tests need that fact, and one test needs the opposite.

The one test that starts MPI

Some checks need a crate-private item and a running MPI at once, such as handing the C layer a group handle past the end of its table. They all go in one test:

    /// The one test that initializes MPI. Other tests of this binary need a
    /// process in which MPI was never initialized, so this one is ignored by
    /// default and runs alone, as a singleton: `cargo test --lib -- --ignored`.
    #[test]
    #[ignore = "initializes MPI; run alone with `cargo test --lib -- --ignored`"]
    fn checks_that_need_mpi() {
        use crate::{CustomDatatype, MpiDatatype, MpiErrorClass, StructField};

        let mpi = Mpi::init_thread(ThreadLevel::Multiple).expect("MPI init failed");
        let world = mpi.world();
        // The threads below duplicate the world communicator with no order
        // between their calls, which is valid only in a world of one process.
        assert_eq!(world.size(), 1, "this test needs a world of one process");
        // …
        crate::request::tests::stale_handle_is_rejected(&world);
        // …
    }

The test starts MPI at Multiple, runs every check that needs it, including helpers from other modules’ test code such as request::tests::stale_handle_is_rejected, and drops the Mpi at the end, which finalizes MPI for the rest of the process. That is why it is ignored: cargo test --lib skips it, and cargo test --lib -- --ignored runs it and nothing else, alone in its process. Started by cargo, it is a singleton, and it asserts a world of one. Its threads duplicate the world communicator with no order between their calls, which is valid only when no other process has to match them (chapter 6).

--include-ignored runs both kinds in one process, and then the result depends on timing. Three runs on the machine this chapter was written on, with the default pool of threads: two passed, and the third failed rt::tests::only_the_initializing_thread_is_admitted_while_initializing. On one thread the harness runs the tests in name order. The singleton then comes before three tests that need MPI never started, and they fail every time:

Each of the three finds MPI finalized where it expected MPI never started: the empty scope, for one, returns Err(Finalized). A suite that passes or fails by timing hides the failure most of the time, so the rule is to run the two commands apart and never pass --include-ignored.

Doctests that must not compile

rustdoc builds every Rust code block in the API documentation as a program of its own. Of the 308, 220 are marked no_run: they are compiled and never run, since running one would start MPI, and most need more than one process. Five run, and none of them starts MPI. 25 are ignored, all in the design records and guides that src/doc.rs pulls into the documentation.

The other 58 are marked compile_fail. Each is a program that must not compile, because the type system is what keeps it from being unsafe. They test the claims of chapters 11 and 12, such as a request that cannot leave its scope:

/// A request cannot leave the closure, because it borrows the scope:
///
/// ```compile_fail,E0521
/// # use ferrompi::Mpi;
/// # fn main() -> ferrompi::Result<()> {
/// # let mpi = Mpi::init()?;
/// # let world = mpi.world();
/// let mut buf = vec![0u8; 4];
/// let mut keep = None;
/// ferrompi::scope(|s| {
///     keep = Some(world.irecv(s, &mut buf, 1, 0)?);
///     Ok(())
/// })?;
/// # Ok(())
/// # }
/// ```

A compile_fail doctest passes on any compile error, a typo included, so 55 of the 58 also name the error they expect:

Only nightly rustdoc checks it, so CI runs the doctests once more on a nightly of fixed date, nightly-2026-09-30. A fixed date keeps the job from failing when a later nightly changes an error.

MPI tests: programs run as jobs

A test that needs processes to talk is a program: an examples/test_*.rs with a directive on one line, which the runner reads. Nineteen of the other examples carry one too, so every example that can run unattended is run. This one checks that a scope completes a receive whose request was forgotten, the case of chapter 11:

// mpi-test: np=2 valgrind

use std::time::Duration;

use ferrompi::Mpi;

mod common;

fn main() {
    let mpi = Mpi::init().expect("MPI init failed");
    let world = mpi.world();

    if world.rank() == 0 {
        let mut buf = vec![0u8; 64];
        let result = ferrompi::scope(|s| {
            let request = world.irecv(s, &mut buf, 1, 3)?;
            #[allow(
                clippy::forget_non_drop,
                reason = "a Request has drop glue only with the rma feature; the forget is the case under test"
            )]
            std::mem::forget(request);
            world.send(&[0u8], 1, 9)?;
            Ok(())
        });
        common::check(&world, result.is_ok(), "the scope returns Ok");
        common::check(
            &world,
            buf == [3; 64],
            "scope end completes a forgotten receive",
        );
        println!("test_scope_forget: PASS");
    } else {
        let mut go = [0u8; 1];
        world
            .recv(&mut go, 0, 9)
            .expect("recv of the go signal failed");
        std::thread::sleep(Duration::from_millis(100));
        world.send(&[3u8; 64], 0, 3).expect("send failed");
        common::check(&world, true, "the scope returns Ok");
        common::check(&world, true, "scope end completes a forgotten receive");
    }
}

The directive asks for a job of two processes, and for a run under valgrind in the valgrind mode, where a receive that outlived its buffer would show as an invalid write. Rank 1 calls common::check as many times as rank 0, in the same order, with nothing to check: the helper is a collective.

One verdict for every process

Every process decides whether its own checks held, and common::check makes that one decision:

/// Aggregates this rank's verdict across `world` via `allreduce(Min)`. If any
/// rank reports failure, rank 0 prints `FAIL: {name}` and every rank exits
/// with status 2. Status 1 is not a failure under `expect=unfinalized`, where
/// Open MPI turns a clean exit without `MPI_Finalize` into 1.
pub fn check(world: &Communicator, ok: bool, name: &str) {
    let global_ok = world
        .allreduce_scalar(i32::from(ok), ReduceOp::Min)
        .expect("check: allreduce failed");

    if global_ok == 0 {
        if world.rank() == 0 {
            eprintln!("FAIL: {name}");
        }
        std::process::exit(2);
    }
}

The Min of the processes’ verdicts is 1 only if every process passed, and every process gets it. They then pass or fail together: rank 0 prints one FAIL line, and every process exits with status 2. No process exits while another waits in MPI for it. Status 1 is avoided because Open MPI turns a clean exit without MPI_Finalize into status 1, and the runner accepts 1 from the tests that skip finalize on purpose.

A check can fail on one process only. Here the test reads a reduction’s result on every process, though only the root has it:

//! A check can fail on one rank only, so every rank must hear the verdict.
use ferrompi::{Communicator, Mpi, ReduceOp};

/// True on every rank when `ok` is true on every rank.
fn everywhere(world: &Communicator, ok: bool) -> bool {
    let all = world
        .allreduce_scalar(i32::from(ok), ReduceOp::Min)
        .expect("allreduce failed");
    all == 1
}

fn main() {
    let mpi = Mpi::init().expect("MPI init failed");
    let world = mpi.world();
    let rank = world.rank();

    let sum = world
        .reduce_scalar(rank + 1, ReduceOp::Sum, 0)
        .expect("reduce failed");

    // Wrong: the sum is defined at the root only.
    let ok = sum == 3;
    let all = everywhere(&world, ok);
    println!("rank {rank}: sum == 3: here {ok}, everywhere {all}");

    // Right: the root checks the sum, and the other ranks have nothing to check.
    let ok = rank != 0 || sum == 3;
    let all = everywhere(&world, ok);
    println!("rank {rank}: the root's sum == 3: here {ok}, everywhere {all}");
}
rank 0: sum == 3: here true, everywhere false
rank 0: the root's sum == 3: here true, everywhere true
rank 1: sum == 3: here false, everywhere false
rank 1: the root's sum == 3: here true, everywhere true

Had each process decided alone, rank 0 would have passed and printed nothing, and rank 1 would have exited with status 2. What a launcher does with one failed process varies: it may stop the others, or let them run, and it may lose that process’s exit status. Only a FAIL line in the output can be relied on.

The directive says how to run the program and what output to expect. Its keys, and how many of the 122 examples use each:

A file named test_*.rs without a directive, a key the runner does not know, or expect= without its literal stops the run before anything is built. Only two examples have no directive: large_count, which needs more than 4 GB of memory, and ulfm_pending, which needs a fault-tolerant MPI. CI runs them on their own: large_count in a job, and ulfm_pending in a step of the Open MPI 5 job.

The runner

tests/run_mpi_tests.sh runs every example that has a directive, in four stages:

The build takes each executable’s path from cargo’s JSON messages, so it works with any CARGO_TARGET_DIR. It refuses to go on when the library was built without debug assertions, because some examples check diagnostics that only debug builds have, such as the check that Serialized calls do not overlap (chapter 6):

  if ((RELEASE_MODE)); then
    if [[ "$(lib_opt_level "$json_file")" == "0" ]]; then
      die "ferrompi was built with opt-level 0 in release mode; the mode exists to test optimised code"
    fi
  elif [[ "$(lib_debug_assertions "$json_file")" == "false" ]]; then
    die "ferrompi was built without debug assertions; several examples check debug-only diagnostics"
  fi

Each run goes through timeout, with the output and the errors of every process in one file:

      local outfile="$TMPDIR_RUN/${name}.np${np}.out"
      local rc=0
      local -a exec_cmd=("$MPIEXEC" "${MPIEXEC_ARGS[@]}" -n "$np")
      if ((VALGRIND_MODE)); then
        exec_cmd+=(valgrind "${VALGRIND_ARGS[@]}" "--suppressions=$VALGRIND_SUPP")
      fi
      exec_cmd+=("$exe")
      timeout --kill-after=10 "$run_timeout" "${exec_cmd[@]}" >"$outfile" 2>&1 || rc=$?

      local outcome
      outcome=$(classify "$rc" "$outfile" "$skip_ok" "$expect" "$literal" "$IMPL_ID")

From a run to an outcome

classify takes the exit status, the output and the directive’s fields, and returns the first rule that applies:

# A run whose output has FAIL as a word fails in every mode, whatever the exit
# status. Examples report a failed check as `FAIL: <name>`, `rank N: FAIL: ...`
# or `rank N: FAIL Test N ...`, and exit nonzero, but mpiexec on some MPICH
# stacks (hydra 4.2.0 with libmpich 4.2.1) returns 0 for a job whose every rank
# exited nonzero, so the exit status alone cannot be trusted.
classify() {
  local exit_code="$1" outfile="$2" skip_ok="$3" expect="$4" literal="$5" impl="$6"

  if [[ "$exit_code" == "124" || "$exit_code" == "137" ]]; then
    echo "FAIL timeout"
    return 0
  fi

  if [[ "$exit_code" == "99" ]]; then
    echo "FAIL valgrind errors"
    return 0
  fi

  if grep -qwF -- "FAIL" "$outfile"; then
    echo "FAIL output contains a FAIL: line"
    return 0
  fi

  if [[ "$expect" != "unfinalized" ]] && grep -qF -- "$FINALIZE_SKIPPED_MARKER" "$outfile"; then
    echo "FAIL $FINALIZE_SKIPPED_MARKER without expect=unfinalized"
    return 0
  fi
  1. Exit status 124 or 137, from timeout: FAIL.
  2. Exit status 99, valgrind’s status for an error in the valgrind mode: FAIL.
  3. FAIL as a word anywhere in the output: FAIL, whatever the exit status.
  4. The warning that MPI_Finalize was skipped, from an example without expect=unfinalized: FAIL.
  5. With expect=abort: FAIL on exit status 0 or without the literal, PASS otherwise, unless the run exited 0 after a SKIP: line.
  6. An exit status other than 0, or other than 0 and 1 with expect=unfinalized: FAIL.
  7. A SKIP: line: SKIP if skip-ok names this library, FAIL otherwise.
  8. The literal missing from the output: FAIL.
  9. Otherwise: PASS.

The FAIL rule comes before the exit status because the status cannot be trusted. On the stack of CI’s MPICH jobs, Ubuntu’s Hydra 4.2.0 with the libmpich 4.2.1 that replaces Ubuntu’s, mpiexec returns 0 for a job whose every process exited with an error. The warning rule catches a test that leaves a request or a window behind by mistake: MPI_Finalize is skipped, the process exits 0 under MPICH, and without the rule the test would pass.

Skips

A test prints SKIP: reason from rank 0, through common::skip, when the library cannot run it. The skip counts only on a library the directive names. test_inplace, with skip-ok=mpich-4.2, skips its persistent scatter on MPICH 4.2 for a deadlock in that library. The same line from Open MPI would be a failure, so a skip cannot hide a regression on a library it was not written for. A test that needs a feature the build lacks is not run at all, and is counted as SKIP(feature). A run with the default features, two processes and MPICH 4.2.3, cut down:

An abort, and a race in the launcher

A test of abort passes when the job ends with an error and the literal is in its output. The literal is what tells a deliberate abort from a crash, and the launcher can lose it:

// mpi-test: np=2 expect=abort
// mpi-test-stderr: test_abort: calling abort
// …
fn main() -> Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    if world.rank() == 0 {
        eprintln!("test_abort: calling abort");
    }

    world.barrier()?;
    // Covers the launcher's stderr-forwarding race with MPI_Abort (Hydra can tear the job down before forwarding rank 0's already-written marker).
    std::thread::sleep(Duration::from_millis(100));

    if world.rank() == 0 {
        world.abort(3);
    }

With MPI_Abort called right after the line was written, 6 of 100 runs on MPICH 4.2.1 with Hydra had no output at all: the launcher stopped the job before it had passed on what rank 0 wrote. A barrier alone cut that to 1 in 200, and the barrier with a pause of 100 ms to 0 in 500. The test’s header records the measurement, which is the reason for the pause.

Testing the runner

The runner decides what passed, so it has tests of its own. Its decisions are shell functions of their arguments, and it calls main only when it is run, not when it is sourced:

if [[ "${BASH_SOURCE[0]}" == "$0" ]]; then
  main "$@"
fi

tests/runner_selftest.sh sources it and calls the functions on fixtures, with no MPI, cargo or network:

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
# shellcheck source=tests/run_mpi_tests.sh
source "$SCRIPT_DIR/run_mpi_tests.sh"

It checks 77 cases, among them every rule of classify:

Valgrind reports errors inside MPI libraries too, so the job reads suppressions from tests/valgrind/mpich.supp. The file’s header sets four rules for an entry: an exact error kind, a frame inside MPICH, UCX, libfabric, hwloc or libc, no ferrompi_*, rust_* or example frame, and no obj: wildcard. A suppression that matched ferrompi’s own code would hide the defects the job is there to find. Today the file holds the rules and no entry, so nothing is suppressed.

Ubuntu 24.04’s MPICH package, 4.2.0, is broken (Launchpad bug 2072338). The MPICH jobs keep its launcher and replace its library with MPICH 4.2.1, and UCX with a later version, from a dated snapshot of a later Ubuntu release, checking both packages against SHA-256 sums written into .github/scripts/mpich-hotfix.sh, a script with a fixture test of its own.

Exercises

  1. In the once program, call Mpi::init on a second thread while the first Mpi is alive, and then after the drop. Which error does each call return, and which state of the lifecycle explains it?
  2. Run cargo test --lib -- --include-ignored ten times. How many runs pass, and do the failures name the same tests each time? Explain the difference with --test-threads=1.
  3. Change the E0521 doctest in src/scope.rs to expect E0597, and run cargo test --doc on stable. Does it fail? Which command in CI would catch the change?
  4. In the verdict program, have rank 1 exit with status 2 when its own check fails, before the first call to everywhere. What does rank 0 do, and what does mpiexec print and return? Compare it with the program as written.
  5. Add an example test_mine.rs that prints SKIP: not here from rank 0, with // mpi-test: np=2. What does the runner report? Then add skip-ok= with the start of your library’s name.
  6. Remove the barrier and the pause from test_abort and run it 100 times under mpiexec -n 2. How many runs lose the literal?

Summary

  • MPI starts once per process, a job needs a launcher, and a check can fail on one process only. cargo test fits none of these, so the suite is split into layers.
  • Unit tests never start MPI. A stub Mpi built inside the crate reaches every check that runs before an MPI call, and the lifecycle guard refuses the rest without calling MPI.
  • The one test that starts MPI is ignored and runs alone with cargo test --lib -- --ignored. Run with the other tests in one process, it makes them pass or fail by timing.
  • 58 doctests must fail to compile, and 55 name their error. Stable rustdoc ignores the code, so CI runs them again on a dated nightly.
  • MPI tests are examples with a directive. common::check takes the Min of every process’s verdict, so every process fails together, rank 0 prints FAIL, and all exit with status 2.
  • The runner judges a run by its output before its exit status, since a launcher can lose the status. A FAIL word fails, a skipped finalize fails unless declared, and a skip counts only on the libraries the directive names.
  • CI adds a second and a third library, release with fat LTO, valgrind, the oldest supported Rust, the standard ABI’s stubs, large counts, fault tolerance and coverage.
