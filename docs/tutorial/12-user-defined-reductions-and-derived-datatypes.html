Part II · Chapter 12

User-defined reductions and derived datatypes

Chapter 4 used ferrompi’s datatypes and reductions. This chapter opens them up: how a Rust type becomes the datatype MPI is told about, how the compiler decides which operation may reduce which type, how a Rust closure becomes an MPI_Op that the MPI library calls, and how a derived datatype is checked against the slice it describes.

By the end of the chapter you can say how the datatype tag is sealed and why no code outside the crate can read it, name the operation errors the compiler catches and the one the run time catches, follow a call to a user-defined operation from your program into MPI and back into your closure, say who frees an operation and in what order, and name the two numbers a derived datatype must match before a _custom call reaches MPI.

The designs are ADR 0003 for the datatype traits and ADR 0005 for user-defined operations. The excerpts of ferrompi’s source below name the file they come from. A comment // … marks lines left out. CI checks that every excerpt still matches its file.

From a type to a datatype

Every typed call turns its slices into what the C layer takes: an address, a count and a datatype tag, which get_datatype maps to an MPI_Datatype (chapter 10). One function does it for a slice that MPI reads, and its twin buf_mut for one that MPI writes:

#[inline(always)]
pub(crate) fn buf<T: MpiDatatype>(s: &[T]) -> (*const c_void, i64, i32) {
    (
        buf_ptr(s.as_ptr(), s.len(), false),
        s.len() as i64,
        tag_of::<T>() as i32,
    )
}

The count is the slice’s length, which never exceeds isize::MAX, so the cast to i64 loses nothing. The tag comes from the element type, through a function that only the crate can call:

pub trait MpiDatatype: sealed::Sealed + Copy + Send + 'static {}

/// The tag the C layer dispatches on for `T`.
#[inline]
pub(crate) fn tag_of<T: MpiDatatype>() -> DatatypeTag {
    T::tag(sealed::Token)
}

MpiDatatype declares nothing of its own. What it means is in its supertraits: Copy, because MPI copies elements byte by byte; Send and 'static, because a buffer may move to another thread or be owned by a request; and sealed::Sealed, which carries the tag.

The seal

/// Internal module to seal [`MpiDatatype`] — prevents external implementations.
mod sealed {
    use super::DatatypeTag;

    /// Argument of [`Sealed::tag`]: it cannot be named outside this crate, so
    /// the tag cannot be read through a public bound.
    pub struct Token;

    pub trait Sealed {
        fn tag(_: Token) -> DatatypeTag;
    }
}
macro_rules! impl_mpi_datatype {
    ($ty:ty, $tag:expr) => {
        impl sealed::Sealed for $ty {
            #[inline]
            fn tag(_: sealed::Token) -> DatatypeTag {
                $tag
            }
        }
        impl MpiDatatype for $ty {}
    };
}

impl_mpi_datatype!(f32, DatatypeTag::F32);
impl_mpi_datatype!(f64, DatatypeTag::F64);
impl_mpi_datatype!(i32, DatatypeTag::I32);
impl_mpi_datatype!(i64, DatatypeTag::I64);
impl_mpi_datatype!(u8, DatatypeTag::U8);
impl_mpi_datatype!(u32, DatatypeTag::U32);
impl_mpi_datatype!(u64, DatatypeTag::U64);

The module sealed is private. Outside the crate its trait cannot be named, so no type there can implement Sealed, or therefore MpiDatatype. The tag’s function takes a Token, a public struct in that private module: a generic function outside the crate cannot make one, so it cannot call tag even through a bound. And DatatypeTag has no public path. Two compile_fail doctests in src/datatype.rs pin this: use ferrompi::DatatypeTag fails with E0432, and T::TAG in a function generic over T: MpiDatatype fails with E0599. Before 0.7.0 the tag was a public constant, T::TAG. ADR 0003’s amendments made its values internal, so that a release may renumber them, for instance to the handle values of the MPI 5 standard ABI.

The list is closed because the C layer’s switch on the tag is closed: a type outside it has no MPI_Datatype to map to. rsmpi, the other MPI binding for Rust, lets any type implement its Equivalence trait and supply a datatype of its own. ADR 0003 rejected that, and also a run-time enum of element kinds, which the compiler could not check against the slice. A struct of your own goes through a CustomDatatype instead, with the checks at the end of this chapter.

Each family of types has a seal of its own, so the families stay apart:

A pair type is not an MpiDatatype, so a broadcast of DoubleInts does not compile, and neither does a MAX_LOC reduction of f64s, as the next section shows.

An empty buffer

The address in buf is not always the slice’s own. An empty slice has no memory to point at, and Rust gives it a dangling address equal to the type’s alignment: address 1 for an empty &[u8]. In Open MPI and in the MPI 5 standard ABI, address 1 is MPI_IN_PLACE, so an empty send buffer of bytes would ask for an in-place operation. ferrompi hands MPI a private address instead:

static EMPTY: [u64; 2] = [0; 2];
// …
#[inline(always)]
pub(crate) fn buf_ptr<T>(ptr: *const T, len: usize, written: bool) -> *const c_void {
    if align_of::<T>() == 1 && (len == 0 || size_of::<T>() == 0) {
        std::ptr::from_ref(&EMPTY[usize::from(written)]).cast()
    } else {
        ptr.cast()
    }
}

Only a type of alignment 1 needs it. A larger alignment gives an even address, and MPI_IN_PLACE is an odd address in Open MPI, MPICH and the standard ABI. The pointer is never null either, which keeps null free for ferrompi’s own in-place marker: allreduce_inplace passes a null send buffer, and the C layer maps it to MPI_IN_PLACE. There are two addresses, one for a buffer MPI reads and one for a buffer it writes, because some MPI calls refuse a send and a receive buffer at the same address, even with a count of zero.

An operation for each type

A reducing call takes its operation as impl Into<CollectiveOp<'a, T>>, where T is the element type of its buffers:

pub struct CollectiveOp<'a, T> {
    op: CollectiveRepr<'a>,
    // T appears only as a `fn` return, so it adds no auto-trait or drop bound.
    _marker: PhantomData<fn() -> T>,
}

CollectiveOp holds no T. The marker PhantomData<fn() -> T> ties it to the type without making it Send or Sync only when T is, and without a drop check on T. What converts into it decides which operation compiles with which buffers:

impl<T: MpiDatatype> From<ReduceOp> for CollectiveOp<'_, T> {
    fn from(op: ReduceOp) -> Self {
        Self {
            op: CollectiveRepr::Builtin(Builtin::Reduce(op)),
            _marker: PhantomData,
        }
    }
}

impl<'a, T: MpiDatatype> From<&'a UserOp<T>> for CollectiveOp<'a, T> {
    fn from(op: &'a UserOp<T>) -> Self {
        Self {
            op: CollectiveRepr::User(&op.registration),
            _marker: PhantomData,
        }
    }
}

impl<T: MpiIndexedDatatype> CollectiveOp<'static, T> {
    /// `MPI_MAXLOC`: the maximum value and the index that came with it.
    pub const MAX_LOC: Self = Self {
        op: CollectiveRepr::Builtin(Builtin::PairMax),
        _marker: PhantomData,
    };

    /// `MPI_MINLOC`: the minimum value and the index that came with it.
    pub const MIN_LOC: Self = Self {
        op: CollectiveRepr::Builtin(Builtin::PairMin),
        _marker: PhantomData,
    };
}

A ReduceOp converts for any primitive type. A &UserOp<T> converts only for its own T, and the borrow’s lifetime becomes the 'a. MAX_LOC and MIN_LOC exist only for pair types. The one-sided calls take operations of their own, AccumulateOp and FetchOp, built the same way. Most of these programs are compile_fail doctests in src/op.rs:

The check left to run time

One rule is not in the types. ReduceOp is one enum for every primitive type, and MPI defines the bitwise and logical operations on integers only. Splitting the enum by type would make ReduceOp::Sum two different values, so the rule is checked when the call starts:

#[inline]
fn op_fault(op: Builtin, tag: DatatypeTag) -> Option<OpFault> {
    match tag {
        DatatypeTag::F32 | DatatypeTag::F64 => match op {
            Builtin::Reduce(ReduceOp::Sum | ReduceOp::Max | ReduceOp::Min | ReduceOp::Prod)
            | Builtin::Replace
            | Builtin::NoOp => None,
            Builtin::Reduce(
                ReduceOp::BitwiseOr
                | ReduceOp::BitwiseAnd
                | ReduceOp::BitwiseXor
                | ReduceOp::LogicalOr
                | ReduceOp::LogicalAnd
                | ReduceOp::LogicalXor,
            ) => Some(OpFault::FloatBitwise),
            Builtin::PairMax | Builtin::PairMin => Some(OpFault::LocNeedsPair),
        },
        // …
    }
}

The arms left out cover the other tags. Integers take every ReduceOp. Pair types take only MAX_LOC and MIN_LOC, which the types already ensure. Bytes take only the bitwise operations: the byte reductions of BytePermutable types take a plain ReduceOp, so for them this check is the only one. Each fault has its message:

#[cold]
#[inline(never)]
fn op_error(fault: OpFault) -> Error {
    Error::InvalidArgument {
        arg: "op",
        reason: match fault {
            OpFault::FloatBitwise => "bitwise and logical ops do not apply to floating-point types",
            OpFault::PairNeedsLoc => "only MAX_LOC and MIN_LOC apply to pair types",
            OpFault::LocNeedsPair => "MAX_LOC and MIN_LOC apply only to pair types",
            OpFault::ByteNeedsBitwise => "only the bitwise ops apply to byte reductions",
        },
    }
}

/// Rejects a predefined op that MPI does not define on the element kind `tag`. On
/// pair and byte tags it also rejects `MPI_REPLACE` and `MPI_NO_OP`, which
/// MPI-4.1 §12.3.4 allows but no window element type reaches.
#[inline]
pub(crate) fn check_op(op: Builtin, tag: DatatypeTag) -> Result<()> {
    match op_fault(op, tag) {
        None => Ok(()),
        Some(fault) => Err(op_error(fault)),
    }
}

CollectiveOp::code runs the check and turns the operation into the code the C layer’s get_op maps to an MPI_Op. A user-defined operation needs no check, since its type was matched at compile time:

impl<T> CollectiveOp<'_, T> {
    pub(crate) fn code(&self, tag: DatatypeTag) -> Result<i32> {
        match self.op {
            CollectiveRepr::Builtin(op) => check_op(op, tag).map(|()| op.code()),
            CollectiveRepr::User(registration) => Ok(registration.code()),
        }
    }

Every reduction calls it first, before it compares the lengths or calls MPI:

    pub fn allreduce<'a, T: MpiDatatype>(
        &self,
        send: &[T],
        recv: &mut [T],
        op: impl Into<CollectiveOp<'a, T>>,
    ) -> Result<()> {
        let op = op.into().code(tag_of::<T>())?;
        check_same_len("recv", send.len(), recv.len())?;
        let (sp, n, dt) = buf(send);
        let (rp, _, _) = buf_mut(recv);
        // SAFETY: send.len() == recv.len() is verified above; the two slices cannot alias
        // (&[T] vs &mut [T]).
        let ret = unsafe { ffi::ferrompi_allreduce(sp, rp, n, dt, op, self.handle) };
        Error::check_with_op(ret, "allreduce")
    }

The check reads nothing but the operation and T, which every process of a correct program passes alike. So every process refuses, and none is left waiting in MPI_Allreduce for a peer that returned an error. MPI itself calls a reduction with an operation its datatype does not support erroneous, and leaves what happens to the implementation. The program below runs one reduction that is fine, one that is refused, and one that is fine again:

use ferrompi::{Mpi, ReduceOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    let mut sum = [0.0f64];
    world.allreduce(&[rank as f64 + 0.5], &mut sum, ReduceOp::Sum)?;
    println!("rank {rank}: Sum on f64: {sum:?}");

    // MPI defines the bitwise operations on integers only. The check depends
    // only on the operation and the element type, so every process refuses.
    let mut bits = [0.0f64];
    match world.allreduce(&[1.0f64], &mut bits, ReduceOp::BitwiseOr) {
        Ok(()) => println!("rank {rank}: BitwiseOr on f64 ran"),
        Err(err) => println!("rank {rank}: BitwiseOr on f64: {err}"),
    }

    let mut flags = [0u64];
    world.allreduce(&[1u64 << rank], &mut flags, ReduceOp::BitwiseOr)?;
    println!("rank {rank}: BitwiseOr on u64: {:#b}", flags[0]);
    Ok(())
}

A closure as an MPI operation

MPI_Op_create takes a C function and a flag that says whether the operation commutes. When MPI combines two buffers, it calls the function as f(invec, inoutvec, &len, &datatype): the two buffers, a pointer to the count and a pointer to the datatype. Nothing in the call says which operation it belongs to, and there is no argument for data of the caller’s. A closure is code and the state it captured, so it cannot be passed as it is. ferrompi compiles sixteen C functions, ferrompi_user_op_trampoline_0 to _15, each of which passes its own slot number on (chapter 10), and keeps the closures in a table in Rust that the slot number indexes:

/// Type-erased closure stored in each op slot: it receives MPI's raw
/// `invec`/`inoutvec` pointers and element count.
type ByteClosure = Box<dyn Fn(*const c_void, *mut c_void, usize) + Send + Sync + 'static>;

/// Per-slot registry of thin pointers to boxed closures.
///
/// Each slot holds `Box::into_raw(Box::new(byte_closure))` — a thin
/// `*mut ByteClosure` — or null.  Protocol:
/// - `create_in_free_slot` publishes a slot with `Ordering::Release` before
///   calling `MPI_Op_create`.
/// - `rust_user_op_invoke` (the trampoline) loads a slot with
///   `Ordering::Acquire`.
/// - `ferrompi_op_drop_closure` swaps a slot to null only after
///   `MPI_Op_free` returns, so no trampoline call can observe a freed
///   closure.
static REGISTRY: [AtomicPtr<ByteClosure>; MAX_OPS] =
    [const { AtomicPtr::new(std::ptr::null_mut()) }; MAX_OPS];

An entry points to a boxed ByteClosure, which is itself a box: a box in a box. A pointer to a dyn Fn takes two words, one for the data and one for the table of its methods, and no atomic holds two words. A pointer to the outer box takes one. The comment states the protocol that the three functions below keep. This is how an operation is created:

    fn new_impl<F>(f: F, commute: i32) -> Result<Self>
    where
        F: Fn(&[T], &mut [T]) + Send + Sync + 'static,
    {
        // The guard admits the call before it takes a slot, and its token
        // covers the claim, the create and any rollback. `Mpi::init` resets
        // the op table before `MPI_Init_thread`, and the guard orders every
        // call it admits after `MPI_Init_thread`, so no claim meets that
        // reset. `Mpi::drop` frees the ops left in the table only when no
        // admitted call is in progress, so it never meets a slot claimed for
        // an op not yet created.
        let _call = rt::enter().map_err(|code| Error::from_code_with_op(code, "op_create"))?;
        #[cfg(debug_assertions)]
        let _flag = rt::begin_call().map_err(|code| Error::from_code_with_op(code, "op_create"))?;
        let slot = create_in_free_slot(typed_adapter::<T, F>(f), commute)?;
        Ok(UserOp {
            registration: Arc::new(OpRegistration { slot }),
            _marker: PhantomData,
        })
    }
fn create_in_free_slot(closure: ByteClosure, commute: i32) -> Result<i32> {
    let mut slot: i32 = -1;
    // SAFETY: slot is a local out-parameter written by ferrompi_op_alloc_slot
    // before this function reads it below (guarded by the `ret != 0` check).
    let ret = unsafe { ffi::ferrompi_op_alloc_slot(&mut slot) };
    if ret != 0 {
        return Err(Error::from_code_with_op(ret, "op_create"));
    }
    let idx = slot as usize;
    debug_assert!(idx < MAX_OPS, "slot out of range");

    // Publish the boxed closure to the registry.  A thin
    // `*mut ByteClosure` — no fat-pointer decomposition needed.  This
    // Release store, paired with the trampoline's Acquire load of the
    // same atomic, synchronizes-with that load directly (no external
    // happens-before edge required).
    let ptr: *mut ByteClosure = Box::into_raw(Box::new(closure));
    REGISTRY[idx].store(ptr, Ordering::Release);

    let mut handle: i32 = -1;
    // SAFETY: handle is a local out-parameter written by
    // ferrompi_op_create_user before this function reads it below; slot is
    // the value ferrompi_op_alloc_slot returned above; the caller holds the
    // in-flight token this unguarded MPI call needs.
    let ret = unsafe { ffi::ferrompi_op_create_user(slot, commute, &mut handle) };
    if ret != 0 {
        // …
        unsafe { ferrompi_op_drop_closure(slot) };
        // …
        unsafe { ffi::ferrompi_op_free_slot_only(slot) };
        return Err(Error::from_code_with_op(ret, "op_create"));
    }
    debug_assert_eq!(handle, slot);
    Ok(slot)
}
  1. ferrompi_op_alloc_slot claims a free slot of the C layer’s operation table, with the compare-and-swap of chapter 10.
  2. The closure is boxed and stored in REGISTRY[slot] with Release, before any MPI_Op exists that could make MPI call it.
  3. ferrompi_op_create_user calls MPI_Op_create with the slot’s trampoline, and keeps the MPI_Op in the slot.
  4. If that fails, the closure is dropped and the slot given back without MPI_Op_free, since no operation was made.

The guard taken in new_impl covers the four steps, so Mpi’s drop, which frees the operations left in the table, never meets one half made.

The closure in the registry is not yours. typed_adapter wraps yours in one that takes MPI’s untyped pointers:

/// Wraps a typed reduction closure in the type-erased form `REGISTRY` stores.
fn typed_adapter<T: MpiDatatype, F>(f: F) -> ByteClosure
where
    F: Fn(&[T], &mut [T]) + Send + Sync + 'static,
{
    Box::new(
        move |invec: *const c_void, inoutvec: *mut c_void, len: usize| {
            if len == 0 {
                // MPI may pass null buffers for an empty reduction; an empty
                // slice needs no pointer.
                f(&[], &mut []);
                return;
            }
            // SAFETY: invec/inoutvec point to `len` elements of the datatype the
            // op was applied with, which every reduction passes as T's own
            // because CollectiveOp<'a, T> ties the op's T to the buffers' T;
            // MPI's buffers are aligned for that datatype; the two buffers
            // are distinct; T: MpiDatatype is Copy with a stable layout.
            let (invec, inoutvec) = unsafe {
                (
                    std::slice::from_raw_parts(invec.cast::<T>(), len),
                    std::slice::from_raw_parts_mut(inoutvec.cast::<T>(), len),
                )
            };
            f(invec, inoutvec);
        },
    )
}

The adapter is generic over T and your closure’s type, so each UserOp::new compiles one of its own, and the element type is erased only when it is boxed. The slices rest on two facts. MPI may pass null pointers when there are no elements, and a slice may not be made from a null pointer even with length zero, so that case gets empty slices. And the pointers point at Ts, because the only way to give a UserOp<T> to a reduction is as a CollectiveOp<'a, T>, whose T is the buffers’.

When MPI calls it

#[unsafe(no_mangle)]
pub unsafe extern "C" fn rust_user_op_invoke(
    slot: std::ffi::c_int,
    invec: *const c_void,
    inoutvec: *mut c_void,
    len: std::ffi::c_int,
) {
    let ptr = REGISTRY[slot as usize].load(Ordering::Acquire);
    if ptr.is_null() {
        // A null slot here is an invariant violation: the publish-before-
        // create / drop-after-free protocol on REGISTRY guarantees a live
        // closure for every slot MPI can still invoke.  Treat it the same as
        // the panic path below — abort rather than deref a null pointer.
        std::process::abort();
    }
    // SAFETY: ptr is non-null, published by `create_in_free_slot` with `Ordering::Release`
    // before `MPI_Op_create`, and this `Ordering::Acquire` load of the same
    // atomic synchronizes-with that store.  `ferrompi_op_drop_closure` nulls
    // the slot only after `MPI_Op_free` returns, so no drop can race with
    // this borrow.
    let closure: &ByteClosure = unsafe { &*ptr };

    // Wrap the closure call in catch_unwind (ADR-0005 Decision 6).
    // A panic across the FFI boundary is UB; abort on Err.
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        closure(invec, inoutvec, len as usize);
    }));
    if result.is_err() {
        // A panic inside a user-defined reduction closure is a fatal
        // programming error.  Abort immediately to prevent silent data
        // corruption in the collective result (ADR-0005 Decision 6).
        std::process::abort();
    }
}

The Acquire load pairs with the Release store in create_in_free_slot, so whichever thread MPI calls from sees the closure fully built. The protocol leaves no way for the entry to be null; if it were, the function aborts rather than follow it. The datatype MPI passed is not read: the trampoline discards it with (void)dt, and the adapter relies on the types instead. ADR 0005’s first amendment records that there is no comparison of the two.

A panic may not unwind into the MPI library, which is C and knows nothing of unwinding. The function catches it and aborts: a user function has no way to report a failure to MPI, and returning as if nothing had happened would hand every process a result with part of the reduction missing. Chapter 11 lists the other places where a panic aborts.

The count is an int: ferrompi makes its operations with the classic MPI_Op_create, whose function takes an int length. Given a larger count, MPICH narrows it into that int rather than split the reduction, so the C layer refuses a user-defined operation over more than INT_MAX elements, on every MPI version:

// A user op is a classic MPI_User_function with an int length; MPICH narrows a
// larger count into it without splitting the reduction, so a user op above
// INT_MAX elements is refused on every MPI version, never sent to a _c call.
static int is_user_op(int32_t op) { return op >= FERROMPI_OP_USER_BASE; }

MPI calls the function from inside any MPI call that makes progress on the reduction: the reduction itself, the wait or test of a nonblocking one, or another MPI call. Under ThreadLevel::Multiple that can be on any thread, and an implementation with a progress thread may use its own. The registry is a static that every thread reads, and an operation can outlive the function that made it, held by a persistent request. So the closure must be Send, Sync and 'static, and the compiler refuses a capture that is not (chapter 4 showed the rules from the caller’s side):

A registry in thread-local storage would need no atomics. ADR 0005 rejected it for this reason: MPI may call the function on a thread that never saw the entry.

Freeing an operation

pub struct UserOp<T: MpiDatatype> {
    pub(crate) registration: Arc<OpRegistration>,
    _marker: PhantomData<T>,
}

/// One live `MPI_Op` slot and its closure; freed when the last holder drops.
#[derive(Debug)]
pub(crate) struct OpRegistration {
    pub(crate) slot: i32,
}

/// Op codes at or above this name the user op in slot `code - USER_OP_CODE_BASE`;
/// smaller codes are the predefined ops `get_op` switches on. Mirrors
/// `FERROMPI_OP_USER_BASE` in csrc/ferrompi.h; keep in sync.
pub(crate) const USER_OP_CODE_BASE: i32 = 64;

impl OpRegistration {
    pub(crate) fn code(&self) -> i32 {
        USER_OP_CODE_BASE + self.slot
    }
}

A UserOp is its slot, shared through an Arc. A blocking or nonblocking reduction borrows it, and that borrow is the 'a of CollectiveOp<'a, T>. iallreduce takes a CollectiveOp<'s, T>, so a nonblocking reduction borrows the operation for the whole scope, and dropping the operation inside the scope is refused with E0505, cannot move out of op because it is borrowed. A persistent reduction outlives any borrow, so allreduce_init clones the Arc into the request:

    pub fn allreduce_init<'a, T: MpiDatatype>(
        &self,
        send: Vec<T>,
        mut recv: Vec<T>,
        op: impl Into<CollectiveOp<'a, T>>,
    ) -> Result<PersistentRequest<T>> {
        let op = op.into();
        let code = op.code(tag_of::<T>())?;
        check_same_len("recv", send.len(), recv.len())?;
        // …
        Error::check_with_op(ret, "allreduce_init")?;
        let mut request = PersistentRequest::new_pair(request_handle, send, recv, Vec::new());
        request.op = op.registration();
        Ok(request)
    }

The MPI_Op is freed when the last holder drops, the UserOp or the last request made with it:

impl Drop for OpRegistration {
    fn drop(&mut self) {
        let Some(_call) = rt::drop_guard("UserOp") else {
            return;
        };
        // Drop ordering (ADR-0005 Decision 3):
        //   1. ferrompi_op_free → MPI_Op_free (MPI will not invoke the
        //      trampoline after this returns, because no pending operation
        //      references the op: the last OpRegistration holder is gone).
        //   2. ferrompi_op_free → ferrompi_op_drop_closure (Rust callback,
        //      drops the Box).
        //   3. ferrompi_op_free → free_op_slot (reclaims the C-side slot).
        //
        // The slot is valid for the lifetime of this registration; it is freed
        // exactly once here.
        let ret = unsafe {
            // SAFETY: self.slot was allocated by create_in_free_slot and has
            // not been freed.  Drop is called exactly once.
            ffi::ferrompi_op_free(self.slot)
        };
        // Log but do not panic in Drop.
        if ret != 0 {
            eprintln!("ferrompi: freeing a user op: ferrompi_op_free returned error code {ret}");
        }
    }
}

ferrompi_op_free, quoted in chapter 10, runs the steps in that order. The closure is dropped only after MPI_Op_free has returned, and by then no pending operation uses the op, since its last holder is gone. If MPI_Op_free fails, both the closure and the slot stay: MPI may still hold the op, and a slot given back could be claimed for a new operation, whose closure the old op’s trampoline would then call. Operations still alive when Mpi drops are freed through the same function, by a sweep in ferrompi_finalize:

    // Free every live user op: frees the MPI op and drops the Rust closure
    // through the same path as OpRegistration's Drop; a failed MPI_Op_free keeps both.
    for (int i = 0; i < MAX_OPS; i++) {
        if (atomic_load_explicit(&op_used[i], memory_order_acquire)) {
            ferrompi_op_free(i);
        }
    }

When MPI_Finalize is skipped (chapter 11), the sweep does not run, and the closures stay until the process exits. The program below makes an operation, gives it to a persistent reduction, and drops it. The request keeps it alive, and holds one of the sixteen slots until it goes:

use ferrompi::{Mpi, UserOp};

fn sum(a: &[u64], b: &mut [u64]) {
    for (x, y) in a.iter().zip(b.iter_mut()) {
        *y += x;
    }
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    let op = UserOp::new(sum)?;
    let mut request = world.allreduce_init(vec![rank as u64 + 1], vec![0], &op)?;
    // The request shares the operation's registration, so this frees nothing:
    // MPI calls the closure again on every start.
    drop(op);
    for round in 1..=2 {
        request.start()?;
        request.wait()?;
        println!("rank {rank}: round {round}: {:?}", request.buffer()?);
    }

    // The request still holds one of the sixteen slots.
    let mut ops = Vec::new();
    let refused = loop {
        match UserOp::new(sum) {
            Ok(op) => ops.push(op),
            Err(err) => break err,
        }
    };
    println!(
        "rank {rank}: {} more operations, then: {refused}",
        ops.len()
    );

    // The last holder of the first operation goes, and its slot with it.
    drop(request);
    let again = UserOp::new(sum).is_ok();
    println!("rank {rank}: after the request was dropped, one more: {again}");
    Ok(())
}
rank 0: round 1: [3]
rank 0: round 2: [3]
rank 0: 15 more operations, then: ferrompi operation table is full
rank 0: after the request was dropped, one more: true
rank 1: round 1: [3]
rank 1: round 2: [3]
rank 1: 15 more operations, then: ferrompi operation table is full
rank 1: after the request was dropped, one more: true

Each round adds 1 and 2, the two contributions, by calling sum after the UserOp was gone. The seventeenth operation is refused with Error::ResourceExhausted before any MPI call, because the C layer finds no free slot (chapter 10).

ADR 0005 weighed other ways to keep a closure. Box::leak would make it 'static with no way to free it, so a program that made an operation in every iteration would grow without end. A single trampoline for every operation would have to find its closure through something the call does not carry: MPI defines attributes on communicators, windows and datatypes, but not on operations, and machine code generated for each operation is refused by systems that forbid memory both writable and executable. Sixteen functions compiled in advance cost nothing at run time, and set the limit of sixteen operations alive at once.

Derived datatypes inside

Chapter 4 built derived datatypes. A CustomDatatype is an index into the C layer’s datatype table, which has 64 slots, and three numbers asked of MPI when the type is committed:

#[derive(Debug)]
pub struct CustomDatatype {
    /// Index into the C-side `datatype_table`.
    pub(crate) handle: i32,
    /// `MPI_Type_get_extent` extent, in bytes, recorded at commit.
    extent: i64,
    /// `MPI_Type_get_true_extent` true lower bound, in bytes, recorded at commit.
    true_lb: i64,
    /// `MPI_Type_get_true_extent` true extent, in bytes, recorded at commit.
    true_extent: i64,
}

Each constructor calls a C function that builds the type, commits it, and stores it in a free slot. create_struct translates each field’s tag with the same get_datatype as every other call, so a field is always a primitive type:

int ferrompi_type_create_struct(int32_t count,
                                const int32_t* blocklengths,
                                const int64_t* displacements,
                                const int32_t* basetype_tags,
                                int32_t* newtype_handle) {
    /* Reject an empty field list before the stack arrays are filled. */
    if (count <= 0) return MPI_ERR_ARG;
    MPI_Aint stack_disp[32];
    MPI_Datatype stack_types[32];
    MPI_Aint* disp = stack_disp;
    MPI_Datatype* types = stack_types;
    int heap_alloc = 0;
    if (count > 32) {
        /* … */
    }
    for (int32_t i = 0; i < count; i++) {
        MPI_Datatype t = get_datatype(basetype_tags[i]);
        if (t == MPI_DATATYPE_NULL) {
            if (heap_alloc) { free(disp); free(types); }
            return MPI_ERR_TYPE;
        }
        disp[i] = (MPI_Aint) displacements[i];
        types[i] = t;
    }
    MPI_Datatype new_t;
    int ret = MPI_Type_create_struct((int)count, (int*)blocklengths, disp, types, &new_t);
    if (heap_alloc) { free(disp); free(types); }
    if (ret != MPI_SUCCESS) return ret;
    ret = MPI_Type_commit(&new_t);
    if (ret != MPI_SUCCESS) {
        MPI_Type_free(&new_t);
        return ret;
    }
    *newtype_handle = alloc_datatype(new_t);
    if (*newtype_handle < 0) {
        MPI_Type_free(&new_t);
        return FERROMPI_ERR_DATATYPES_FULL;
    }
    return MPI_SUCCESS;
}

Up to 32 fields go in arrays on the stack, more in arrays it allocates. If the table is full, the committed type is freed, and the call returns FERROMPI_ERR_DATATYPES_FULL, which Rust reports as Error::ResourceExhausted. Then from_committed asks MPI for the bounds:

    fn from_committed(handle: i32) -> Result<Self> {
        let mut dt = CustomDatatype {
            handle,
            extent: 0,
            true_lb: 0,
            true_extent: 0,
        };
        // SAFETY: handle was just committed by the caller; extent/true_lb/true_extent
        // are exclusive stack locations valid for the duration of this call.
        let ret = unsafe {
            ffi::ferrompi_type_get_extents(
                handle,
                &mut dt.extent,
                &mut dt.true_lb,
                &mut dt.true_extent,
            )
        };
        Error::check_with_op(ret, "type_get_extents")?;
        Ok(dt)
    }
int ferrompi_type_get_extents(int32_t type_handle, int64_t* extent,
                              int64_t* true_lb, int64_t* true_extent) {
    MPI_Datatype dt = get_datatype_committed(type_handle);
    if (dt == MPI_DATATYPE_NULL) return MPI_ERR_TYPE;
    MPI_Aint lb, ext;
    int ret = MPI_Type_get_extent(dt, &lb, &ext);
    if (ret != MPI_SUCCESS) return ret;
    MPI_Aint tlb, text;
    ret = MPI_Type_get_true_extent(dt, &tlb, &text);
    if (ret != MPI_SUCCESS) return ret;
    *extent = (int64_t)ext;
    *true_lb = (int64_t)tlb;
    *true_extent = (int64_t)text;
    return MPI_SUCCESS;
}

The two pairs of numbers answer different questions. The extent is the stride: element i of a count of the datatype starts i extents after the buffer’s address. It runs from the type’s lower bound to its upper bound, which MPI derives from the fields and rounds up for alignment, and which resized sets by hand. The true lower bound and the true extent say where the data is, from the first byte that a field covers to the last.

The layout check

A _custom call passes buf.len() as the count, so MPI walks buf.len() elements of the datatype from the slice’s address. They are the slice’s elements only if the extent equals size_of::<T>(), and MPI stays inside the slice only if each element’s data lies within one T. Before every _custom call, ferrompi checks both:

    pub(crate) fn check_layout<T>(&self) -> Result<()> {
        let size = std::mem::size_of::<T>() as i64;
        if self.extent != size {
            return Err(Error::InvalidArgument {
                arg: "datatype",
                reason: "extent differs from the element size",
            });
        }
        match self.true_lb.checked_add(self.true_extent) {
            Some(end) if self.true_lb >= 0 && end <= size => Ok(()),
            _ => Err(Error::InvalidArgument {
                arg: "datatype",
                reason: "data lies outside one element",
            }),
        }
    }
    pub fn recv_custom<T: PlainData>(
        &self,
        buf: &mut [T],
        datatype: &CustomDatatype,
        source: impl Into<Source>,
        tag: impl Into<Tag>,
    ) -> Result<Status> {
        let source = source.into().source_code("source")?;
        let tag = tag.into().tag_code("tag")?;
        datatype.check_layout::<T>()?;
        let mut status = ffi::FerrompiStatus::default();

        // SAFETY: buf.as_mut_ptr() is exclusively writable for buf.len() elements; datatype.handle
        // is an owned, committed CustomDatatype; the buffer outlives this blocking call; the
        // PlainData bound on T makes any bytes MPI writes a valid T, and check_layout above
        // guarantees each element's data lies within its T, so MPI touches only buf.
        let ret = unsafe {
            ffi::ferrompi_recv_custom(
                buf.as_mut_ptr().cast::<std::ffi::c_void>(),
                buf.len() as i64,
                datatype.handle,
                source,
                tag,
                self.handle,
                &mut status,
            )
        };
        Error::check_with_op(ret, "recv_custom")?;
        Ok(Status::from_ffi(status))
    }

The program below sends two f64s with each of the three:

use ferrompi::{CustomDatatype, Mpi, StructField};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Three datatypes, each meant to describe one f64.
    // An f64 and an i32: more than one f64.
    let pair = CustomDatatype::create_struct(&[
        StructField::new::<f64>(1, 0),
        StructField::new::<i32>(1, 8),
    ])?;
    // One f64 at byte 8, an offset taken from another struct. Its extent is
    // 8 bytes, the size of an f64, but its data starts where the element ends.
    let shifted = CustomDatatype::create_struct(&[StructField::new::<f64>(1, 8)])?;
    let plain = CustomDatatype::contiguous::<f64>(1)?;

    for (name, datatype) in [("pair", &pair), ("shifted", &shifted), ("plain", &plain)] {
        // Both ends check the datatype against f64 before calling MPI.
        let result = if rank == 0 {
            world.send_custom(&[1.5f64, 2.5], datatype, 1, 0)
        } else {
            let mut back = [0.0f64; 2];
            world
                .recv_custom(&mut back, datatype, 0, 0)
                .map(|_| println!("rank 1: {name}: received {back:?}"))
        };
        if let Err(err) = result {
            println!("rank {rank}: {name}: {err}");
        }
    }
    Ok(())
}

rank 0: shifted: invalid argument `datatype`: data lies outside one element

Both ends used the same datatype each time, so both refused the first two before calling MPI, and no send was left without its receive. Two ends that use different datatypes with the same type signature are correct MPI, and if only one end refuses, the other may block, as with any error on one side of a message.

A struct of your own

The layout check covers where MPI writes. What it writes is the other half: a receive puts whatever bytes arrive into each T. So recv_custom requires T: PlainData, an unsafe trait whose implementor promises that any bit pattern is a valid value (chapter 11). It is implemented for the primitive types and for arrays of them. For a struct of your own, you write the one line:

use std::mem::{offset_of, size_of};

use ferrompi::{CustomDatatype, Mpi, PlainData, StructField};

#[repr(C)]
#[derive(Clone, Copy, Debug)]
struct Sample {
    value: f64,
    count: u32,
}

// SAFETY: Sample is #[repr(C)] of an f64 and a u32. Every bit pattern of each
// is a valid value, and padding may hold any bytes.
unsafe impl PlainData for Sample {}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // The fields at Rust's offsets, and the extent set to Rust's size, so the
    // datatype's elements line up with the slice's whatever padding MPI adds.
    let fields = CustomDatatype::create_struct(&[
        StructField::new::<f64>(1, offset_of!(Sample, value) as i64),
        StructField::new::<u32>(1, offset_of!(Sample, count) as i64),
    ])?;
    let sample = fields.resized(0, size_of::<Sample>() as i64)?;

    if rank == 0 {
        let out = [
            Sample {
                value: 1.5,
                count: 3,
            },
            Sample {
                value: -0.25,
                count: 7,
            },
        ];
        world.send_custom(&out, &sample, 1, 0)?;
    } else {
        let mut back = [Sample {
            value: 0.0,
            count: 0,
        }; 2];
        let status = world.recv_custom(&mut back, &sample, 0, 0)?;
        println!("rank 1: status.count = {:?}", status.count);
        println!("rank 1: {back:?}");
    }
    Ok(())
}
rank 1: status.count = Some(2)
rank 1: [Sample { value: 1.5, count: 3 }, Sample { value: -0.25, count: 7 }]

The fields are placed at the offsets Rust chose, from offset_of!, and resized sets the extent to Rust’s size, trailing padding included. MPICH also rounds this struct’s extent up to 16 bytes, by its own alignment rules, which need not be Rust’s; with resized the check passes on any implementation. A bool, char, enum, reference or Box field would break the promise: a byte that arrives as 2 is not a bool.

A CustomDatatype has no Clone, since two values would free one slot twice. Its drop frees the type through the lifecycle guard, and the C function clears the slot even when MPI_Type_free fails:

int ferrompi_type_free(int32_t type_handle) {
    if (type_handle < 0 || type_handle >= MAX_DATATYPES) return MPI_ERR_ARG;
    if (!atomic_load_explicit(&datatype_used[type_handle],
                              memory_order_acquire)) return MPI_SUCCESS;  /* already freed */
    int ret = MPI_Type_free(&datatype_table[type_handle]);
    free_datatype_slot(type_handle);  /* clears slot regardless of MPI_Type_free outcome */
    return ret;
}

An operation’s free does the opposite, and the difference is the callback. MPI never calls into Rust through a datatype, so a datatype slot given back too early cannot lead MPI to Rust state that is gone. An operation’s slot can.

Summary

  • A typed slice reaches the C layer as an address, a count and a tag. The tag comes from a sealed trait whose method takes a private token, so no code outside the crate can implement the trait or read the tag.
  • An empty buffer of a type with alignment 1 gets a private address, since its own, address 1, is MPI_IN_PLACE in Open MPI and the standard ABI.
  • CollectiveOp<'a, T> ties an operation to the element type: MAX_LOC on a primitive type, a user-defined operation of another type, or a predefined operation on a pair does not compile. A bitwise or logical operation on a float is refused at run time, on every process, before MPI is called.
  • A closure becomes an MPI_Op through one of sixteen C trampolines and a static registry in Rust, and the slot number is all the trampoline passes on. The closure is stored with Release before MPI_Op_create, and loaded with Acquire when MPI calls it.
  • The call runs your closure inside catch_unwind and aborts on a panic. It ignores MPI’s datatype argument and relies on the types. The closure is Send, Sync and 'static because MPI may call it on any thread, after the function that made it has returned.
  • An operation is freed when its last holder drops, the UserOp or a persistent request made with it: MPI_Op_free first, then the closure, then the slot. A failed MPI_Op_free keeps both the closure and the slot.
  • A _custom call checks that the datatype’s extent equals size_of::<T>() and that its data lies within one T, and requires T: PlainData, so MPI writes only inside the slice, and only bytes that make valid values.
