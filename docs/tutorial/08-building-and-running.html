Part II · Chapter 8

Building and running

Part I ran every program with two commands, cargo build and mpiexec. This chapter opens both: what cargo does with ferrompi before your code compiles, how the program finds the MPI library when it starts, how a launcher starts it on a laptop and on a cluster, and what to do when one of its processes panics or hangs.

By the end of the chapter you can add ferrompi to a project, read what its build script found, choose the MPI library a build uses, tell which library a program loads, launch a job through Cargo or Slurm, and get a backtrace from every process of a job that crashed or hung. Part II starts here because every later chapter builds and runs ferrompi; the next one takes its layers apart.

Adding ferrompi to a project

ferrompi is an ordinary crate on crates.io. A program that uses it names it in Cargo.toml:

[dependencies]
ferrompi = "0.7"

Two features add optional parts of the API. Neither needs another system library:

FeatureAdds
rmawindows and one-sided communication, including shared-memory windows (chapter 5)
slurmthe slurm module, which reads a Slurm job’s variables, and TopologyInfo::slurm
numadeprecated: 0.6’s name for slurm and rma together, removed in 0.8.0
 
[dependencies]
ferrompi = { version = "0.7", features = ["rma", "slurm"] }

The machine that builds the program needs an MPI library with its headers, as Before you start describes, and the machines that run it need the same library. ferrompi’s manifest also says links = "ferrompi". Cargo allows one package per links name in a build, so a program contains one copy of ferrompi’s C layer: if two of its dependencies need versions of ferrompi that cannot be unified, such as 0.6 and 0.7, Cargo stops at dependency resolution instead of linking both.

Build, then start the built program under a launcher, as in chapter 1. The rest of this chapter is about what each of those two steps does.

What cargo build does

ferrompi is a Rust crate with a C file inside. Before it compiles any of ferrompi’s Rust, cargo runs its build script, build.rs, which does three things: it finds an MPI installation, compiles the C layer against that installation’s mpi.h, and tells rustc which library to link. The figure follows a build against MPICH, found through its compiler wrapper.

The wrapper’s flags

An MPI compiler wrapper such as mpicc is a C compiler with the library’s flags added. Given -show (MPICH) or --showme (Open MPI), it prints the command it would run instead of running it. Here and below, $PREFIX is the directory MPICH 4.2.3 is installed in:

mpicc -show
gcc -I$PREFIX/include -L$PREFIX/lib -Wl,-rpath -Wl,$PREFIX/lib -Wl,--enable-new-dtags -lmpi

build.rs keeps the -I, -L, -l and -D tokens and ignores the rest, the compiler included. The cc crate compiles csrc/ferrompi.c with the system’s C compiler, cc, or the one the CC variable names, and adds the include directories and defines itself. The -Wl,-rpath tokens are dropped too: they make a C program built with mpicc record where libmpi is, and a ferrompi program records no such directory. Finding the library at run time covers what that means.

Some pkg-config files also list the MPI library’s own dependencies, such as hwloc, pmix or ucx, among the libraries to link. build.rs leaves them out: libmpi loads its dependencies itself, and naming them again fails the link where they are not on the default library path.

What the build script reports

A build script talks to cargo through lines on its standard output, and leaves notes for people on standard error. cargo build -vv shows both, each line prefixed with the package’s name. Among the cc crate’s own lines, the build above printed:

[ferrompi 0.7.0] cargo:rerun-if-changed=csrc/ferrompi.c
[ferrompi 0.7.0] cargo:rerun-if-changed=csrc/ferrompi.h
[ferrompi 0.7.0] cargo:rerun-if-env-changed=MPI_PKG_CONFIG
[ferrompi 0.7.0] cargo:rerun-if-env-changed=MPICC
[ferrompi 0.7.0] cargo:rerun-if-env-changed=CRAY_MPICH_DIR
[ferrompi 0.7.0] cargo:rerun-if-env-changed=PATH
[ferrompi 0.7.0] Found MPI via MPICC=$PREFIX/bin/mpicc
[ferrompi 0.7.0] cargo:rustc-link-lib=static=ferrompi
[ferrompi 0.7.0] cargo:rustc-link-search=native=…/target/debug/build/ferrompi-…/out
[ferrompi 0.7.0] cargo:rustc-link-search=native=$PREFIX/lib
[ferrompi 0.7.0] cargo:rustc-link-lib=mpi
  • The rerun-if lines say when cargo must run the script again; the next section comes back to them.
  • Found MPI via names the probe that found the library. Read it first when a build picks up the wrong one.
  • link-lib=static=ferrompi is the C layer, compiled into libferrompi.a in the script’s out directory.
  • The last two lines are the wrapper’s -L and -l.

Cargo prints these lines only when it runs the script. Once ferrompi is built, the same lines are in the files cargo kept, one directory per way ferrompi was built; the newest is the last build’s:

cat "$(ls -t target/debug/build/ferrompi-*/stderr | head -1)"
cat "$(ls -t target/debug/build/ferrompi-*/output | head -1)"

What the program records

The linker joins three things into the program: your code with ferrompi’s Rust, libferrompi.a, and libmpi. readelf -d shows what the program says about the libraries it needs:

readelf -d target/debug/examples/hello_world | grep -E 'NEEDED|RPATH|RUNPATH'
 0x0000000000000001 (NEEDED)             Shared library: [libmpi.so.12]
 0x0000000000000001 (NEEDED)             Shared library: [libgcc_s.so.1]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
 0x0000000000000001 (NEEDED)             Shared library: [ld-linux-x86-64.so.2]

libferrompi.a is not in the list: a static library is copied into the program. libmpi is a shared library, loaded when the program starts, and the program asks for it as libmpi.so.12, not the libmpi.so that -lmpi named. A shared library has three names:

ls -l $PREFIX/lib/libmpi.so*
libmpi.so -> libmpi.so.12.4.3
libmpi.so.12 -> libmpi.so.12.4.3
libmpi.so.12.4.3
NameWhat uses it
libmpi.sothe linker, given -lmpi. Distributions ship it in the development package, next to mpi.h.
libmpi.so.12the loader. It is the library’s soname, written into the library when it was built; the linker copies it into the program. It changes only when the ABI does (chapter 7).
libmpi.so.12.4.3nothing by this name: it is the file itself, this MPICH release’s build of that ABI.

Choosing the MPI library

Chapter 7 gave the order in which build.rs looks for MPI. On a machine with one MPI library, that order finds it. On a machine with several, as a cluster usually has, choose one with a variable:

VariableNamesFor example
MPI_PKG_CONFIGa pkg-config packageMPI_PKG_CONFIG=ompi
MPICCa compiler wrapper, asked with -show, then --showmeMPICC=/usr/bin/mpicc.mpich
CRAY_MPICH_DIRa Cray MPICH installationset by the cray-mpich module

The first of them that is set wins, in that order. If its probe fails, the build stops; it does not go on to look for another library, which could be the wrong one:

MPICC=/opt/nowhere/bin/mpicc cargo build --example hello_world
error: failed to run custom build command for `ferrompi v0.7.0 (…)`
…
  --- stderr
  thread 'main' (…) panicked at build.rs:70:61:
  MPICC=/opt/nowhere/bin/mpicc: failed to run '/opt/nowhere/bin/mpicc': No such file or directory (os error 2)

On a Cray system, leave MPICC unset: Cray’s compiler wrapper, cc, answers neither -show nor --showme, and CRAY_MPICH_DIR already points at the library.

When cargo rebuilds ferrompi

The rerun-if lines tell cargo to run build.rs again, and so recompile the C layer, when csrc/ferrompi.c or csrc/ferrompi.h changes, or when one of the three variables or PATH does. Loading another MPI module changes PATH, so the next build is against the new module’s library, without a cargo clean. Two things follow:

  • Switching back and forth between two libraries rebuilds ferrompi, and your program, at every switch. Give each library its own target directory, such as CARGO_TARGET_DIR=target/openmpi, and each keeps its build.
  • Reinstalling a library in place, at the same path, changes none of them, so cargo does not notice. Run cargo clean -p ferrompi to build against the new files.

The compatibility guide’s Building section lists every probe, including the directories tried last.

Finding the library at run time

The program names libmpi.so.12 and no directory. When it starts, the dynamic loader searches for a file of that name: first in the directories of LD_LIBRARY_PATH, then in the cache that ldconfig builds from the system’s library directories, then in /lib and /usr/lib. It loads the first file it finds. ldd shows which one that is, without running the program:

ldd target/debug/examples/hello_world | grep mpi
	libmpi.so.12 => $PREFIX/lib/libmpi.so.12 (0x…)

When no directory has the file, the program does not start, as chapter 7 showed. The quieter failure is a directory with another library of the same name. The figure shows it on a machine with MPICH 4.2.3 under $PREFIX, which built the program, and Ubuntu 24.04’s MPICH 4.2.0 package in /usr/lib: the package that starts every process as a separate job, as Before you start warns.

env -u LD_LIBRARY_PATH mpiexec -n 2 target/debug/examples/hello_world
Hello from rank 0 of 1 on node01 (MPI 4.1)

All processes reported in. Test passed!
Hello from rank 0 of 1 on node01 (MPI 4.1)

All processes reported in. Test passed!

The launcher was MPICH 4.2.3’s, the one the program was built for. The library was not. Chapter 7 gives a mismatched mpiexec as the cause of “rank 0 of 1”; this is the other cause, and ldd tells the two apart.

To load the right library, put its directory first:

  • set LD_LIBRARY_PATH, as an MPI module or the installation’s environment script does (DYLD_LIBRARY_PATH on macOS);
  • for a library meant for every user of the machine, register its directory with ldconfig;
  • or record the directory in your own program.

ferrompi records no directory because it is a library: it cannot know where the programs built on it will run, and a directory on the build machine is usually wrong on a cluster or in a container. A program you build for the machine you build it on can record one itself, by passing the linker an rpath:

RUSTFLAGS="-C link-arg=-Wl,-rpath,$PREFIX/lib" cargo build --examples

With Ubuntu’s linker, readelf -d then shows a RUNPATH entry, and the program loads MPICH 4.2.3 with LD_LIBRARY_PATH unset. The loader searches a RUNPATH after LD_LIBRARY_PATH, so a module can still point the program at another build. Changing RUSTFLAGS rebuilds every crate of the project.

Launching

Through cargo

Building and launching are two commands because cargo run starts the program itself, without a launcher. Cargo can start it through one: a runner is a command that cargo puts in front of the programs it runs. Set it for one command with an environment variable:

CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUNNER="mpiexec -n 2" cargo run --example launcher

or for a project in .cargo/config.toml:

[target.'cfg(target_os = "linux")']
runner = "mpiexec -n 2"

Cargo uses the runner for cargo run, cargo test and cargo bench, so with this setting every test and benchmark binary also starts as a job of two processes. The environment variable wins over the file.

What the launcher tells each process

A launcher gives each process its place in the job through environment variables, which the MPI library reads during initialization. They are set before main runs:

LauncherRankRank among the processes on its node
MPICH’s mpiexec (Hydra)PMI_RANKMPI_LOCALRANKID
Open MPI’s mpirunOMPI_COMM_WORLD_RANKOMPI_COMM_WORLD_LOCAL_RANK
Slurm’s srunSLURM_PROCIDSLURM_LOCALID

After Mpi::init, the communicator is what counts. Before it, the variables are all a process has, and they are enough to name a log file or choose a GPU before the library starts. When they disagree with the communicator, the program and the launcher are not in the same job. This program checks:

use std::env;

use ferrompi::Mpi;

// Where each launcher puts a process's rank, and its rank among the processes
// on its node: MPICH's Hydra, Open MPI's mpirun, and Slurm's srun.
const RANK: [&str; 3] = ["PMI_RANK", "OMPI_COMM_WORLD_RANK", "SLURM_PROCID"];
const LOCAL_RANK: [&str; 3] = ["MPI_LOCALRANKID", "OMPI_COMM_WORLD_LOCAL_RANK", "SLURM_LOCALID"];

// The first of `names` that is set to a number, and the number.
fn launcher_var(names: &[&'static str]) -> Option<(&'static str, i32)> {
    names
        .iter()
        .find_map(|&name| Some((name, env::var(name).ok()?.parse().ok()?)))
}

fn main() -> ferrompi::Result<()> {
    // Before MPI is initialized, only the launcher's variables say which
    // process this is: enough to name a log file, or to choose a GPU.
    let launcher_rank = launcher_var(&RANK);
    if let Some((name, local)) = launcher_var(&LOCAL_RANK) {
        eprintln!("before init: {name}={local}");
    }

    let mpi = Mpi::init()?;
    let rank = mpi.world().rank();
    match launcher_rank {
        Some((name, early)) if early == rank => {
            eprintln!("rank {rank}: {name}={early}");
            println!("rank {rank}: the launcher's rank agrees with MPI's");
        }
        Some((name, early)) => println!("rank {rank}: {name} says rank {early}"),
        None => println!("rank {rank}: no launcher variable is set"),
    }
    Ok(())
}

With two processes it prints, on standard output:

rank 0: the launcher's rank agrees with MPI's
rank 1: the launcher's rank agrees with MPI's

and on standard error, under Hydra, lines such as before init: MPI_LOCALRANKID=0 and rank 0: PMI_RANK=0. Started with Ubuntu’s library, as in the figure above, both processes call themselves rank 0, and the second one says so:

rank 0: the launcher's rank agrees with MPI's
rank 0: PMI_RANK says rank 1

Started without a launcher, it prints rank 0: no launcher variable is set.

Environment, input and output

Environment. Hydra passes its whole environment to every process (-envall, the default), and so does srun (--export=ALL, the default). Open MPI’s mpirun exports a variable to the processes on other nodes when you name it with -x:

mpirun -n 4 --hostfile hosts -x RUST_BACKTRACE -x RUST_LOG target/release/examples/launcher

Input. Only rank 0 gets the terminal’s standard input. With MPICH, a read on another rank waited until the job was killed. Open MPI gives the other ranks /dev/null, and --stdin chooses other ranks, all or none. Read input on rank 0 and broadcast it.

Output. Every process’s output reaches the terminal through the launcher, a line at a time, in whatever order the lines arrive. Each launcher can label the lines or keep each rank’s output in a file of its own:

LauncherLabel each lineA file per rank
MPICH’s mpiexec-prepend-rank, which writes [0]-outfile-pattern 'out.%r.txt', -errfile-pattern 'err.%r.txt'
Open MPI’s mpirun--output tag, which writes [job,rank]<stdout>:--output file=out, which writes out. and the rank
Slurm’s srun--label--output 'out.%t.txt'

On a cluster

On a cluster the build and the run happen on different machines: you build on a login node, and the job runs on compute nodes that the scheduler picks. Three things have to match between them.

  • The library. Load the same MPI module in the job script as in the shell you built in. The module sets PATH, which build.rs reads, and LD_LIBRARY_PATH, which the loader reads; the job needs the second.
  • The files. The compute nodes see the program where you built it only when the target directory is on a shared filesystem, such as home or a scratch filesystem. Otherwise copy it to each node, for example with Slurm’s sbcast.
  • The processor. A program built with -C target-cpu=native uses every instruction the login node’s processor has, and dies with an illegal instruction on a compute node whose processor lacks one. Name the compute nodes’ processor instead, or keep the default.

A Slurm job script for a job of two nodes, four processes on each, with eight CPUs per process for its threads (chapter 6):

#!/bin/bash
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=4
#SBATCH --cpus-per-task=8
#SBATCH --time=00:30:00

module load mpich                 # the module you built with; names vary by site
srun --mpi=pmix --cpus-per-task="$SLURM_CPUS_PER_TASK" target/release/examples/job_report

srun starts the processes itself, and --mpi=pmix connects them to the MPI library through PMIx, the process-management service that chapter 1 showed the library using to wire up the job. srun --mpi=list shows which interfaces your Slurm offers, and the MPI library must support the one you choose. Where it does not, run the library’s own mpiexec inside the job instead. Passing --cpus-per-task to srun as well keeps each process’s CPU count independent of what the job step inherits from the job. The time limit ends a job that hangs.

Where the processes ran

ferrompi can report where a job’s processes ran. Communicator::topology is a collective that gathers each process’s host name into a TopologyInfo. With the slurm feature, it also carries the Slurm job’s id, node list and CPUs per task, as a SlurmInfo. This program prints each process’s host and, on rank 0, the whole report:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // A collective: each process contributes its host's name, and each gets
    // the map of every host to its ranks.
    let topo = world.topology(&mpi)?;
    for (host, entry) in topo.hosts().iter().enumerate() {
        if entry.ranks.contains(&rank) {
            println!(
                "rank {rank}: host {host} of {}, with ranks {:?}",
                topo.num_hosts(),
                entry.ranks
            );
        }
    }

    if rank == 0 {
        // The whole report, host names and library included.
        eprintln!("{topo}");
        match topo.slurm() {
            Some(job) => println!("Slurm job {}", job.job_id),
            None => println!("not a Slurm job"),
        }
    }
    Ok(())
}

With two processes on one machine it prints:

rank 0: host 0 of 1, with ranks [0, 1]
not a Slurm job
rank 1: host 0 of 1, with ranks [0, 1]

and rank 0 writes the report on standard error. With MPICH 4.2.3, with the machine’s name where this shows node01:

================ MPI Topology ================
Library:   MPICH Version:      4.2.3
MPICH Release date: Wed Oct  2 09:35:21 AM CDT 2024
MPICH ABI:          16:3:4
MPICH Device:       ch4:ofi
MPICH configure:    --prefix=$PREFIX --disable-fortran --with-device=ch4:ofi
…
Standard:  MPI 4.1
Threads:   Single
Processes: 2 across 1 node

  node01: ranks 0, 1  (2 processes)
==============================================

The Library line is the version string of the library rank 0 loaded, from Mpi::library_version: the check that the loader figure calls for, from inside the program. Its MPICH ABI line is the library’s version in libtool’s notation, which the file names come from: 16 − 4 = 12 for the soname, then 4 and 3 for the file, libmpi.so.12.4.3. Under Slurm the report adds the job’s id, node list and CPUs per task, and the program prints Slurm job and the id.

When a process panics or hangs

A job fails as a whole: when one process stops, the others wait at their next call that needs it. Chapter 1 showed how to stop a job on purpose, with abort. This section is about a process that stops on its own. The examples run a program, panic_demo, in which rank 1 indexes past the end of an empty Vec while the other ranks go on to a barrier.

A panic on one process

With Rust’s default, the panic unwinds rank 1’s stack, the process prints the message and exits with status 101, and rank 0 waits in the barrier for a process that is gone. The job hangs, and mpiexec with it.

To make a panic end the job, build with panic = "abort", in the Cargo.toml at the root of the workspace:

[profile.dev]
panic = "abort"

[profile.release]
panic = "abort"

The process then stops at the panic with SIGABRT, and the launcher, seeing a process killed, stops the others. With MPICH the job ended within a second, and mpiexec exited with a non-zero status after printing:

===================================================================================
=   BAD TERMINATION OF ONE OF YOUR APPLICATION PROCESSES
=   PID … RUNNING AT node01
=   EXIT CODE: 134
=   CLEANING UP REMAINING PROCESSES
=   YOU CAN IGNORE THE BELOW CLEANUP MESSAGES
===================================================================================
YOUR APPLICATION TERMINATED WITH THE EXIT STRING: Aborted (signal 6)

Three limits. Cargo reads profiles only from the workspace’s root Cargo.toml, so a library cannot choose this for the programs that use it. Tests and benchmarks ignore the setting, since Rust’s test harness needs to unwind. And an aborting process runs no Drop: it does not finalize MPI, flush a BufWriter, or remove its temporary files.

A backtrace from every process

RUST_BACKTRACE=1 makes a panicking process print its stack. Hydra and srun pass it on; with Open MPI’s mpirun, add -x RUST_BACKTRACE for the processes on other nodes.

RUST_BACKTRACE=1 mpiexec -n 2 target/debug/examples/panic_demo

A process that crashes in C, inside the MPI library or ferrompi’s C layer, prints no Rust backtrace. Run every process under gdb in batch mode instead: each gdb runs its process, and if the process stops on a signal, prints the stack and exits. rust-gdb, which rustup installs, is gdb with Rust’s pretty-printers loaded.

mpiexec -n 2 gdb -q -batch -ex run -ex bt --args target/debug/examples/panic_demo

Built with panic = "abort", the panic is such a signal. Rank 1’s gdb prints, after the panic’s message:

Thread 1 "panic_demo" received signal SIGABRT, Aborted.
…
#4  0x… in __GI_abort () at ./stdlib/abort.c:79
…
#15 0x… in core::panicking::panic_bounds_check () at library/core/src/panicking.rs:271
…
#19 0x… in panic_demo::main () at examples/panic_demo.rs:8

Built with unwinding, rank 1 instead exits normally, and its gdb prints [Inferior 1 (process …) exited with code 0145]: gdb writes exit codes in octal, and 0145 is 101.

Where a hung job waits

A hung job prints nothing. To see where each process waits, interrupt them all under gdb. MPICH’s mpiexec passes a SIGINT on to its processes, printing Sending Ctrl-C to processes as requested, and gdb, on SIGINT, stops its process and goes on to its next command, bt. timeout sends the signal after the number of seconds you give it:

timeout -s INT 60 mpiexec -n 2 gdb -q -batch -ex run -ex bt --args target/debug/examples/panic_demo

On the unwinding build, rank 0’s gdb shows it in the barrier, through every layer of ferrompi down to MPICH:

Thread 1 "panic_demo" received signal SIGINT, Interrupt.
…
#12 0x… in MPIR_Barrier_intra_dissemination () from $PREFIX/lib/libmpi.so.12
…
#18 0x… in PMPI_Barrier () from $PREFIX/lib/libmpi.so.12
#19 0x… in ferrompi_barrier (comm_handle=0) at csrc/ferrompi.c:1108
#20 0x… in ferrompi::ffi::ferrompi_barrier (comm=0) at …/ferrompi/src/ffi.rs:234
#21 ferrompi::comm::Communicator::barrier (self=0x…) at …/ferrompi/src/comm/blocking.rs:29
#22 0x… in panic_demo::main () at examples/panic_demo.rs:10

Read it from the bottom: your main; ferrompi’s Communicator::barrier; the declaration of the C function, in src/ffi.rs; the C layer’s ferrompi_barrier; and PMPI_Barrier, the library’s own entry point, under which MPICH waits for a message that will not come. Chapter 3 lists the usual reasons a collective hangs, and chapter 9 follows the same path through ferrompi’s source.

gdb can also attach to a running process, with gdb -p and its process id, without restarting the job, where the kernel allows it. Ubuntu sets /proc/sys/kernel/yama/ptrace_scope to 1, which lets a process trace only its own children, so gdb fails to attach to a rank that mpiexec started, and names that file. It can attach when run as root.

Exercises

  1. Run cargo clean -p ferrompi, then cargo build -vv --example hello_world, and find the Found MPI via line. If pkg-config knows your library, build again with MPI_PKG_CONFIG set to its package, and compare the rustc-link lines.
  2. Run ldd on an example with and without LD_LIBRARY_PATH. If your machine has a second libmpi.so.12, run the launcher program both ways and say which line changes, and why.
  3. Set the runner in .cargo/config.toml and run the job report with cargo run. Then run cargo test in a project with one unit test, and count the test result lines.
  4. Change the job report so that each process also prints its rank on its node, from the launcher’s variable, and compare it with the position of its rank in its host’s list of ranks.
  5. Write panic_demo. Run it under timeout 20 as built, then with panic = "abort", and compare how each job ends.
  6. Run the unwinding panic_demo under the hang recipe, and find the frame where ferrompi’s Rust calls its C layer.

Summary

  • Add ferrompi like any crate. The rma and slurm features add parts of the API, and a program contains one version of ferrompi.
  • build.rs finds MPI, compiles csrc/ferrompi.c with the library’s flags into libferrompi.a, and tells rustc to link libmpi. cargo build -vv, or the output and stderr files under target/debug/build, show what it found.
  • Choose a library with MPI_PKG_CONFIG, MPICC or CRAY_MPICH_DIR. A set variable whose probe fails stops the build. Cargo rebuilds ferrompi when one of them or PATH changes.
  • A program names libmpi.so.12, not a directory. The loader takes the first file of that name on LD_LIBRARY_PATH, in its cache, or in the system directories, and ldd shows which. A library of the same name from another build can load silently.
  • A Cargo runner launches cargo run, cargo test and cargo bench through mpiexec. Launchers put each process’s rank in variables that exist before Mpi::init. Only rank 0 reads standard input, and each launcher can label or separate the ranks’ output.
  • On a cluster, build and run with the same module, put the program where the compute nodes can read it, build for their processor, and launch with srun --mpi=pmix or the library’s mpiexec.
  • A panic on one process hangs the job unless the program is built with panic = "abort". Run each process under gdb in batch mode to get a backtrace of a crash, and send the job SIGINT to see where a hung job waits.
