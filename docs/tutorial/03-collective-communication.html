Part I · Chapter 3

Collective communication

Operations that every process of a communicator takes part in: one process sends to all, all send to one, or all combine their values. A collective says what the group needs done, and the library decides which messages to send.

By the end of the chapter you can hand out work and collect results, combine values across processes, compute where each process writes in a shared output, and tell why a collective hangs. The chapter assumes chapter 2: a collective is made of the same kind of messages, but the library sends them for you.

What a collective is

A collective operation involves every process of a communicator. Each process calls the same method on the communicator, and the call does that process’s part: sending, receiving, or combining. A point-to-point call names a partner and a tag; a collective names neither. The communicator is the group, and the call’s place in the program identifies it. The rules follow from that:

  • Every process of the communicator makes the call. A process that skips it leaves the others waiting.
  • Every process makes the communicator’s collective calls in the same order. MPI pairs each process’s first collective with every other process’s first, the second with the second, and so on. A pair that does not match, a broadcast against a reduction say, is an error the libraries do not check: the job hangs, crashes, or computes the wrong result.
  • Every process passes the same root, and slices whose lengths agree. MPI requires each process to receive exactly the amount sent to it: unlike a point-to-point receive, a collective receive may not be longer. ferrompi takes the count it hands MPI from a slice’s length, such as the slice of a broadcast, so those lengths must match across processes.
  • There are no tags. Collective messages never match point-to-point receives, even on the same communicator.
  • A collective need not synchronize. A process’s call returns once that process’s part is done, so the root of a broadcast may return before any other process has the data. A collective whose result needs every process’s data, such as a sum, cannot finish anywhere before every process has joined it; the barrier is the one collective that exists to wait.

Chapter 1 met these rules already: creating a communicator is collective. This chapter covers the collectives that move and combine data.

Barrier

barrier() (MPI_Barrier) returns on a process only once every process of the communicator has called it. Its common use is timing: start every process’s clock at the same moment, so that every process times the same phase.

use std::time::Duration;

use ferrompi::{Mpi, ReduceOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Start every clock at the same moment, so that every process times the
    // same phase.
    world.barrier()?;
    let start = mpi.wtime();

    // The phase: rank r works for 10 (r + 1) milliseconds.
    std::thread::sleep(Duration::from_millis(10 * (rank as u64 + 1)));
    let elapsed = mpi.wtime() - start;

    // The phase lasts as long as its slowest process.
    let slowest = world.reduce_scalar(elapsed, ReduceOp::Max, 0)?;
    if rank == 0 {
        println!("the phase took {slowest:.3} s");
    }
    Ok(())
}

With four processes it prints a time a little over 0.040 s, which is rank 3’s. Mpi::wtime reads MPI_Wtime, a wall clock in seconds, and the reduce_scalar at the end, covered under Reductions, hands rank 0 the largest of the four times.

Most programs need fewer barriers than they have. A collective that needs every process’s data already waits for it, and a receive already waits for its message; a barrier between them only adds a wait.

A barrier does not order output

Calling barrier between prints does not make the processes print in rank order. Each process’s standard output reaches your terminal through the launcher, which forwards each process’s lines as they arrive, so lines printed after a barrier can still come out in any order. To print in order, gather the values at one process and print them there.

Moving data

Five collectives move data without combining it. The figure shows what each one does to the buffers of three processes.

Broadcast

broadcast(data, root) (MPI_Bcast) copies the root’s slice into every other process’s slice. Every process passes a slice of the same length; the root’s is read and the others are overwritten.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Only rank 0 knows the run's parameters, say from a file it read. Every
    // process passes a slice of the same length.
    let mut params = [0u64; 3];
    if rank == 0 {
        params = [64, 32, 10];
    }
    world.broadcast(&mut params, 0)?;

    let [nx, ny, steps] = params;
    println!("rank {rank}: grid {nx} x {ny}, {steps} steps");
    Ok(())
}

With four processes it prints:

rank 0: grid 64 x 32, 10 steps
rank 1: grid 64 x 32, 10 steps
rank 2: grid 64 x 32, 10 steps
rank 3: grid 64 x 32, 10 steps

The other processes cannot learn the length from the message, because a collective receive must name exactly the amount sent. When only the root knows how long the data is, broadcast the length first, then the data.

Scatter and gather

scatter(send, recv, root) (MPI_Scatter) splits the root’s send slice into blocks of recv.len() elements and gives block i to rank i, the root included. gather(send, recv, root) (MPI_Gather) does the reverse: the root’s recv receives every process’s send, in rank order, so it must hold send.len() times the number of processes. The root’s side of each call is read only at the root, and the other processes may pass an empty slice there.

use ferrompi::Mpi;

const CHUNK: usize = 3;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());
    let root = rank == 0;

    // Rank 0 holds the whole input, 1 to 3 size. The other processes pass an
    // empty slice: MPI reads the send slice of a scatter only at the root.
    let input: Vec<i64> = if root {
        (1..=(CHUNK * size as usize) as i64).collect()
    } else {
        Vec::new()
    };
    let mut mine = [0i64; CHUNK];
    world.scatter(&input, &mut mine, 0)?;

    let partial: i64 = mine.iter().sum();
    println!("rank {rank} got {mine:?}, partial sum {partial}");

    // The receive slice of a gather, likewise, matters only at the root.
    let mut partials = vec![0i64; if root { size as usize } else { 0 }];
    world.gather(&[partial], &mut partials, 0)?;
    if root {
        let total: i64 = partials.iter().sum();
        println!("rank 0 gathered {partials:?}, total {total}");
    }
    Ok(())
}

With four processes it prints:

rank 0 got [1, 2, 3], partial sum 6
rank 1 got [4, 5, 6], partial sum 15
rank 2 got [7, 8, 9], partial sum 24
rank 3 got [10, 11, 12], partial sum 33
rank 0 gathered [6, 15, 24, 33], total 78

ferrompi checks the lengths before calling MPI, where they matter: a root whose send holds fewer than recv.len() times the number of processes gets Err(Error::BufferSize) back. The check runs on the root alone, and the other processes have already entered the scatter, where they wait for data that never comes. When a collective hangs returns to this.

Allgather and all-to-all

allgather(send, recv) (MPI_Allgather) is a gather without a root: every process receives every process’s block, in rank order.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    // Each process owns some cells of a grid. Every process learns how many
    // each one owns, so that any of them can tell who owns a given cell.
    let mine = [100 + 10 * rank];
    let mut owned = vec![0i32; size as usize];
    world.allgather(&mine, &mut owned)?;
    println!("rank {rank} sees {owned:?}");
    Ok(())
}

With four processes it prints:

rank 0 sees [100, 110, 120, 130]
rank 1 sees [100, 110, 120, 130]
rank 2 sees [100, 110, 120, 130]
rank 3 sees [100, 110, 120, 130]

alltoall(send, recv) (MPI_Alltoall) gives every process a block from every process: each send holds one block per process, block j goes to rank j, and the block from rank i lands in block i of recv. Both slices have the same length, a multiple of the number of processes.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    // Rank r holds row r of a size x size matrix whose entry (r, c) is 10 r + c.
    let row: Vec<i32> = (0..size).map(|c| 10 * rank + c).collect();

    // Element c of `row` goes to rank c, and element r of `column` comes from
    // rank r: the exchange transposes the matrix.
    let mut column = vec![0i32; size as usize];
    world.alltoall(&row, &mut column)?;
    println!("rank {rank}: row {row:?} -> column {column:?}");
    Ok(())
}

With three processes it prints:

rank 0: row [0, 1, 2] -> column [0, 10, 20]
rank 1: row [10, 11, 12] -> column [1, 11, 21]
rank 2: row [20, 21, 22] -> column [2, 12, 22]

All-to-all is the most expensive of the five: with p processes, each one exchanges a block with each of the p − 1 others. Programs use it to transpose distributed matrices, as in a parallel FFT, and to send each item to the process that owns its key.

Reductions

A reduction combines one value from every process into one result. reduce(send, recv, op, root) (MPI_Reduce) combines the processes’ send slices element by element with op and writes the result into the root’s recv. allreduce(send, recv, op) (MPI_Allreduce) gives the result to every process. Each has two shorter forms: reduce_scalar and allreduce_scalar take one value and return the result, which only the root may use in the case of reduce_scalar; reduce_inplace and allreduce_inplace overwrite the input slice with it.

The operation is a ReduceOp: Sum, Prod, Max and Min for every element type; BitwiseAnd, BitwiseOr and BitwiseXor, and LogicalAnd, LogicalOr and LogicalXor, for the integer types only. A bitwise or logical operation on f32 or f64 returns Err(Error::InvalidArgument) before MPI is called. Chapter 4 covers the reductions that also report which process holds the maximum, and operations you define yourself.

This program computes π as the integral of 4 / (1 + x²) from 0 to 1, with the midpoint rule on a million intervals shared among the processes:

use ferrompi::{Mpi, ReduceOp};

const INTERVALS: u32 = 1_000_000;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    // Pi is the integral of 4 / (1 + x^2) over [0, 1]. Each process applies the
    // midpoint rule to every size-th interval, starting at its own rank.
    let h = 1.0 / f64::from(INTERVALS);
    let mine: f64 = (rank as u32..INTERVALS)
        .step_by(size as usize)
        .map(|i| {
            let x = h * (f64::from(i) + 0.5);
            4.0 / (1.0 + x * x)
        })
        .sum();

    // Every process gets the sum of every process's share.
    let pi = world.allreduce_scalar(mine * h, ReduceOp::Sum)?;
    println!("rank {rank}: pi is about {pi:.10}");
    Ok(())
}

With four processes it prints:

rank 0: pi is about 3.1415926536
rank 1: pi is about 3.1415926536
rank 2: pi is about 3.1415926536
rank 3: pi is about 3.1415926536

Floating-point results

Floating-point addition is not associative: (a + b) + c and a + (b + c) can differ in the last bits. A reduction adds the processes’ values in an order the library chooses, and the MPI standard only recommends that the same values, in the same order, give the same result. Printed with 17 decimals instead of 10, the π above, under MPICH 4.2.3, changes with the number of processes from the thirteenth decimal on: 3.14159265358976425 with one process, 3.14159265358993878 with two, 3.14159265358990325 with four. Part of that comes from the partial sums, which group the intervals differently for each process count, and part from the reduction. The reduction alone can change it too: with six processes, forcing MPICH’s ring algorithm with MPIR_CVAR_ALLREDUCE_INTRA_ALGORITHM=ring turns 3.14159265358989792 into 3.14159265358989837, from the same six partial sums.

So compare floating-point results with a tolerance, not for equality, and print them at a precision the computation supports, as the checked output above does. When a result must be the same to the last bit, fix the order yourself: gather the values to one process and add them there in rank order. Integer operations that do not overflow, and Max and Min on any type, involve no rounding, so their results never depend on the order.

Scans

A scan is a reduction over a prefix of the ranks. scan (MPI_Scan) gives rank r the combination of the values of ranks 0 to r, its own included; exscan (MPI_Exscan) gives it ranks 0 to r − 1, and leaves rank 0’s result undefined. Both have _scalar forms. Here are the four ways to combine values side by side, for a sum over four processes:

RankValuereduce to rank 0 allreducescan exscan
0110101undefined
12not written1031
23not written1063
34not written10106

The classic use is offsets. When every process writes its items into one output, a file or a global numbering, a process’s items start after those of every lower rank: at the exclusive scan of the counts.

use ferrompi::{Mpi, ReduceOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Each process has rank + 1 items to write into one output, after the
    // items of every lower rank.
    let count = rank as u64 + 1;

    // The inclusive scan ends where this process's items end.
    let end = world.scan_scalar(count, ReduceOp::Sum)?;
    // The exclusive scan starts where they start. Rank 0 calls it too, like
    // every collective, but its result there is undefined.
    let before = world.exscan_scalar(count, ReduceOp::Sum)?;
    let start = if rank == 0 { 0 } else { before };

    println!("rank {rank} writes items {start}..{end}");
    Ok(())
}

With four processes it prints:

rank 0 writes items 0..1
rank 1 writes items 1..3
rank 2 writes items 3..6
rank 3 writes items 6..10

One scan is enough here. For a sum, the exclusive scan is the inclusive scan minus the process’s own value, so end - count gives start without the second call and without the special case for rank 0. The program makes both calls to show both.

Variable counts

Scatter, gather, allgather and all-to-all move blocks of one size. Each has a v form that takes a count per process, and a displacement per process that says where that process’s block starts in the buffer of whole data, both in elements. gatherv(send, recv, counts, displs, root) (MPI_Gatherv) receives rank i’s send, of counts[i] elements, into the root’s recv at index displs[i]. Only the root reads counts and displs. The usual pattern is two collectives: one to learn the counts, one to move the data.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());
    let root = rank == 0;

    // Rank r has r + 1 results.
    let mine: Vec<i32> = (0..=rank).map(|i| 10 * rank + i).collect();

    // The root learns how many results each process has...
    let mut counts = vec![0i32; if root { size as usize } else { 0 }];
    world.gather(&[mine.len() as i32], &mut counts, 0)?;

    // ...places each process's block right after the previous one...
    let displs: Vec<i32> = counts
        .iter()
        .scan(0, |next, &count| {
            let start = *next;
            *next += count;
            Some(start)
        })
        .collect();
    let mut all = vec![0i32; counts.iter().sum::<i32>() as usize];

    // ...and gathers the blocks there. Only the root reads counts and displs.
    world.gatherv(&mine, &mut all, &counts, &displs, 0)?;
    if root {
        println!("counts {counts:?}, displacements {displs:?}");
        println!("gathered {all:?}");
    }
    Ok(())
}

With four processes it prints:

counts [1, 2, 3, 4], displacements [0, 1, 3, 6]
gathered [0, 10, 11, 20, 21, 22, 30, 31, 32, 33]

The others work the same way. scatterv takes the root’s counts and displacements for the blocks it sends; allgatherv needs them on every process; and alltoallv takes a count and a displacement per process for both what it sends and what it receives.

How a library implements a collective

A collective fixes the result; how the messages flow is up to the library. Take a broadcast from rank 0 to eight processes. Written as a loop of sends from the root, it takes seven steps, and the root sends every message. A binomial tree takes three rounds: in each round, every process that has the data sends it to one that does not, so the number of processes with the data doubles, and p processes need ⌈log₂ p⌉ rounds.

Which algorithm runs depends on the message size and the number of processes. MPICH 4.2 documents its usual choice for broadcast, which mpivars prints: a binomial tree for messages under 12 KiB or fewer than 8 processes; above that, a scatter of the message in pieces followed by an allgather of the pieces. A tree sends the whole message in every round, which costs little while the message is small and the time goes mostly to latency. Scatter then allgather sends it in pieces, so no process sends more than about twice the message, however many processes there are. Allreduce has its own set of algorithms (recursive doubling, a ring, a reduce-scatter followed by an allgather, trees), chosen the same way. Open MPI picks among similar algorithms, with thresholds of its own.

Libraries also use the shape of the machine. MPICH’s smp algorithms split a collective into a part within each node, through shared memory, and a part between nodes, in which one process per node takes part. A loop of point-to-point calls gets none of this: it fixes one algorithm, usually the slowest, and hides from the library what the program means. Use the collective.

Choosing the algorithm by hand

MPICH reads its choice from control variables, which mpivars lists with their values. To run the broadcast program with a binomial tree whatever the message size, for instance:

MPIR_CVAR_BCAST_INTRA_ALGORITHM=binomial mpiexec -n 8 target/debug/examples/broadcast

Forcing an algorithm is a way to measure or to test, not a fix: the library’s choice is usually the right one.

Nonblocking collectives

Every collective has a nonblocking form, added in MPI 3.0 and named with an i: ibarrier, ibroadcast, iallreduce, igather, and so on. As with isend and irecv, the call starts the operation and returns a request, inside a ferrompi::scope that borrows the slices until it has completed the request (chapter 2).

use ferrompi::{Mpi, ReduceOp};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // This process's part of a vector distributed over every process.
    let v = vec![f64::from(rank) + 1.0; 2];
    let squares = [v.iter().map(|x| x * x).sum::<f64>()];
    let mut total = [0.0f64];
    let mut largest = 0.0f64;

    ferrompi::scope(|s| {
        world.iallreduce(s, &squares, &mut total, ReduceOp::Sum)?;
        // Work that does not need the sum runs while the reduction proceeds.
        largest = v.iter().fold(0.0, |m, x| m.max(x.abs()));
        Ok(())
    })?;

    println!("rank {rank}: norm {:.6}, largest entry here {largest}", total[0].sqrt());
    Ok(())
}

With four processes it prints:

rank 0: norm 7.745967, largest entry here 1
rank 1: norm 7.745967, largest entry here 2
rank 2: norm 7.745967, largest entry here 3
rank 3: norm 7.745967, largest entry here 4

A nonblocking collective is still a collective. Every process starts it, in the same order as its other collectives on the communicator, and a nonblocking collective never matches a blocking one: iallreduce on one process and allreduce on the others is an error. Several may be in flight on one communicator at a time. Overlap is not promised, as chapter 2’s note on progress says, and a collective made of several rounds of messages may get no further than its first round before the scope ends.

Persistent collectives

A program that runs the same collective at every step can set it up once. MPI 4.0 added persistent collectives, which work like chapter 2’s persistent requests: an _init call returns a request, which the program starts and waits for as often as it needs, so the library can choose its algorithm and prepare once instead of at every call. allreduce_init(send, recv, op) returns a PersistentRequest that owns both vectors. Between runs, write the next input through send_buffer_mut and read the result through buffer.

use ferrompi::{Mpi, ReduceOp};

const TOLERANCE: f64 = 0.1;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Set the reduction up once, and run it at every step. Needs MPI 4.0 or
    // Open MPI 5.
    let mut largest = world.allreduce_init(vec![0.0f64], vec![0.0f64], ReduceOp::Max)?;

    let mut residual = f64::from(rank) + 1.0;
    let mut steps = 0;
    loop {
        largest.send_buffer_mut()?[0] = residual;
        largest.start()?;
        largest.wait()?;
        // Every process gets the same maximum, so all of them leave the loop
        // at the same step.
        let worst = largest.buffer()?[0];
        if worst < TOLERANCE {
            println!("rank {rank}: stopped after {steps} steps, largest residual {worst}");
            break;
        }
        residual /= 2.0; // one step of work
        steps += 1;
    }
    Ok(())
}

With four processes it prints:

rank 0: stopped after 6 steps, largest residual 0.0625
rank 1: stopped after 6 steps, largest residual 0.0625
rank 2: stopped after 6 steps, largest residual 0.0625
rank 3: stopped after 6 steps, largest residual 0.0625

The _init call is a collective, and so is every start: each process starts the request at the same place in its sequence of collectives. That is why the loop decides from the allreduce’s result rather than from each process’s own residual. Every process must leave the loop at the same step, or the ones that stay start a collective the others never join; a maximum involves no rounding, so every process sees the same value and decides the same way.

Needs MPI 4.0 or Open MPI 5

Persistent collectives are MPI 4.0 functions. MPICH has them from 4.0, and Open MPI from 5.0. Built against an older library, such as Open MPI 4.1, every _init collective returns Err(Error::NotSupported) without calling MPI, so a program that must run there falls back to the blocking or nonblocking form.

When a collective hangs

A hung collective almost always means the processes disagree about which collective comes next. The usual causes:

  • A collective under a condition that only some processes meet, such as if rank == 0 { world.barrier()?; }, or in a loop whose number of steps differs between processes.
  • Collectives in a different order on different processes, or with a different root.
  • An error on one process. ferrompi checks lengths and arguments before it calls MPI and returns the error on the process that made the mistake, which usually returns from main; the others are already inside the collective. As chapter 1 says, an Err on one process does not stop the others: call world.abort(code) when the job cannot go on.

When the processes might disagree, have them agree first. Compute the condition on every process and combine it with an allreduce, taking the Min of a flag that is 1 when the process can go on and 0 when it cannot; every process then gets the same answer and takes the same branch. ferrompi’s MPI tests agree on their verdicts this way, in the check helper of examples/common.

To find where a hung job waits, attach a debugger to its processes, for instance gdb -p PID followed by bt: the backtrace names the collective each one is in, and the process that is somewhere else is usually the culprit.

Exercises

  1. In the barrier program, make rank 0 sleep 100 ms before its first barrier, and end the phase with a second world.barrier()? before reading the clock. Run it, then remove the first barrier and run it again. Why does the time change, and which of the two is the phase’s?
  2. Rewrite the broadcast program with send and recv, rank 0 sending to every other rank in turn. With p processes, how many messages does rank 0 send, and how many steps does the last rank wait for? Compare the binomial tree.
  3. In the scatter-gather program, give rank 0 an input one element short. What does rank 0 get, and what do the other processes do? Stop the job with Ctrl-C, then make rank 0 end the job with world.abort when the scatter fails.
  4. Print π with {pi:.17} and run the program with 1 to 8 processes. Under MPICH, run it with six processes and MPIR_CVAR_ALLREDUCE_INTRA_ALGORITHM=ring, then with recursive_doubling.
  5. Make the gatherv program give the whole result to every process: gather the counts with allgather, compute the displacements on every process, and replace gatherv with allgatherv.
  6. Split the world into even and odd ranks with split (chapter 1) and run the offsets program’s two scans on each half. Predict what each rank prints with -n 4, then run it.

Summary

  • A collective involves every process of a communicator. All of them make the call, in the same order relative to their other collectives, with the same root and with amounts that match exactly; there are no tags.
  • A collective need not synchronize. Only the barrier exists to wait, and it does not order output.
  • Broadcast, scatter, gather, allgather and all-to-all move data; their v forms take a count and a displacement per process. The root’s buffers matter only at the root.
  • Reductions combine a value from every process with a ReduceOp; scans combine a prefix of the ranks and give each process its offset. A floating-point sum can change with the process count and the algorithm, so compare it with a tolerance.
  • The library chooses the messages: a tree for a small broadcast, scatter then allgather for a large one, shared memory within a node. Use the collective rather than a loop of sends.
  • Nonblocking collectives run in a ferrompi::scope and never match blocking ones. Persistent collectives, from MPI 4.0, set an operation up once for a loop.
  • A hang means the processes disagree about the next collective. Agree on conditions with an allreduce, and end a job that cannot go on with abort.
