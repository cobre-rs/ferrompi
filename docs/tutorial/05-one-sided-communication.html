Part I · Chapter 5

One-sided communication and shared-memory windows

In one-sided communication a process reads or writes another process’s memory, and the other process makes no call for the transfer. This chapter covers the memory a process exposes, the three ways to synchronize access to it, the operations that update it atomically, and memory that the processes of one node share.

By the end of the chapter you can write a halo exchange with puts, keep counters that any process can add to, hand out work from a queue that no process serves, and keep one copy of a table per node instead of one per process. The chapter assumes chapter 2 for the halo exchange and chapter 3 for barriers and reductions.

The rma feature

ferrompi builds its one-sided API only with the rma feature. Enable it in Cargo.toml:

[dependencies]
ferrompi = { version = "0.7", features = ["rma"] }

Inside the ferrompi repository, build the examples with cargo build --examples --features rma.

What one-sided means

Every message in chapter 2 took two calls: a send at one process and a matching receive at the other. The receiver had to expect the message and say where to put it. One-sided communication, which MPI calls remote memory access (RMA), has no receive. A process exposes part of its memory as a window. Another process, the origin, puts data into it, gets data from it, or combines data with it, naming the target process and a position in the target’s window. The target makes no call for the transfer.

The target still takes part in synchronization. A put is not visible at the target when the origin issues it. MPI completes it by the end of an epoch, a stretch of the program that one synchronization call opens and another closes. Every transfer belongs to an epoch, and the call that closes the epoch is the point after which both sides can rely on it.

One-sided communication suits patterns the target cannot predict: updates to data that other processes own, work handed out on demand, and reads of a large table that lives at another process. It also fits a regular exchange, such as a halo, where it skips the matching of sends with receives. Whether that makes the exchange faster depends on the library and the network, so measure before you switch.

Windows

A window is created by every process of a communicator together: the constructors are collective, like the collectives of chapter 3. Each process contributes its own memory, of any length, including none. The element type may differ from process to process, but its size may not. ferrompi has three constructors:

ConstructorMPI callMemory
Win::create(&comm, vec)MPI_Win_createa Vec you fill first; the window owns it, and into_buffer gives it back
Win::allocate(&comm, count)MPI_Win_allocateallocated by MPI, which can pick memory suited to RMA on its network; starts at zero
Win::allocate_shared(&comm, count)MPI_Win_allocate_sharedallocated by MPI in memory that every process of comm can load and store; starts at zero

A position in a window is a displacement, counted in elements: ferrompi sets the displacement unit to size_of::<T>(), so displacement 3 of a Win<f64> is its fourth element, at byte 24. Each process’s window starts at displacement 0, wherever it is in memory.

A process reads and writes its own window through a WinView, from win.local() outside an epoch or from the epoch handle inside one. A view has read(i), write(i, value), copy_to_slice and copy_from_slice, but no safe &[T]: another process may write the memory at any time, and the compiler may assume that a slice does not change while it is borrowed. The view’s accesses are relaxed atomic loads and stores, which stay sound while that happens.

Dropping a window frees it with MPI_Win_free, which is collective. Every process must drop it: a process that keeps its window while the others drop theirs leaves them waiting in MPI_Win_free. A window still alive when the Mpi handle is dropped makes ferrompi skip MPI_Finalize, as chapter 1 said, so drop windows before it, in the same order at every process.

Fence epochs

The simplest synchronization is the fence. Win::fence calls MPI_Win_fence, runs a closure in which the process issues its transfers, and calls MPI_Win_fence again when the closure returns. A fence is collective over the window’s communicator, like a barrier. When the closing fence returns at a process, the transfers that process issued are complete, and the transfers that targeted its window have landed.

Here is chapter 2’s halo exchange written with puts. Each process’s window holds its three cells between two ghost cells, at displacements 0 and 4, and each process puts its edge cells straight into its neighbors’ ghost cells:

use ferrompi::{Mpi, Win, WinFenceAssert};

const CELLS: usize = 3;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    let first = rank * CELLS as i32;
    let cells: Vec<i32> = (first..first + CELLS as i32).collect();

    // The window holds a ghost cell, the three cells, and another ghost cell:
    // the ghosts are displacements 0 and CELLS + 1.
    let mut window = vec![0i32; CELLS + 2];
    window[1..=CELLS].copy_from_slice(&cells);
    let mut win = Win::create(&world, window)?;

    // The origin buffers of the puts are declared before the epoch: MPI reads
    // them until the closing fence returns.
    let first_cell = [cells[0]];
    let last_cell = [cells[CELLS - 1]];

    // No RMA call came before the opening fence, and none comes after the
    // closing one.
    win.fence(WinFenceAssert::no_precede(), WinFenceAssert::no_succeed(), |e| {
        // Write the edge cells straight into the neighbors' ghost cells. The
        // neighbors make no call for them.
        if rank + 1 < size {
            e.put(&last_cell, rank + 1, 0)?;
        }
        if rank > 0 {
            e.put(&first_cell, rank - 1, CELLS as i64 + 1)?;
        }
        Ok(())
    })?;

    // The closing fence has returned at every process: the puts that target
    // this process have landed.
    let view = win.local();
    let ghost_left = view.read(0);
    let ghost_right = view.read(CELLS + 1);
    let mut next = [0i32; CELLS];
    next[0] = ghost_left + cells[0] + cells[1];
    for i in 1..CELLS - 1 {
        next[i] = cells[i - 1] + cells[i] + cells[i + 1];
    }
    next[CELLS - 1] = cells[CELLS - 2] + cells[CELLS - 1] + ghost_right;
    println!("rank {rank}: {cells:?} -> {next:?}");
    Ok(())
}

With four processes it prints what chapter 2’s version printed:

rank 0: [0, 1, 2] -> [1, 3, 6]
rank 1: [3, 4, 5] -> [9, 12, 15]
rank 2: [6, 7, 8] -> [18, 21, 24]
rank 3: [9, 10, 11] -> [27, 30, 21]

Compared with chapter 2’s version, there are no receives, tags or requests: each process says where its data goes, and its neighbors make no call for it. The closing fence is the one point at which every process waits. In C, one MPI_Win_fence between two steps of a time loop closes one epoch and opens the next. ferrompi gives each epoch its own closure, with a fence on each side, so a loop that calls fence once per step makes two fences per step.

Origin buffers belong to MPI until the epoch closes

put does not copy its origin slice when it is called: MPI may read the slice at any time until the closing fence returns. ferrompi enforces that with the borrow that chapter 2’s scope used. Every buffer an operation names is borrowed until the epoch closes, so the program cannot change it or drop it sooner. A buffer declared inside the closure would be dropped before the closing fence, so ferrompi rejects it: declare the origin buffers, and the destinations of get, before the call to fence, as the program does with first_cell and last_cell.

Assertions

The two WinFenceAssert arguments are promises that let MPI skip work. The program makes the two most common ones: its opening fence asserts that no earlier transfer is waiting for it, and its closing fence that no epoch follows. Each of those two must be made at every process or at none.

AssertionMPI modeThe promise
none()0none
no_store()MPI_MODE_NOSTOREthis process stored nothing into its window since the last synchronization
no_put()MPI_MODE_NOPUTno put or accumulate will update this process’s window before the next synchronization
no_precede()MPI_MODE_NOPRECEDEthe fence completes no transfer; opening fence only
no_succeed()MPI_MODE_NOSUCCEEDthe fence opens no epoch; closing fence only

Combine them with |. ferrompi refuses no_succeed on an opening fence and no_precede on a closing one, either of which would let MPI keep using a buffer after the closing fence returned. Any other false promise goes undetected and can give wrong data, so pass none() unless you know an assertion holds.

Accumulate and atomic operations

Two puts to the same element in one epoch conflict, and so do a put and a get of it: MPI does not say what lands or what is read. Accumulates are the exception. accumulate combines its data into the target with a reduction operation, and accumulates from any number of processes to one element in one epoch all take effect, as long as they use the same operation. Each one is atomic per element.

A tally is the plain case. Here each candidate’s tally lives at one process, and every process adds its ballots to the tallies wherever they live:

use ferrompi::{Mpi, ReduceOp, Win, WinFenceAssert};

const CANDIDATES: usize = 8;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    // The tally of candidate c lives at process c % size, in slot c / size.
    let owned = (CANDIDATES - rank as usize).div_ceil(size as usize);
    let mut win = Win::<u64>::allocate(&world, owned)?;

    // Each process holds five ballots; candidate 5 is on all of them.
    let ballots: Vec<usize> = (0..4)
        .map(|i| (rank as usize * 3 + i) % CANDIDATES)
        .chain([5])
        .collect();
    let one = [1u64];

    win.fence(WinFenceAssert::no_precede(), WinFenceAssert::no_succeed(), |e| {
        for &c in &ballots {
            let owner = (c % size as usize) as i32;
            let slot = (c / size as usize) as i64;
            // Several processes add to one tally in the same epoch. Each
            // accumulate is atomic per element, so no vote is lost.
            e.accumulate(&one, owner, slot, ReduceOp::Sum)?;
        }
        Ok(())
    })?;

    let view = win.local();
    let tallies: Vec<String> = (0..view.len())
        .map(|slot| {
            let c = slot * size as usize + rank as usize;
            format!("candidate {c}: {}", view.read(slot))
        })
        .collect();
    println!("rank {rank}: {}", tallies.join(", "));
    Ok(())
}

With four processes it prints:

rank 0: candidate 0: 2, candidate 4: 2
rank 1: candidate 1: 3, candidate 5: 5
rank 2: candidate 2: 2, candidate 6: 2
rank 3: candidate 3: 3, candidate 7: 1

All four processes added to candidate 5’s tally in the same epoch, process 1 twice, and no vote was lost. Compare it with chapter 4’s histogram, built with reduce_scatter_block, where every process sent a count for every bin. Here a process sends one operation per ballot to the process that owns the tally, and the owner never learns how many arrived. That suits a large table of which each process touches a few entries.

accumulate returns nothing. Three more operations also fetch the value that was there, atomically with the update:

MethodMPI callWhat it does
accumulate(&origin, rank, disp, op)MPI_Accumulatecombines origin into the target
get_accumulate(&origin, &mut result, rank, disp, op)MPI_Get_accumulatethe same, and fetches the old values into result
fetch_and_op(&origin, &mut result, rank, disp, op)MPI_Fetch_and_opthe same for one element, which libraries can do faster
compare_and_swap(&origin, &compare, &mut result, rank, disp)MPI_Compare_and_swapfor one element: stores origin if the target equals compare, and fetches the old value; integers only

The operation is a ReduceOp, or AccumulateOp::REPLACE to store the data atomically. The two fetching operations take a FetchOp, which adds FetchOp::NO_OP: it changes nothing and fetches the value, an atomic read. compare_and_swap is offered for the integer types only, since comparing floating-point values bit by bit is rarely what a program means.

Passive target: locks

Every process takes part in a fence, so a fence epoch is one-sided only for the data. In a passive-target epoch the target takes no part at all: the origin locks the target’s window, issues its operations, and unlocks it. Win::lock(lock_type, rank, f) locks rank’s window, runs the closure, and unlocks the window when the closure returns. An Exclusive lock keeps every other origin out. Several origins can hold a Shared lock at once, which is enough when their operations are accumulates or do not conflict. lock_all takes a shared lock on every process’s window.

One counter can hand out work. Here process 0’s window holds the number of the next task. Each process claims a task with fetch_and_op, which adds 1 to the counter and returns its old value, and does the task with that number, until the numbers run out. No process serves the queue, and a process that finishes its tasks sooner takes more of them:

use ferrompi::{LockType, Mpi, ReduceOp, Win};

const TASKS: u64 = 20;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // One counter, the next task to hand out, at process 0. An allocated
    // window starts at zero.
    let mut win = Win::<u64>::allocate(&world, if rank == 0 { 1 } else { 0 })?;

    let one = 1u64;
    let mut task = 0u64;
    let mut done = vec![0u64; TASKS as usize];
    loop {
        // Take the next task: add 1 to the counter and fetch its old value,
        // in one atomic operation. The lock is shared, so other processes can
        // take tasks at the same time.
        win.lock(LockType::Shared, 0, |e| {
            e.fetch_and_op(&one, &mut task, 0, 0, ReduceOp::Sum)
        })?;
        // The unlock has returned: `task` is valid.
        if task >= TASKS {
            break;
        }
        // The task itself; here, mark it done.
        done[task as usize] += 1;
    }

    // Count how often each task ran, over every process.
    let mut runs = vec![0u64; TASKS as usize];
    world.allreduce(&done, &mut runs, ReduceOp::Sum)?;
    if rank == 0 {
        println!("{} tasks done", runs.iter().sum::<u64>());
        println!(
            "every task ran exactly once: {}",
            runs.iter().all(|&n| n == 1)
        );
    }
    Ok(())
}

With four processes, process 0 prints:

20 tasks done
every task ran exactly once: true

Which process takes which task changes from run to run, but no number goes to two processes, because fetch_and_op is atomic. Each process stops at its first number past the last task, so the counter ends at 20 plus the number of processes.

What the compiler rejects

The program reads task after lock returns. MPI would allow reading it sooner: flush(0) completes the epoch’s operations on process 0 without ending the epoch. Try it: call e.flush(0)? after the fetch_and_op, return Ok(task < TASKS) from the closure, and stop the loop when lock returns false. The program does not compile:

error[E0503]: cannot use `task` because it was mutably borrowed
  --> src/main.rs:24:16
   |
21 |         let more = win.lock(LockType::Shared, 0, |e| {
   |                                                   - has type `&'1 PassiveEpoch<'1, '_, u64>`
22 |             e.fetch_and_op(&one, &mut task, 0, 0, ReduceOp::Sum)?;
   |             ----------------------------------------------------
   |             |                    |
   |             |                    `task` is borrowed here
   |             argument requires that `task` is borrowed for `'1`
23 |             e.flush(0)?;
24 |             Ok(task < TASKS)
   |                ^^^^ use of borrowed `task`

The borrow of task lasts until the epoch closes, whatever happens inside it, so ferrompi is stricter here than MPI: data fetched in an epoch is read after it. A program that needs a value sooner ends the epoch there and opens another, as the counter loop does with one lock per task. The flushes still complete transfers at the target without giving up the lock, which a program needs before it tells another process, by a message, that the data is there. The rustdoc of Win lists what else the borrows reject.

When the target must make progress

A passive target makes no call, but its MPI library may still have work to do for the origin. Where the network cannot apply an operation by itself, the target’s library applies it, and the library usually runs only inside an MPI call. A target that computes for a long time without calling MPI can then hold up every origin that locked it, whose unlock waits until the target’s library runs. In the counter program process 0 is a worker too and calls MPI for every task, so the counter never waits long. For a target that computes for long stretches, MPICH can run a progress thread: MPIR_CVAR_ASYNC_PROGRESS=1 in the environment starts one, and raises the thread level to Multiple, which chapter 6 covers.

Synchronizing with neighbors only

A fence synchronizes every process of the window, even in a halo exchange, where each process deals with two others. The third mode, post-start-complete-wait (PSCW), narrows the synchronization to groups. A target opens an exposure epoch for a group of origins with post, and closes it with wait_exposure, which returns once they have all finished. An origin opens an access epoch to a group of targets with start, which runs a closure and calls MPI_Win_complete when it returns. The groups are the ones of chapter 1. Here is the halo exchange again, with each process synchronizing with its neighbors only:

use ferrompi::{Mpi, Win, WinPscwAssert};

const CELLS: usize = 3;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    let first = rank * CELLS as i32;
    let cells: Vec<i32> = (first..first + CELLS as i32).collect();
    let mut window = vec![0i32; CELLS + 2];
    window[1..=CELLS].copy_from_slice(&cells);
    let mut win = Win::create(&world, window)?;

    // The neighbors are the processes that write here, and the processes
    // this one writes to.
    let neighbors: Vec<i32> = [rank - 1, rank + 1]
        .into_iter()
        .filter(|&r| (0..size).contains(&r))
        .collect();
    let group = world.group()?.include(&neighbors)?;

    let first_cell = [cells[0]];
    let last_cell = [cells[CELLS - 1]];

    // Expose this window to the neighbors, then write into theirs.
    win.post(&group, WinPscwAssert::none())?;
    win.start(&group, WinPscwAssert::none(), |e| {
        if rank + 1 < size {
            e.put(&last_cell, rank + 1, 0)?;
        }
        if rank > 0 {
            e.put(&first_cell, rank - 1, CELLS as i64 + 1)?;
        }
        Ok(())
    })?;
    // Wait until both neighbors have finished writing here.
    win.wait_exposure()?;

    let view = win.local();
    let ghost_left = view.read(0);
    let ghost_right = view.read(CELLS + 1);
    let mut next = [0i32; CELLS];
    next[0] = ghost_left + cells[0] + cells[1];
    for i in 1..CELLS - 1 {
        next[i] = cells[i - 1] + cells[i] + cells[i + 1];
    }
    next[CELLS - 1] = cells[CELLS - 2] + cells[CELLS - 1] + ghost_right;
    println!("rank {rank}: {cells:?} -> {next:?}");
    Ok(())
}

It prints the same lines:

rank 0: [0, 1, 2] -> [1, 3, 6]
rank 1: [3, 4, 5] -> [9, 12, 15]
rank 2: [6, 7, 8] -> [18, 21, 24]
rank 3: [9, 10, 11] -> [27, 30, 21]

Each process is a target, for the neighbors that write its ghost cells, and an origin, writing theirs, so it posts and starts with the same group. start may wait until every target has posted, so post first: two neighbors that each start before they post can wait for each other forever.

ModeferrompiWho synchronizesSuits

A fence epoch and a lock epoch must not overlap at any process. To move from fences to locks, close the last fence with no_succeed and meet at a barrier before the first lock; to move back, meet at a barrier between the unlock and the next fence. examples/shared_memory.rs moves from fences to a lock this way.

Shared-memory windows

Processes on one node share the node’s memory, but each has its own address space, so a table that every process needs is usually held once per process. Win::allocate_shared allocates a window in memory that every process of a node maps, and each process can then load and store the other processes’ parts of it directly, with no MPI call per access. Its communicator must hold only processes that can share memory, which split_shared gives. Here node rank 0 holds a table and the other processes of the node read it in place:

use ferrompi::{Mpi, Win, WinFenceAssert};

const ENTRIES: usize = 1000;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // The processes that share memory: here, every process on this machine.
    let node = world.split_shared()?;
    let (rank, size) = (node.rank(), node.size());

    // The whole table is allocated once per node, at node rank 0. The other
    // processes allocate nothing.
    let count = if rank == 0 { ENTRIES } else { 0 };
    let mut win = Win::<u64>::allocate_shared(&node, count)?;

    // Node rank 0 fills the table. The closing fence publishes its stores to
    // every process of the node.
    win.fence(WinFenceAssert::no_precede(), WinFenceAssert::no_succeed(), |e| {
        if rank == 0 {
            let squares: Vec<u64> = (0..ENTRIES as u64).map(|i| i * i).collect();
            e.local().copy_from_slice(&squares);
        }
        Ok(())
    })?;

    // Every process reads node rank 0's memory in place: loads, not messages.
    let table = win.remote(0)?;
    let sum: u64 = (rank as usize..table.len())
        .step_by(size as usize)
        .map(|i| table.read(i))
        .sum();
    println!(
        "node rank {rank}: owns {} entries, reads {} in place, sum of its share = {sum}",
        win.local().len(),
        table.len()
    );
    Ok(())
}

On one machine, with four processes, it prints:

node rank 0: owns 1000 entries, reads 1000 in place, sum of its share = 82834000
node rank 1: owns 0 entries, reads 1000 in place, sum of its share = 83083250
node rank 2: owns 0 entries, reads 1000 in place, sum of its share = 83333000
node rank 3: owns 0 entries, reads 1000 in place, sum of its share = 83583250

remote(0) returns a view of node rank 0’s part. It makes no MPI call: ferrompi asked MPI for every part’s address when it created the window, and the view reads with the same relaxed atomic loads as local(). On a node with 64 processes, a table read by all of them is held once instead of 64 times.

Stores into shared memory are not messages, and MPI orders them for you only at a synchronization. In the program, the closing fence publishes the table: it returns at each reader only after node rank 0 has entered it, and node rank 0 has finished its stores by then. Without fences, the writer stores and calls sync inside a lock_all epoch, the processes meet at a barrier, and the readers call sync before they load; examples/shared_memory.rs shows that pattern.

Direct access needs MPI’s unified memory model, in which loads, stores and RMA operations all see one copy of the window. MPI reports the model of each window, and remote returns Error::NotSupported if it is not unified, as well as for a window that is not shared.

When one-sided goes wrong

Most one-sided mistakes give wrong data rather than an error, and many depend on timing, so a program can work until the network gets faster or slower. ferrompi refuses the mistakes it can see at the origin before it calls MPI. A transfer past the end of the target’s window, or to a process outside the epoch, is one:

use ferrompi::{LockType, Mpi, Win};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // Four elements at every process: displacements 0 to 3.
    let mut win = Win::<i32>::allocate(&world, 4)?;

    let value = [7i32];
    if world.rank() == 0 {
        let (past_end, outside) = win.lock(LockType::Exclusive, 1, |e| {
            // One element past the end of process 1's window.
            let past_end = e.put(&value, 1, 4);
            // Process 0's window, which this lock does not cover.
            let outside = e.put(&value, 0, 0);
            Ok((past_end, outside))
        })?;
        if let Err(err) = past_end {
            println!("put at displacement 4: {err}");
        }
        if let Err(err) = outside {
            println!("put to process 0 under a lock on 1: {err}");
        }
    }
    Ok(())
}

With two processes it prints:

put at displacement 4: invalid argument `target_disp`: access extends past the target's window
put to process 0 under a lock on 1: invalid argument `target_rank`: rank outside the epoch's access set

Both are refused with Error::InvalidArgument, and neither reaches MPI. In C both are erroneous: the first can write past the end of process 1’s window, and nothing completes the second, since the lock covers process 1 only. The other mistakes are up to you:

A Win and its views are neither Send nor Sync, so a window stays on the thread that created it; chapter 6 covers MPI with threads.

Exercises

  1. Turn the halo program into a loop of five steps: after each epoch, compute next, write it into the window’s cells with win.local().write, and put the new edge cells in the next epoch. Check the result against chapter 2’s program extended the same way. How many times does each process call MPI_Win_fence?
  2. In the vote program, replace accumulate with a put of each process’s own count for each candidate. Why is the result undefined, even when it looks right?
  3. Make the counter program print how many tasks each process did. Then make process 0 sleep for 100 milliseconds after each of its tasks, with std::thread::sleep. How does the split change? What happens to the other processes if process 0 sleeps for two seconds once, before it takes its first task?
  4. Take task numbers with compare_and_swap instead: read the counter with fetch_and_op and FetchOp::NO_OP, then swap in the value plus one if the counter still holds it, and retry if not. Count the retries of each process.
  5. Split the shared table across the node: each process allocates ENTRIES / size entries, fills its own part in the fence epoch, and sums the whole table by reading every part through remote(r). Does every process get the same sum?
  6. In the PSCW program, start an access epoch to the right neighbor only, and read the error that the put to the left neighbor returns. Then restore it, and post to the right neighbor only. What happens, and why? Run it under timeout.

Summary

  • In one-sided communication an origin puts, gets or accumulates into a target’s window, and the target makes no call for the transfer. Transfers belong to epochs, and are complete when the epoch’s closing call returns.
  • A window is created by every process of a communicator together, and freed when every process drops it. Win::create owns a Vec; allocate and allocate_shared let MPI allocate. Displacements count elements.
  • A fence synchronizes every process; post-start-complete-wait, the processes of a group; a lock, no process but the origin. In ferrompi each epoch is a closure, and the closing call is made when it returns.
  • Every buffer an operation names is borrowed until the epoch closes: declare it before the epoch, and read fetched data after it.
  • Puts to one element in one epoch conflict; accumulates with one operation do not. fetch_and_op and compare_and_swap update one element atomically and return the old value.
  • A passive target may still need to make MPI progress for its origins.
  • allocate_shared on a split_shared communicator gives memory that every process of a node loads and stores directly; a fence, or sync with a barrier, publishes the stores.
  • ferrompi refuses a transfer outside the target’s window or the epoch. Conflicting accesses, early reads and mixed epochs are not detected.
