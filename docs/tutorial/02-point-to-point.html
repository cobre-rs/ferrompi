Part I · Chapter 2

Point-to-point communication

How one process sends data to another: what a message carries, which receive takes it, how the library moves it, why a correct-looking exchange can hang, and how nonblocking and persistent calls let a process keep working while its messages travel.

By the end of the chapter you can exchange data between any two processes, tell a safe exchange from one that works only by luck, and write the halo exchange at the heart of most domain-decomposed programs. The chapter assumes chapter 1: ranks, communicators, and how to build and launch a program.

Messages and envelopes

A point-to-point message goes from one process to one other process of a communicator. It has two parts. The data is a slice of values. The envelope says where the message comes from and how to recognize it: the source rank, the destination rank, a tag, and the communicator. A tag is a non-negative integer that the program chooses, so that a receiver can tell kinds of message apart.

A receive names the envelope it wants: a source, a tag, and the communicator it is called on. A message matches the receive when all three agree. Matching never looks at the data: not its values, not its length, not its type.

Sending and receiving

send(data, dest, tag) (MPI_Send) sends a slice to rank dest of the communicator it is called on. recv(data, source, tag) (MPI_Recv) receives a message from source with tag tag into data. Both block: send returns once the program may change the slice again, and recv returns once the message is in the slice.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // Tag 0 marks the ping and tag 1 the pong.
    match world.rank() {
        0 => {
            world.send(&[1.0f64, 2.0, 3.0], 1, 0)?;
            let mut pong = [0.0f64; 3];
            let status = world.recv(&mut pong, 1, 1)?;
            println!("rank 0 got {pong:?} back from {:?}", status.source);
        }
        1 => {
            let mut buf = [0.0f64; 3];
            world.recv(&mut buf, 0, 0)?;
            println!("rank 1 got {buf:?}");
            for x in &mut buf {
                *x *= 2.0;
            }
            world.send(&buf, 0, 1)?;
        }
        _ => {}
    }
    Ok(())
}

With two processes it prints:

rank 1 got [1.0, 2.0, 3.0]
rank 0 got [2.0, 4.0, 6.0] back from Rank(1)

That send has returned says nothing about the receiver. The library may have delivered the data, or only copied it into a buffer of its own; the sender cannot tell which, and How a message travels explains why that matters.

The slice holds any type that implements MpiDatatype: f32, f64, i32, i64, u8, u32 and u64. ferrompi passes MPI the datatype of the element type and counts in elements, not bytes. MPI requires the receiver to name the type that was sent, and the libraries do not check it: an f64 received as i64 arrives as the same bytes, read as integers. Chapter 4 covers other types.

The receive slice may be longer than the message, which then fills only its first elements; it may not be shorter (When a receive fails). A rank is an i32 or a Source, and a tag an i32 or, for a receive, a Tag. MPI guarantees every tag from 0 to 32767; the largest tag above that depends on the library.

Matching

Wildcards and the status

A receive can leave its source open with Source::Any (MPI_ANY_SOURCE) and its tag open with Tag::Any (MPI_ANY_TAG). The receiver then needs to know what it got, and the Status that recv returns says: source and tag are the matched message’s, and count is the number of elements received, or None when the message is not a whole number of elements.

use ferrompi::{Mpi, Source, Tag};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    if rank == 0 {
        // Long enough for the longest message; shorter ones fill a prefix.
        let mut buf = vec![0i32; size as usize];
        for _ in 1..size {
            let status = world.recv(&mut buf, Source::Any, Tag::Any)?;
            let n = status.count.expect("a whole number of i32");
            println!("from {:?} with {:?}: {:?}", status.source, status.tag, &buf[..n]);
        }
    } else {
        // Rank r sends r copies of r, tagged 100 + r.
        world.send(&vec![rank; rank as usize], 0, 100 + rank)?;
    }
    Ok(())
}

With four processes it prints these three lines, in the order the messages reached rank 0, which can change from run to run:

from Rank(1) with Value(101): [1]
from Rank(2) with Value(102): [2, 2]
from Rank(3) with Value(103): [3, 3, 3]

Which message a receive takes

A message that arrives before a matching receive is posted waits in the receiving process’s library, in arrival order. A receive takes the oldest waiting message that matches it, or, if none does, the first matching message to arrive after it. A message no receive matches waits for as long as the process runs.

MPI guarantees one order: messages do not overtake each other. When one process sends two messages to another on the same communicator and both match a receive, the receive takes the one sent first. Nothing orders messages from different senders; they arrive in the order the network delivers them, so a receive from Source::Any can take a different message in each run. Tags are how a receiver takes messages out of order: a receive for tag 7 passes over older messages with other tags.

Sending to nobody

Source::ProcNull (MPI_PROC_NULL) is a rank that is not there. A send to it sends nothing and returns at once. A receive from it receives nothing, leaves the slice as it was, and returns at once with a status whose source is ProcNull and whose count is Some(0). Code at the edge of a domain uses it to treat a missing neighbor as one that never sends, as the halo exchange below does. Source::Any is not a destination: a send to it returns Err(Error::InvalidArgument) without calling MPI.

How a message travels

MPI says when send may return, not how the data gets across. MPICH and Open MPI both move a message by one of two protocols, chosen for each message by its size.

For a small message the library uses the eager protocol: it sends the data with the envelope right away. If the receiver has not posted a matching receive yet, its library keeps the message in a buffer of its own and copies it out when the receive comes. The sender’s send returns as soon as the data has left its slice, whether or not anyone ever receives it.

For a large message the library uses the rendezvous protocol: it sends only the envelope, waits until the receiver posts a matching receive, and then sends the data straight into the receive slice. No buffer at the receiver has to hold a large message, but the sender’s send waits for the receiver.

The size at which a library switches depends on the library, its version and the path between the two processes: shared memory within a node, or the network between nodes. Both libraries let you change it: Open MPI through MCA parameters (ompi_info --all lists the ones named eager_limit), and MPICH through its MPIR_CVAR_ environment variables. A correct program works whatever the value is. MPI calls this behavior of send the standard mode: the library may buffer the message or wait for the receive, and the program cannot choose. Send modes lists the other three.

Deadlock

A program that is correct only if send buffers is called unsafe. The most common one is an exchange in which both processes send first:

use ferrompi::Mpi;

// 32 bytes: small enough for every MPI library to send eagerly.
const N: usize = 4;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();
    let other = 1 - rank;

    let mine = vec![rank as f64; N];
    let mut theirs = vec![0.0f64; N];

    // Both processes send first and receive second.
    world.send(&mine, other, 0)?;
    world.recv(&mut theirs, other, 0)?;
    println!("rank {rank} received {} values from rank {other}", theirs.len());
    Ok(())
}

With two processes it prints:

rank 0 received 4 values from rank 1
rank 1 received 4 values from rank 0
Pitfall

This program is wrong, and it passes: the tutorial’s CI runs it and checks both lines. At 4 values each send goes eagerly and returns before the other process has posted its receive. Make N 1 << 20 and both processes block in send for good: each sends a rendezvous envelope and waits for a receive that the other process posts only after its own send returns. On one laptop with MPICH 4.2.3, 1024 values (8 KiB) went through and 2048 (16 KiB) hung. A program like this passes its tests on small inputs and hangs in production.

Three changes make the exchange safe: order the calls so that every send meets a receive, combine the send and the receive into one call, or make the calls nonblocking, which the next section covers.

Ordering the calls

Let one side receive first: even ranks send and then receive, odd ranks receive and then send. Every blocking send then has a receive waiting for it, or about to be. examples/ring.rs orders a ring of any size this way.

Send and receive in one call

sendrecv(send, dest, sendtag, recv, source, recvtag) (MPI_Sendrecv) sends one message and receives another in a single call, which behaves as if the two ran at the same time: the library posts the receive before it waits on the send, so two processes in sendrecv with each other cannot block each other. It is the call for a shift, in which every process sends to one neighbor and receives from the other:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());
    let next = (rank + 1) % size;
    let prev = (rank + size - 1) % size;

    // Move every value one step around the ring, size - 1 times, so that each
    // process sees the rank of every other process once.
    let mut passing = [rank];
    let mut sum = rank;
    for _ in 1..size {
        let mut incoming = [0i32];
        world.sendrecv(&passing, next, 0, &mut incoming, prev, 0)?;
        sum += incoming[0];
        passing = incoming;
    }
    println!("rank {rank}: the ranks sum to {sum}");
    Ok(())
}

With four processes it prints:

rank 0: the ranks sum to 6
rank 1: the ranks sum to 6
rank 2: the ranks sum to 6
rank 3: the ranks sum to 6

Nonblocking communication

isend (MPI_Isend) and irecv (MPI_Irecv) start a send or a receive and return at once with a Request. The transfer goes on while the process does other work, and the request tells when it is done. Two rules come with them from MPI: the program must neither read nor write a receive slice until its receive completes, and must not write a send slice until its send completes. Reading a send slice is allowed, since MPI 3.0. In C nothing enforces either rule, and a slice reused too early holds wrong data without any error.

Requests and scopes

ferrompi turns both rules into borrows. A nonblocking call takes the Scope that ferrompi::scope passes to its closure, and borrows its slice for the whole scope. isend borrows its slice shared, so the program can still read it but not write it; irecv borrows its slice exclusively, so the program cannot touch it. When the closure returns, scope completes every request that is still pending and only then returns itself; the borrows end there, and the slices are the program’s again. A request needs no completion call of its own.

A halo exchange

Most programs that split a domain across processes exchange halos. Here a line of twelve cells is split into four blocks of three, and each step replaces every cell by the sum of itself and its two neighbors. A cell at the edge of a block needs the edge cell of the next block, so each process keeps a copy of its neighbor’s edge cell, a ghost cell, on each side, and refreshes the ghost cells before each step:

use ferrompi::{Mpi, Source};

const CELLS: usize = 3;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    // This process owns three cells of a line, each holding its index on the
    // whole line.
    let first = rank * CELLS as i32;
    let cells: Vec<i32> = (first..first + CELLS as i32).collect();

    // The two ends of the line have no neighbor on their outer side. A send
    // to ProcNull sends nothing, and a receive from it receives nothing.
    let left = if rank > 0 { Source::Rank(rank - 1) } else { Source::ProcNull };
    let right = if rank + 1 < size { Source::Rank(rank + 1) } else { Source::ProcNull };

    // One ghost cell on each side holds a copy of the neighbor's edge cell.
    let mut ghost_left = [0i32];
    let mut ghost_right = [0i32];
    let mut next = [0i32; CELLS];

    ferrompi::scope(|s| {
        // Tag 0 travels to the right, tag 1 to the left.
        world.irecv(s, &mut ghost_left, left, 0)?;
        world.irecv(s, &mut ghost_right, right, 1)?;
        world.isend(s, &cells[CELLS - 1..], right, 0)?;
        world.isend(s, &cells[..1], left, 1)?;

        // While the edge cells travel, update the cells that need no ghost.
        for i in 1..CELLS - 1 {
            next[i] = cells[i - 1] + cells[i] + cells[i + 1];
        }
        Ok(())
    })?;

    // Every request has completed: the ghost cells are filled.
    next[0] = ghost_left[0] + cells[0] + cells[1];
    next[CELLS - 1] = cells[CELLS - 2] + cells[CELLS - 1] + ghost_right[0];
    println!("rank {rank}: {cells:?} -> {next:?}");
    Ok(())
}

With four processes it prints:

rank 0: [0, 1, 2] -> [1, 3, 6]
rank 1: [3, 4, 5] -> [9, 12, 15]
rank 2: [6, 7, 8] -> [18, 21, 24]
rank 3: [9, 10, 11] -> [27, 30, 21]

No order of the four calls can deadlock, since none of them waits. The receives are posted first all the same, a habit worth keeping: a message whose receive is already posted can go straight into the receive slice, without waiting in a library buffer. The middle cell is updated while the messages travel, which it may be because it only reads cells, and the sends borrow cells shared. The edge cells are updated after the scope, once the ghost cells are filled.

Note

Starting a transfer early lets it overlap with computation, but MPI does not promise that it will. Many libraries move data only while the process is inside an MPI call, so a transfer can sit idle through a long computation and happen at the end of the scope. Whether a transfer progresses on its own depends on the library and the network.

What the compiler rejects

Try to finish the left edge cell inside the scope: name the first receive’s request from_left, call from_left.wait()? and compute next[0] before Ok(()). The receive has completed, but the borrow lasts until the scope returns, so the program does not compile:

The other mistakes MPI forbids are rejected the same way: writing to a slice that isend is sending, dropping a slice while a request uses it, or letting a request outlive its scope. Data received in a scope is read after it; a program that needs the data sooner ends the scope there and starts another one. Chapter 11 explains why the borrow cannot end at the wait, and the rustdoc of scope lists every program it rejects.

Completing a request early

A program that needs a request completed before the scope ends, to know that a send went out or to react to receives in the order they finish, has four calls. Request::wait blocks until the request completes and returns its Status. Request::test returns at once, with Some(status) if the request has completed and None if not, for a program that polls between pieces of work. Request::wait_all completes a slice of requests, and Request::wait_any the first of them to finish, returning its index with its status. examples/nonblocking.rs uses each of them with nonblocking collectives, which chapter 3 covers.

Messages of unknown size

A receiver that does not know how long a message is can ask before it receives. probe::<T>(source, tag) (MPI_Probe) waits until a matching message has arrived and returns its Status without receiving it; status.count is the message’s length in elements of T. iprobe returns at once, with None if nothing matches yet.

A probe followed by a receive has a race when several threads receive on one communicator: another thread can receive the probed message between the two calls. mprobe (MPI_Mprobe) closes it. It removes the message it matches from matching and returns it as a Message, which only Message::mrecv can receive. It is correct with or without threads:

use ferrompi::{Mpi, Source, Tag};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());

    if rank == 0 {
        for _ in 1..size {
            // Match the next message without receiving it, and read its length.
            let (message, status) = world.mprobe::<u64>(Source::Any, Tag::Any)?;
            let len = status.count.expect("a whole number of u64");
            let mut buf = vec![0u64; len];
            message.mrecv(&mut buf)?;
            let sum: u64 = buf.iter().sum();
            println!("{len} values from {:?}, summing to {sum}", status.source);
        }
    } else {
        // Rank r sends the numbers 1 to 1000 r.
        let data: Vec<u64> = (1..=1000 * rank as u64).collect();
        world.send(&data, 0, 0)?;
    }
    Ok(())
}

With four processes it prints, in the order the messages arrive:

1000 values from Rank(1), summing to 500500
2000 values from Rank(2), summing to 2001000
3000 values from Rank(3), summing to 4501500

MPI requires every matched message to be received. Dropping a Message without calling mrecv receives the data into a scratch buffer and discards it. improbe is the form that returns at once.

Persistent requests

A program that repeats the same exchange, with the same peers, tags and buffers, can describe it once. send_init and recv_init (MPI_Send_init, MPI_Recv_init) create a PersistentRequest without starting anything. start begins one round, wait completes it, and the request can then be started again. The library can do its setup once rather than every round; how much that saves depends on the library and the network.

A persistent request owns its buffer. It takes a Vec, and buffer and buffer_mut reach it between rounds, returning an error while a round is in progress. The borrows of a scope become a check at run time, and in exchange the request needs no scope: it can live across a loop or in a struct.

use ferrompi::{Mpi, PersistentRequest};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let (rank, size) = (world.rank(), world.size());
    let next = (rank + 1) % size;
    let prev = (rank + size - 1) % size;

    // Describe the exchange once. Each request owns its buffer.
    let mut requests = [
        world.send_init(vec![0i32], next, 0)?,
        world.recv_init(vec![0i32], prev, 0)?,
    ];
    for step in 0..3 {
        requests[0].buffer_mut()?[0] = 10 * rank + step;
        PersistentRequest::start_all(&mut requests)?;
        PersistentRequest::wait_all(&mut requests)?;
        let got = requests[1].buffer()?[0];
        println!("step {step}: rank {rank} got {got} from rank {prev}");
    }
    Ok(())
}

With three processes it prints:

step 0: rank 0 got 20 from rank 2
step 1: rank 0 got 21 from rank 2
step 2: rank 0 got 22 from rank 2
step 0: rank 1 got 0 from rank 0
step 1: rank 1 got 1 from rank 0
step 2: rank 1 got 2 from rank 0
step 0: rank 2 got 10 from rank 1
step 1: rank 2 got 11 from rank 1
step 2: rank 2 got 12 from rank 1

start_all and wait_all start and complete a slice of requests together. Starting the send and the receive together is what keeps this ring from deadlocking, as with sendrecv.

Send modes

MPI has four send modes, which differ in when a send may complete. ferrompi offers the three besides the standard mode only as persistent requests.

ModeA send completes whenferrompi
Standardthe library is done with the send buffer, which may or may not mean that the receive has startedsend, isend, send_init
Synchronousthe matching receive has started ssend_init
Bufferedthe data is copied into a buffer the program attached with Mpi::buffer_attach; it never waits for the receiver bsend_init
Readyas in standard mode, but the program promises that the matching receive is already posted; breaking the promise is an error MPI need not detect rsend_init

Synchronous mode is the one to test with. It never buffers, so a program that completes with synchronous sends in place of its standard sends does not depend on any eager threshold. Exercise 2 tries it on the head-to-head exchange.

When a receive fails

A message longer than the receive slice is an error. MPI reports MPI_ERR_TRUNCATE, which ferrompi returns as Err(Error::Mpi) with class MpiErrorClass::Truncate:

use ferrompi::{Error, Mpi, MpiErrorClass};

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    match world.rank() {
        0 => {
            let mut small = [0i32; 1];
            match world.recv(&mut small, 1, 0) {
                Err(Error::Mpi { class: MpiErrorClass::Truncate, .. }) => {
                    println!("4 values do not fit in 1: the receive failed with Truncate")
                }
                other => println!("unexpected: {other:?}"),
            }
        }
        1 => world.send(&[1i32, 2, 3, 4], 0, 0)?,
        _ => {}
    }
    Ok(())
}

With two processes it prints:

4 values do not fit in 1: the receive failed with Truncate

Only the receiver sees the error; rank 1’s send succeeded. Matching the class rather than the error’s message keeps the program portable, since each library words its messages differently. When the length can vary, probe first, as above.

Other mistakes are caught before MPI is called, on the process that makes them: a negative rank or tag, or Source::Any as a destination, returns Err(Error::InvalidArgument). A rank that is not in the communicator reaches MPI, which reports it with class Rank.

Exercises

  1. Set N to 1 << 20 in the head-to-head program and run it with -n 2; stop it with Ctrl-C. Find the largest N that still completes on your machine, then make the program safe twice: once by ordering the calls by rank parity, once with sendrecv.
  2. Back at N = 4, replace the head-to-head program’s send with a synchronous send: let mut send = world.ssend_init(mine, other, 0)?; followed by send.start()?; and send.wait()?;. Run it. Why does it hang at 32 bytes now?
  3. In the any-source program, make rank 0 receive from rank 1, then 2, then 3, with Source::Rank(r). Does the order of the output still vary? Where does a message that arrives before its receive wait?
  4. Make the halo line a ring: rank 0’s left neighbor is the last rank, and the last rank’s right neighbor is rank 0. Predict what ranks 0 and 3 print with -n 4, then run it.
  5. In the mprobe program, allocate len - 1 elements. What does mrecv return?

Summary

  • A message is a slice and an envelope: source, destination, tag and communicator. A receive takes the oldest message whose envelope matches its own; the data’s length and type play no part.
  • send returns when its slice may be reused, not when the message is received. recv returns when the data is in its slice, with a Status that says what arrived.
  • Messages from one sender to one receiver on one communicator stay in order. Nothing orders messages from different senders.
  • Small messages travel eagerly, large ones by rendezvous. A program that works only because send buffered is unsafe and hangs once its messages grow; synchronous sends expose it.
  • Break a cycle of blocking sends by ordering the calls, with sendrecv, or with nonblocking calls.
  • Nonblocking calls run inside ferrompi::scope, which borrows their slices until it has completed every request, so the compiler rejects a slice touched too early.
  • Use mprobe for a message of unknown length, persistent requests for an exchange that repeats, and the class Truncate to recognize a message too long for its slice.
