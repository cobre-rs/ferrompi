Part I · Chapter 1

The MPI model

What MPI is and how an MPI program runs: the standard and the libraries that implement it, the processes a launcher starts, how MPI is initialized and finalized, and the communicators that every MPI call goes through.

By the end of the chapter you can launch a ferrompi program on any number of processes, explain the output it prints, and split its processes into smaller communicators. Before you start, on the tutorial’s contents page, says how to install MPI and build the examples.

What MPI is for

A cluster is many computers, called nodes, joined by a network. Each node has its own memory, and a process on one node cannot read the memory of another. Threads share memory, so they help only inside one node. To use more than one node, a program runs as several processes, and the processes send each other the data they need as messages.

MPI, the Message Passing Interface, is the standard interface for this. Most large scientific codes use it. It is used inside a single node too: some programs run one MPI process per core, and others run one process per node or per socket and use threads inside it (chapter 6).

A standard, not a library

MPI is a specification published by the MPI Forum, a body of vendors, laboratories and universities. It defines functions, constants and what they mean, in C and Fortran; the C++ bindings of MPI-2 were removed in MPI-3.0. It does not define an implementation: it says nothing about how a message travels, which algorithm a collective uses, or what a handle looks like in memory.

An MPI implementation is what you install. It provides:

  • a library (libmpi, libmpich) and its mpi.h header;
  • compiler wrappers (mpicc, mpifort) that add the include and link flags;
  • a launcher (mpiexec, often also installed as mpirun) that starts the processes of a job.

MPICH and Open MPI are the two main open-source implementations, and most vendor MPIs derive from one of them; chapter 7 compares them. ferrompi compiles against the mpi.h of one implementation and links its library, chosen when ferrompi is built (the compatibility guide’s Building section).

A library has two version numbers: the version of the standard it implements, and its own release number. ferrompi reports both, with Mpi::version and Mpi::library_version:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let _mpi = Mpi::init()?;
    println!("standard: {}", Mpi::version()?);
    println!("library:  {}", Mpi::library_version()?);
    Ok(())
}

With MPICH 4.2 the first line is standard: MPI 4.1, and the second starts with library: MPICH Version: and the release number, such as 4.2.3, followed by MPICH’s build details. Open MPI 4.1 and 5.0 both report MPI 3.1, although Open MPI 5 implements some MPI-4.0 features. ferrompi needs a library that implements at least MPI 3.1, and enables an MPI-4.0 feature only where the library has it; the compatibility guide lists which feature needs which library.

One program, many processes

mpiexec -n 4 ./prog starts four processes, all running the same program. This model is called SPMD: single program, multiple data. The processes share no memory. Each one has its own copy of every variable, and a value computed by one is visible to another only if it is sent there.

What tells the processes apart is their rank, an integer from 0 to n − 1 that MPI assigns. A program reads its rank and acts on it: which part of the data to work on, or whether it is the process that reads the input file.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    println!(
        "Hello from rank {} of {} on {}",
        world.rank(),
        world.size(),
        world.processor_name()?
    );
    Ok(())
}

With four processes on a machine named node01, it prints:

Hello from rank 2 of 4 on node01
Hello from rank 0 of 4 on node01
Hello from rank 3 of 4 on node01
Hello from rank 1 of 4 on node01

The order changes from run to run. Each process writes to its own standard output, and the launcher forwards each line as it arrives. A barrier before the println! does not fix the order: it synchronizes the processes, not the launcher’s forwarding. To print in rank order, send the lines to one process and print them there (chapter 3).

Launching a job

What the launcher does

mpiexec does five things:

  1. It starts the processes, on the local machine or on the hosts of a host file or of the batch system’s allocation.
  2. It tells each process its rank, the size of the job, and how to reach the launcher’s process-management service, called PMI or PMIx.
  3. It runs that service while the processes start. Inside MPI_Init, each process publishes its network address to the service and reads the addresses of the others. This step is called wire-up.
  4. It forwards standard output, standard error and signals between your terminal and the processes.
  5. It ends the job when the processes exit, and kills the remaining processes when one of them fails. How quickly it does so varies; the compatibility guide’s known issues record a case where it does not.

After wire-up the processes talk to each other directly, over shared memory or the network. The launcher carries no message data.

Build, then launch the binary

cargo build --release --example hello_world
mpiexec -n 4 target/release/examples/hello_world

mpiexec -n 4 cargo run --example hello_world also works once the build is up to date, but it starts four cargo processes, each of which checks the build before it runs the program. Build once and launch the binary.

A process started without a launcher

Run the binary on its own and MPI starts a job of one process: rank 0 of 1. The standard calls this a singleton MPI_Init, and MPICH and Open MPI support it. It is handy for a quick check, and it is how ferrompi’s one unit test that initializes MPI runs.

When every process says “rank 0 of 1”

If mpiexec -n 2 prints this:

Hello from rank 0 of 1 on node01
Hello from rank 0 of 1 on node01

each process failed to reach the launcher’s service and started as a singleton. There are two usual causes:

  • The launcher comes from a different implementation than the library the program is linked against, for example Open MPI’s mpiexec starting a program built against MPICH. Each library talks only to its own implementation’s launcher.
  • Ubuntu 24.04’s MPICH 4.2.0 package, which does this even under its own launcher; Before you start says which package to use instead.

Two commands tell you which implementation each side is:

mpiexec --version
ldd target/release/examples/hello_world | grep -i mpi

The first names the launcher’s implementation; the second shows the MPI library the program loads: libmpi.so.12 for an MPICH built from source, libmpich.so.12 for the Debian and Ubuntu MPICH packages, and libmpi.so.40 for Open MPI. Mpi::library_version() reports the same from inside the program.

Initializing and finalizing MPI

The standard sets three rules:

  • MPI_Init (or MPI_Init_thread) runs once per process, before any other MPI call. A few queries, such as the version, are allowed before it.
  • MPI_Finalize runs once, after the process’s last MPI call. Every process calls it, and a process completes all its communication before calling it.
  • After MPI_Finalize, MPI cannot be initialized again.

ferrompi turns these rules into a value. Mpi::init() initializes MPI and returns an Mpi handle, and dropping the handle finalizes MPI. There is one handle per process:

  • While the handle exists, a second Mpi::init() returns Err(Error::AlreadyInitialized).
  • After the handle is dropped, Mpi::init() returns Err(Error::Finalized), and so does every call that would reach MPI through a communicator or another handle, without calling MPI.

Mpi::init() requests the Single thread level; Mpi::init_thread requests another one (chapter 6). Mpi is neither Send nor Sync, so it stays on the thread that initialized MPI.

Pitfall

Because dropping the handle finalizes MPI, keep it in a named variable for as long as the program uses MPI. let _ = Mpi::init()?; finalizes at once: _ binds nothing, so the handle is dropped at the end of that statement. Write let _mpi = Mpi::init()?; when you need the handle only to keep MPI initialized.

A Communicator does not borrow the Mpi handle, so one struct can own both. Rust drops a struct’s fields in declaration order, so declare the Mpi field last; every other handle in the struct is then freed while MPI is still initialized:

use ferrompi::{Communicator, Mpi};

/// Fields drop in declaration order: `comm` is freed while MPI is still
/// initialized, then `mpi` finalizes MPI.
struct Context {
    comm: Communicator,
    mpi: Mpi,
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let comm = mpi.world().duplicate()?;
    let ctx = Context { comm, mpi };
    println!(
        "rank {} of {} at thread level {:?}",
        ctx.comm.rank(),
        ctx.comm.size(),
        ctx.mpi.thread_level()
    );
    Ok(())
}

With two processes it prints:

rank 0 of 2 at thread level Single
rank 1 of 2 at thread level Single

The order matters most for RMA windows (chapter 5): if a window is still alive when the Mpi handle is dropped, ferrompi skips MPI_Finalize and prints a warning. A communicator, group or datatype still alive at that point is freed by ferrompi’s own finalization instead, and its later drop makes no MPI call. Chapter 11 lists every case in which MPI_Finalize is skipped; the rustdoc of Mpi has the complete rule.

Ranks and the world communicator

mpi.world() returns MPI_COMM_WORLD, the communicator of every process the launcher started. It makes no MPI call: ferrompi reads the rank and the size once, when MPI is initialized. rank() and size() on any Communicator also return values read when that communicator was created.

A rank belongs to a communicator, not to a process. The same process usually has different ranks in different communicators, so “rank 0” always means rank 0 of some communicator.

Communicators

A communicator is a group of processes plus a context, a private channel that the MPI library assigns. A message sent on one communicator can be received only on that same communicator, never on another one, even one with the same processes and a message with the same tag.

The context is what lets libraries share a program safely. If a program and a library it calls both send on the world communicator with tag 0, the program can receive a message the library meant for itself. A library that works on its own duplicate of the communicator has its own context and cannot be confused with its caller. That is what duplicate() (MPI_Comm_dup) is for: each component that communicates internally gets its own duplicate.

Creating a communicator is collective

A call that creates a communicator is collective over its parent: every process of the parent makes the same call, in the same order relative to the other collective calls on the parent. A process that skips it leaves the others waiting inside the call, and the job hangs. This holds for duplicate, split, split_type, split_shared and create; create_group is collective only over the processes of the group.

Dropping a Communicator frees it with MPI_Comm_free, which the standard also defines as collective: drop each communicator on every one of its processes, just as you created it on every one.

Splitting by color and key

split(color, key) puts the processes that pass the same color into the same new communicator, ordered by key; processes with equal keys keep their order in the parent. A process that passes None joins no communicator and gets None back. A negative color returns Err(Error::InvalidArgument) on the process that passed it. That check is local, so the other processes still enter the split and can block waiting for this one.

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    let rank = world.rank();

    // Even ranks take color 0 and odd ranks color 1. Keying on the world rank
    // keeps the world's order inside each half.
    if let Some(half) = world.split(Some(rank % 2), rank)? {
        println!(
            "world rank {rank} is rank {} of {} in its half",
            half.rank(),
            half.size()
        );
    }
    Ok(())
}

With five processes it prints:

world rank 0 is rank 0 of 3 in its half
world rank 1 is rank 0 of 2 in its half
world rank 2 is rank 1 of 3 in its half
world rank 3 is rank 1 of 2 in its half
world rank 4 is rank 2 of 3 in its half

examples/comm_split.rs is the same split, followed by a reduction inside each half.

One communicator per node

split_shared() (MPI_Comm_split_type with MPI_COMM_TYPE_SHARED) groups the processes that can share memory, which in practice means the processes on one node. It is the starting point for node-shared memory windows (chapter 5) and for a two-level layout in which one process per node, the node leader, talks to the other nodes:

use ferrompi::Mpi;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // The processes on this node.
    let node = world.split_shared()?;

    // One leader per node: local rank 0 joins, every other process opts out.
    let color = if node.rank() == 0 { Some(0) } else { None };
    match world.split(color, world.rank())? {
        Some(leaders) => println!(
            "world rank {}: leader {} of {}, with {} processes on its node",
            world.rank(),
            leaders.rank(),
            leaders.size(),
            node.size()
        ),
        None => println!(
            "world rank {}: local rank {} on its node",
            world.rank(),
            node.rank()
        ),
    }
    Ok(())
}

Groups

A group is an ordered set of processes without a context. world.group() returns a communicator’s group, and Group::include and Group::exclude build smaller groups from it. Group operations are local and make no communication. Turning a group into a communicator is collective: create over the parent communicator, create_group over the processes of the group. Most programs need only split.

When something goes wrong

MPI’s default reaction to an error is to abort the whole job. ferrompi installs MPI’s MPI_ERRORS_RETURN handler instead, so a failing call returns Err. The exception is an error inside MPI_Init itself, which usually aborts the process before Mpi::init() can return.

An Err, a panic or an early return on one process is not reported to the others. They carry on until they need that process, usually at their next collective call, and wait there. Whether the launcher then ends the job depends on how the process exited and on the launcher, so give every batch job a time limit.

To end the whole job on purpose, call world.abort(code), which wraps MPI_Abort and never returns. MPI makes a best effort to end every process of the communicator; if MPI_Abort returns anyway, ferrompi ends the calling process with std::process::abort. Use it when one process meets an error the others cannot recover from. Returning Err from main on that one process does not stop the others.

Exercises

  1. Build examples/hello_world.rs and run it with -n 1, -n 2 and -n 4, then run the binary without mpiexec. A run with n processes prints n different ranks; if yours does not, read When every process says “rank 0 of 1”.
  2. Run the version program and compare its output with mpiexec --version. Which standard version does your library implement, and does ferrompi enable persistent collectives on it? The compatibility guide has the answer.
  3. In the even/odd split, change the key to world.size() - rank. Predict each process’s rank in its half with five processes, then run it.
  4. Run the node-leader program with -n 4 on one machine. How many leaders do you expect, and what node size does each process report?
  5. Make rank 0 skip the split: call world.split(..) only when rank != 0, and run with -n 2. The job hangs, because the other process waits inside the split for a process that never calls it. Stop it with Ctrl-C. This is what a mismatched collective call looks like.

Summary

  • MPI is a standard. MPICH and Open MPI implement it, and ferrompi builds on one of them, chosen when ferrompi is built.
  • A job is n processes running one program. They share no memory, and each one is identified by its rank.
  • The launcher starts the processes and wires them up, then carries no data. The launcher and the library must come from the same implementation.
  • Mpi::init() returns the one Mpi handle of the process, and dropping it finalizes MPI. Keep it alive for as long as you use MPI, and declare it last in a struct that owns other handles.
  • All communication happens on a communicator, and contexts keep communicators apart. Creating or freeing a communicator is collective.
  • An error stays on the process where it happened. A process that stops taking part makes the others hang; abort ends the whole job.
