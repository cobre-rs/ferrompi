Part II · Chapter 10

The C shim

csrc/ferrompi.c is the only part of ferrompi that includes mpi.h. Rust calls its functions with integers and addresses, and it calls MPI with MPI’s own types. This chapter reads it: the interface it offers Rust, the tables where it keeps MPI’s handles, how threads share them, what it does when one is full, and how it tears everything down at the end.

By the end of the chapter you can read any function in the C layer, say which table a Rust value holds a slot in and what happens when that table is full, call the C layer from a C program to test it alone, and name the rules a change to it has to keep.

The excerpts of ferrompi’s source below name the file they come from. A comment // … or /* ... */ marks lines left out. CI checks that every excerpt still matches its file.

Why a C layer

The usual way to call a C library from Rust is bindgen, which reads the library’s header at build time and writes the matching Rust declarations. ferrompi does not use it for MPI. ADR 0001 gives the reasons:

  • The handle types differ. Generated from MPICH’s header, MPI_Comm is an i32; from Open MPI’s, it is a pointer (chapter 7). Every Rust type that held one would change with the library.
  • Functions come and go with the version. An MPI 3.1 header has no MPI_Send_c. Rust code calling it would need the build script to detect the version and a cfg at every call; the C layer needs one #if MPI_VERSION >= 4 where it calls.
  • Callbacks need distinct C functions. MPI calls a user-defined operation through a function pointer with no room for user data, so each live operation needs a function of its own. With bindgen these would still have to be written in C.
  • The unsafe surface stays small. Rust calls only the functions in csrc/ferrompi.h, which take fixed-width integers and addresses, through the declarations in src/ffi.rs.

The ADR also rejects building on a C++ MPI library such as Boost.MPI: a large dependency that leaves the handle and version problems where they were. The cost of the choice is code: csrc/ferrompi.c is about 4,900 lines, every MPI call ferrompi offers is written twice, once in C and once as its Rust declaration, and a change at the boundary needs a reviewer who reads both languages.

The contract

The header opens with the rules every function in it keeps:

/**
 * ferrompi.h - the C interface between ferrompi's Rust code and MPI. Rust
 * calls only these functions. MPI objects are held in fixed-size C handle
 * tables and cross the FFI as integer handles. Every status-returning
 * function returns an MPI error code (MPI_SUCCESS = 0) or one of the
 * negative ferrompi sentinels below. MPI 4.0 operations are compiled only
 * where the library provides them. Fixed-width types are used at the FFI
 * boundary.
 */

Everything that crosses the boundary is one of a few kinds of value:

a communicator, group, datatype, window or user operationint32_t handle0 is MPI_COMM_WORLD

an element countint64_tabove INT_MAX, a _c call
an element typeint32_t tag1 is f64, MPI_DOUBLE
a reductionint32_t code0 is MPI_SUM; 64 and up, a user operation

One struct, written twice

A receive’s status comes back in a struct, the only one that crosses. The header declares it:

typedef struct {
    int32_t source;
    int32_t tag;
    int64_t count;
    int32_t error;
} ferrompi_status;

and src/ffi.rs declares it again, with #[repr(C)] so that Rust lays it out as C does:

pub struct FerrompiStatus {

    pub tag: int32_t,

Values with a mirror

Tags, operation codes and ferrompi’s own error codes are numbers that each side writes down. Nothing compiles one side against the other. Each carries a comment that names its mirror, on one side or on both:

/* Op codes at or above FERROMPI_OP_USER_BASE name the user op in slot
 * (code - FERROMPI_OP_USER_BASE); smaller codes are the predefined ops get_op
 * switches on. MUST stay in sync with the mirrored const in src/op.rs. */
#define FERROMPI_OP_USER_BASE 64
/// Op codes at or above this name the user op in slot `code - USER_OP_CODE_BASE`;
/// smaller codes are the predefined ops `get_op` switches on. Mirrors
/// `FERROMPI_OP_USER_BASE` in csrc/ferrompi.h; keep in sync.
pub(crate) const USER_OP_CODE_BASE: i32 = 64;

A change to one means a change to the other, in the same commit.

The one handle passed by value

A matched message is the exception to the tables below. Its MPI_Message crosses as it is, copied into an int64_t:

// An MPI_Message crosses to Rust by value in an int64_t: an integer handle in
// MPICH, a pointer in Open MPI and in the MPI 5.0 ABI.
_Static_assert(sizeof(MPI_Message) <= sizeof(int64_t),
               "MPI_Message must fit in the int64_t that carries it");

static int64_t message_to_i64(MPI_Message m) {
    int64_t v = 0;
    memcpy(&v, &m, sizeof m);
    return v;
}

The _Static_assert stops the build against a library whose MPI_Message is larger. ADR 0006 makes storing every handle this way, instead of in the tables, the condition for testing ferrompi at run time against the MPI 5.0 ABI.

Six tables

Every other MPI object that outlives a call is kept in a table in csrc/ferrompi.c: an array of MPI handles, an array of flags that say which slots are in use, and a hint of where to look for a free one. The handle Rust holds is the slot’s index:

The six tables differ in size, and in the slot each keeps for itself:

TableSlotsReservedRust values that hold a slot
comm_table256slot 0, MPI_COMM_WORLDCommunicator
group_table64handle 0 is MPI_GROUP_EMPTY, and slot 0 is never usedGroup
datatype_table64CustomDatatype
win_table256Win

request_table16,384Request, PersistentRequest

This program makes communicators, groups and user operations until each table refuses one, keeping every value alive so that each holds its slot:

use ferrompi::{Mpi, UserOp};

/// Calls `make` until it fails, keeping every value it returns. Returns the
/// values and a line naming how many there were and the error that stopped
/// the loop.
fn fill<T>(what: &str, mut make: impl FnMut() -> ferrompi::Result<T>) -> (Vec<T>, String) {
    let mut kept = Vec::new();
    loop {
        match make() {
            Ok(value) => kept.push(value),
            Err(err) => {
                let line = format!("{what}: {} made, then: {err}", kept.len());
                return (kept, line);
            }
        }
    }
}

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();

    // Every value made stays alive, so each one holds a slot.
    let (comms, comm_line) = fill("communicators", || world.duplicate());
    let (groups, group_line) = fill("groups", || world.group());
    let (ops, op_line) = fill("operations", || {
        UserOp::<f64>::new(|a, b| {
            for (x, y) in a.iter().zip(b) {
                *y += x;
            }
        })
    });

    // Dropping a value frees its slot.
    drop((comms, groups, ops));
    let again = world.duplicate()?;

    if world.rank() == 0 {
        println!("{comm_line}");
        println!("{group_line}");
        println!("{op_line}");
        println!("after the drops, a duplicate of size {}", again.size());
    }
    Ok(())
}
communicators: 255 made, then: ferrompi communicator table is full
groups: 63 made, then: ferrompi group table is full
operations: 16 made, then: ferrompi operation table is full
after the drops, a duplicate of size 2

A program gets 255 communicators besides world, since MPI_COMM_WORLD takes slot 0, and 63 groups. The sizes are constants at the top of the file (chapter 9 quoted them), so a program that needs more changes them and rebuilds ferrompi. The tables are fixed so that the C layer never allocates for them, and a full one returns Error::ResourceExhausted instead of growing.

Claiming and freeing a slot

Five of the tables work alike; alloc_comm shows how a slot is claimed:

static int32_t alloc_comm(MPI_Comm comm) {
    int hint = atomic_load_explicit(&next_comm_hint, memory_order_relaxed);
    for (int i = 0; i < MAX_COMMS; i++) {
        int idx = (hint + i) % MAX_COMMS;
        if (idx == 0) continue;  // slot 0 is MPI_COMM_WORLD; never reuse
        int expected = 0;
        if (atomic_compare_exchange_strong_explicit(
                &comm_used[idx], &expected, 1,
                memory_order_acq_rel, memory_order_relaxed)) {
            comm_table[idx] = comm;
            atomic_store_explicit(&next_comm_hint,
                (idx + 1) % MAX_COMMS, memory_order_relaxed);
            return (int32_t)idx;
        }
    }
    return -1;  // No space
}

The scan starts at the hint and wraps around the table once, skipping slot 0. atomic_compare_exchange_strong_explicit changes a flag from 0 to 1 only if it is still 0, so of two threads that reach the same free slot, one claims it and the other moves on. Then the slot gets its MPI_Comm, and the hint moves past it. A return of −1 becomes FERROMPI_ERR_COMMS_FULL in the caller.

Freeing runs the other way:

int ferrompi_comm_free(int32_t comm_handle) {
    if (comm_handle == 0) {
        return MPI_ERR_COMM;  // Cannot free COMM_WORLD
    }
    if (comm_handle < 0 || comm_handle >= MAX_COMMS) {
        return MPI_ERR_COMM;
    }
    if (!atomic_load_explicit(&comm_used[comm_handle], memory_order_acquire)) {
        return MPI_SUCCESS;  // Already freed
    }
    MPI_Comm comm = comm_table[comm_handle];
    int ret = MPI_Comm_free(&comm);
    comm_table[comm_handle] = MPI_COMM_NULL;
    atomic_store_explicit(&comm_used[comm_handle], 0, memory_order_release);
    return ret;
}

Handle 0 is refused, so MPI_COMM_WORLD is never freed. A handle whose slot is free already returns success, and a live one is freed in MPI, set to MPI_COMM_NULL, and only then marked free, whatever MPI_Comm_free returned. get_comm, quoted in chapter 9, gives MPI_COMM_NULL for a free slot, and MPI then fails the call with class Comm.

Groups, datatypes, windows and user operations have the same three functions, under their own names. The group table differs in one place: handle 0 stands for MPI_GROUP_EMPTY, a predefined group the program must not free, which get_group returns without looking at a slot.

The request table

Requests are made and freed far more often than anything else: every nonblocking call makes one and every completion frees it. Their table has 16,384 slots and keeps them apart from the other five in two ways.

Its flags are bits. Each 64-bit word of request_bits holds the flags of 64 slots, and alloc_request finds a free one with a single instruction:

static int64_t alloc_request(MPI_Request req, int persistent) {
    unsigned hint = (unsigned)atomic_load_explicit(&next_request_hint,
                                                    memory_order_relaxed);
    for (int w = 0; w < REQUEST_BITS_WORDS; w++) {
        unsigned widx = (hint + (unsigned)w) % REQUEST_BITS_WORDS;
        uint64_t cur = atomic_load_explicit(&request_bits[widx],
                                            memory_order_relaxed);
        while (cur != UINT64_MAX) {
            int bit = __builtin_ctzll(~cur);  // lowest free slot in this word
            uint64_t mask = (uint64_t)1 << bit;
            uint64_t old = atomic_fetch_or_explicit(&request_bits[widx], mask,
                                                    memory_order_acq_rel);
            if ((old & mask) == 0) {
                int64_t idx = (int64_t)widx * 64 + bit;
                request_table[idx] = req;
                request_state[idx] = persistent ? REQUEST_PERSISTENT : 0;
                request_dtype[idx] = MPI_DATATYPE_NULL;
                /* ... */
                uint32_t gen = atomic_load_explicit(&request_gen[idx],
                                                    memory_order_relaxed);
                /* ... */
                return ((int64_t)gen << 32) | idx;
            }
            cur = old;  // lost the race for that bit; retry the next free one
        }
    }
    return -1;  /* No space */
}

__builtin_ctzll(~cur) counts the trailing zeros of the word’s complement, which is the position of the lowest 0 bit: the first free slot in the word. atomic_fetch_or_explicit sets the bit and returns the word as it was before. If the bit was already set, another thread took the slot in between, and the loop tries the next free bit.

And its handles carry a generation. The return value puts the slot in the low 32 bits and, above them, the slot’s count of past frees:

request_slot does the checking:

static int64_t request_slot(int64_t handle) {
    if (handle < 0) {
        return -1;
    }
    uint64_t slot = (uint64_t)handle & 0xffffffffu;
    if (slot >= (uint64_t)MAX_REQUESTS) {
        return -1;
    }
    unsigned widx = (unsigned)(slot / 64);
    uint64_t mask = (uint64_t)1 << (slot % 64);
    if ((atomic_load_explicit(&request_bits[widx], memory_order_acquire)
            & mask) == 0) {
        return -1;
    }
    /* ... */
    uint32_t gen = atomic_load_explicit(&request_gen[slot], memory_order_relaxed);
    if (gen != (uint32_t)((uint64_t)handle >> 32)) {
        return -1;
    }
    return (int64_t)slot;
}

Without the generation, a handle kept after its request completed would name whatever request took the slot next, and a wait on it would complete someone else’s request. The Rust side never passes a completed request’s handle: it marks the request and passes −1 in its place. The generation makes the C layer refuse one that reaches it anyway. It was added after that mistake had happened; examples/test_request_aba.rs is the regression test.

Calling the C layer from C

Request handles never reach your program, but the C layer can be called without Rust. The build leaves it in a static library, libferrompi.a, which a C program can link. This one makes three rounds of a message to itself and prints each handle, then waits on round 1’s receive again:

/* Calls ferrompi's C layer with no Rust in the program. */
#include <stdio.h>
#include <stdlib.h>
#include "ferrompi.h"

/* The two functions the C layer calls back into Rust. This program makes no
 * user-defined operation, so neither is ever called. */
void rust_user_op_invoke(int32_t slot, void* in, void* inout, int len) {
    (void)slot; (void)in; (void)inout; (void)len;
    abort();
}
void ferrompi_op_drop_closure(int32_t slot) { (void)slot; }

static void show(const char* what, int64_t h) {
    printf("  %s handle 0x%09llx: slot %lld, generation %lld\n", what,
           (unsigned long long)h, (long long)(h & 0xffffffff), (long long)(h >> 32));
}

int main(void) {
    int provided;
    ferrompi_init_thread(0, &provided);
    int64_t first_recv = -1;
    for (int round = 1; round <= 3; round++) {
        int32_t out = round, in = 0;
        int64_t recv, send;
        /* A message to this process itself: datatype tag 2 is i32, comm 0 is
         * MPI_COMM_WORLD. */
        ferrompi_irecv(&in, 1, 2, 0, 0, 0, &recv);
        ferrompi_isend(&out, 1, 2, 0, 0, 0, &send);
        printf("round %d\n", round);
        show("receive", recv);
        show("send   ", send);
        ferrompi_wait(recv, NULL);
        ferrompi_wait(send, NULL);
        if (round == 1) first_recv = recv;
    }

    int ret = ferrompi_wait(first_recv, NULL);
    int32_t cls, len;
    char msg[512];
    ferrompi_error_info(ret, &cls, msg, &len);
    printf("wait on round 1's receive handle: %s\n", msg);
    return ferrompi_finalize();
}

Each round takes slots 0 and 1 again, under a new generation, and the stale handle gets MPI_ERR_REQUEST, whose message is MPICH’s. Nothing between the program and the C layer checks the thread or the lifecycle: the guard is Rust. The two stub functions stand in for the Rust functions the C layer calls back, which a program without user operations never reaches. A program like this is the quickest way to try a change to the C layer on its own.

Threads and the tables

At ThreadLevel::Multiple, any thread can call into the C layer at any time (chapter 6), and every nonblocking call claims a slot. The tables take no lock for that. Each operation on a slot uses one atomic access, with the ordering that makes the others safe:

StepAtomic accessOrderingWhat it guarantees
claim a slotcompare and swap the flag, or fetch_or the bitacquire and releaseone thread wins the slot, and sees everything the thread that freed it last wrote
look up a handleload the flag or the bitacquirea lookup that comes after a free sees the slot free, and for a request the new generation
free a slotstore the flag, or fetch_and the bitreleasethe null handle, and for a request the new generation, are written before the slot looks free
move the hintload or storerelaxednothing: a stale hint only makes the scan longer

free_request shows the order of a free: the slot first, then the generation, then the bit, with release:

static void free_request(int64_t handle) {
    int64_t slot = request_slot(handle);
    if (slot < 0) {
        return;
    }
    request_table[slot] = MPI_REQUEST_NULL;
    /* ... */
    uint32_t gen = atomic_load_explicit(&request_gen[slot], memory_order_relaxed);
    atomic_store_explicit(&request_gen[slot], (gen + 1) & REQUEST_GEN_MASK,
                          memory_order_relaxed);
    unsigned widx = (unsigned)(slot / 64);
    uint64_t mask = (uint64_t)1 << (slot % 64);
    atomic_fetch_and_explicit(&request_bits[widx], ~mask,
                              memory_order_release);
}

One ordering the tables do not give. A slot’s MPI handle is written after the claim, so a thread that receives a ferrompi handle from another needs the two threads ordered by something else. In safe Rust it always is: a value reaches another thread only through something that orders the two, such as a channel, a mutex, or the start or join of a thread. The comment above alloc_comm discusses this, and ADR 0002 compares the choice with a mutex, which would put every wait and test behind one lock, and with a lock-free free list, whose correctness is harder to check by reading.

This program runs four threads in each of two processes. Thread t of one process exchanges a thousand messages with thread t of the other, under tag t, so the request table sees eight threads claiming and freeing slots at once:

use ferrompi::{Error, Mpi, ThreadLevel};

const THREADS: i32 = 4;
const ROUNDS: u32 = 1000;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init_thread(ThreadLevel::Multiple)?;
    if mpi.thread_level() < ThreadLevel::Multiple {
        return Err(Error::Internal("this MPI does not grant Multiple".into()));
    }
    let world = mpi.world();
    let peer = 1 - world.rank();

    // Thread t of each process exchanges with thread t of the other, under
    // tag t. Every round claims two request slots and frees them, on four
    // threads at once.
    let matched = std::thread::scope(|threads| {
        let workers: Vec<_> = (0..THREADS)
            .map(|t| {
                let world = &world;
                threads.spawn(move || -> ferrompi::Result<u32> {
                    let mut matched = 0;
                    for round in 0..ROUNDS {
                        let out = [t as u32 * ROUNDS + round];
                        let mut back = [0u32];
                        ferrompi::scope(|s| {
                            let recv = world.irecv(s, &mut back, peer, t)?;
                            world.isend(s, &out, peer, t)?;
                            recv.wait()?;
                            Ok(())
                        })?;
                        if back == out {
                            matched += 1;
                        }
                    }
                    Ok(matched)
                })
            })
            .collect();
        workers
            .into_iter()
            .map(|w| w.join().expect("a worker panicked"))
            .sum::<ferrompi::Result<u32>>()
    })?;

    println!(
        "rank {}: {THREADS} threads, {matched} of {} exchanges matched",
        world.rank(),
        THREADS as u32 * ROUNDS
    );
    Ok(())
}
rank 0: 4 threads, 4000 of 4000 exchanges matched
rank 1: 4 threads, 4000 of 4000 exchanges matched

Nothing in the program locks anything. The repository’s test_request_table_concurrency and test_comm_table_concurrency examples do the same with more threads, in every CI test job.

The one lock

The C layer has one mutex, and the tables do not use it. It is for MPI’s group calls. MPICH 4.2 builds a group’s ordered list of members the first time a call needs it, and Open MPI 4.1 fills in a group’s entries in place, without a lock in either, so two threads calling them on the same group race inside the library. Every such call is written through a macro:

static pthread_mutex_t group_mutex = PTHREAD_MUTEX_INITIALIZER;
static int group_calls_overlap;

#define GROUP_CALL(ret, call)                                      \
    do {                                                           \
        if (group_calls_overlap) pthread_mutex_lock(&group_mutex); \
        (ret) = (call);                                            \
        if (group_calls_overlap) pthread_mutex_unlock(&group_mutex); \
    } while (0)

group_calls_overlap is set at init from the thread level MPI granted: true at Serialized and Multiple, where two threads can be in a group call at once. Below that, the guard admits one thread, and the macro takes no lock. The lock is held for one local group call at a time, never across a collective.

When a table is full

By the time the C layer learns a table is full, MPI has usually done its part. The object exists, and the C layer has to decide what to do with an object it cannot hand back. For a nonblocking call, the operation is already running against your buffer:

    if (ret == MPI_SUCCESS) {
        *request_handle = alloc_request(req, 0);
        if (*request_handle < 0) {
            complete_unregistered_request(&req);
            return FERROMPI_ERR_REQUESTS_FULL;
        }
    }

with complete_unregistered_request:

static void complete_unregistered_request(MPI_Request* req) {
    abort_if_pending_after_failure(MPI_Wait(req, MPI_STATUS_IGNORE));
}

It waits. The comment above it in the source gives the reasons: freeing the request would let the transfer go on against a buffer Rust is about to give back, and cancelling is not allowed for every kind of request, which MPI_Wait is. So the call returns the error only after the operation is done. This program sends one message more than the table holds requests, to a process that receives them all:

use ferrompi::{Error, Mpi};

/// The request table's size, MAX_REQUESTS in csrc/ferrompi.c.
const SLOTS: u32 = 16384;

fn main() -> ferrompi::Result<()> {
    let mpi = Mpi::init()?;
    let world = mpi.world();
    if world.size() != 2 {
        return Err(Error::Internal("run with -n 2".into()));
    }
    // One value more than the table holds requests.
    let values: Vec<u32> = (0..=SLOTS).collect();

    if world.rank() == 0 {
        let mut registered = 0;
        let refused = ferrompi::scope(|s| {
            for v in &values {
                match world.isend(s, std::slice::from_ref(v), 1, 0) {
                    Ok(_) => registered += 1,
                    Err(err) => return Ok(Some((*v, err))),
                }
            }
            Ok(None)
        })?;
        println!("rank 0: {registered} sends registered");
        if let Some((v, err)) = refused {
            println!("rank 0: the send of {v} returned: {err}");
        }
    } else {
        let mut count = 0;
        let mut last = [0u32];
        for _ in &values {
            world.recv(&mut last, 0, 0)?;
            count += 1;
        }
        println!(
            "rank 1: {count} messages received, the last holding {}",
            last[0]
        );
    }
    Ok(())
}
rank 0: 16384 sends registered
rank 0: the send of 16384 returned: ferrompi request table is full
rank 1: 16385 messages received, the last holding 16384

The send that returned ResourceExhausted was delivered. An error from a nonblocking call on a full table means the call did not give you a request; it does not mean the operation did not happen. A receive in its place would have waited for its message before returning the error.

A communicator gets the opposite treatment:

/* Hand a communicator that MPI returned to Rust: -1 for MPI_COMM_NULL (this
 * process is not in it), otherwise a table slot, after MPI_ERRORS_RETURN is
 * installed on it. When that cannot be installed, or the table is full, the
 * error is returned without freeing the communicator: MPI created it on every
 * rank that belongs to it, MPI_Comm_free is collective over those ranks, and
 * freeing it on this rank alone can hang or mismatch collectives. It stays
 * allocated until MPI_Finalize. A full table leaves -1 in *out_h; a failed
 * install leaves *out_h alone. */
static int store_comm(MPI_Comm comm, int32_t* out_h) {
    if (comm == MPI_COMM_NULL) {
        *out_h = -1;
        return MPI_SUCCESS;
    }
    int eh_ret = install_errors_return(comm);
    if (eh_ret != MPI_SUCCESS) return eh_ret;
    *out_h = alloc_comm(comm);
    if (*out_h < 0) return FERROMPI_ERR_COMMS_FULL;
    return MPI_SUCCESS;
}

Freeing it is a collective call, and only this process has failed, so the C layer leaves it allocated. A group is local to the process, so store_group frees it:

static int store_group(MPI_Group group, int32_t* out_h) {
    if (group == MPI_GROUP_EMPTY) {
        *out_h = 0;
        return MPI_SUCCESS;
    }
    *out_h = alloc_group(group);
    if (*out_h < 0) {
        MPI_Group_free(&group);
        return FERROMPI_ERR_GROUPS_FULL;
    }
    return MPI_SUCCESS;
}

For each kind of object:

Table full whenThe C layerLeft behind
a nonblocking call startswaits for the operationnothing; the operation has completed
a persistent request is madefrees the inactive requestnothing
a communicator is madeleaves itthe communicator, until MPI_Finalize
a window is madeleaves itthe window and its memory; Mpi then skips MPI_Finalize
a group is madefrees itnothing
a datatype is madefrees itnothing
a user operation is madeclaims the slot first, so stops before MPI_Op_createnothing

The communicator and window rows are the ones to plan for. A process whose table had room holds the new object, and a collective call on it cannot complete without this process. The Error::ResourceExhausted documentation says the same.

Translating values

Most of the C layer’s lines turn ferrompi’s integers into MPI’s values and back. Chapter 9 showed the switches for the datatype tag and the operation code; the thread level is one more:

int ferrompi_init_thread(int required, int* provided) {
    init_tables();
    int mpi_required;
    switch (required) {
        case 0: mpi_required = MPI_THREAD_SINGLE; break;
        case 1: mpi_required = MPI_THREAD_FUNNELED; break;
        case 2: mpi_required = MPI_THREAD_SERIALIZED; break;
        case 3: mpi_required = MPI_THREAD_MULTIPLE; break;
        default: mpi_required = MPI_THREAD_SINGLE; break;
    }

Rust passes the position of the level in ThreadLevel, 0 to 3, and gets the granted level back the same way. MPI orders the four constants; their values are the library’s.

MPI_UNDEFINED is another value the standard does not fix. The C layer turns it into −1 on the way out, as the count of a status and a rank that translate_ranks cannot find, and −1 into it on the way in, as the colour of a split:

int ferrompi_comm_split(int32_t comm_handle, int32_t color, int32_t key, int32_t* newcomm_handle) {
    MPI_Comm comm = get_comm(comm_handle);
    int mpi_color = (color == -1) ? MPI_UNDEFINED : color;
    MPI_Comm newcomm;
    int ret = MPI_Comm_split(comm, mpi_color, key, &newcomm);
    if (ret != MPI_SUCCESS) return ret;
    return store_comm(newcomm, newcomm_handle);
}

Rust turns −1 into None, so world.split(None, 0) opts out and returns None.

Some translations exist only where they have been checked. Two of the paired types for MaxLoc and MinLoc have a layout that depends on the platform, and the C layer offers them only where the layout matches the Rust structs:

// MPI_LONG_INT / MPI_LONG_DOUBLE_INT are exposed only where their C layout is
// verified against the Rust LongInt / LongDoubleInt structs.
#if defined(__linux__) && (defined(__x86_64__) || defined(__aarch64__) || (defined(__powerpc64__) && __BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__))
#define FERROMPI_LONG_PAIRS_VERIFIED 1
_Static_assert(sizeof(struct { long v; int i; }) == 16 &&
               _Alignof(struct { long v; int i; }) == 8,
               "MPI_LONG_INT pair layout differs from the Rust LongInt");
_Static_assert(sizeof(struct { long double v; int i; }) == 32 &&
               _Alignof(struct { long double v; int i; }) == 16,
               "MPI_LONG_DOUBLE_INT pair layout differs from the Rust LongDoubleInt");
#endif

The same platform test enables LongInt and LongDoubleInt on the Rust side. Every other case of the switches is compiled everywhere, including the operation codes only the rma feature sends: the C layer accepts any value a Rust enum can hold, whatever features are on.

Sixteen trampolines

A user-defined operation is a Rust closure, and MPI calls it through a plain C function pointer that receives the two buffers, the length and the datatype: no pointer to the closure. The C layer gives each of the sixteen slots of op_table a function of its own, with the slot number built in:

#define FERROMPI_DEFINE_OP_TRAMPOLINE(N)                              \
static void ferrompi_user_op_trampoline_##N(                          \
    void* invec, void* inoutvec, int* len, MPI_Datatype* dt) {        \
    (void)dt;                                                         \
    rust_user_op_invoke(N, invec, inoutvec, *len);                    \
}

FERROMPI_DEFINE_OP_TRAMPOLINE(0)
FERROMPI_DEFINE_OP_TRAMPOLINE(1)
/* ... */
FERROMPI_DEFINE_OP_TRAMPOLINE(14)
FERROMPI_DEFINE_OP_TRAMPOLINE(15)

MPI_Op_create gets the function of the slot the operation claimed, and the function calls rust_user_op_invoke, in src/op.rs, which finds the closure registered for that slot. The operation code Rust passes in a reduction is 64 plus the slot. Freeing keeps the closure alive for as long as MPI can call it:

int ferrompi_op_free(int32_t handle) {
    if (handle < 0 || handle >= MAX_OPS) return MPI_ERR_ARG;
    if (!atomic_load_explicit(&op_used[handle], memory_order_acquire)) return MPI_SUCCESS;  /* already freed */
    /* ... */
    MPI_Op tmp = atomic_load_explicit(&op_table[handle], memory_order_acquire);
    int ret = MPI_Op_free(&tmp);
    atomic_store_explicit(&op_table[handle], tmp, memory_order_release);
    /* ... */
    if (ret != MPI_SUCCESS) {
        return ret;
    }
    /* Step 2: drop the Rust-boxed closure via the Rust callback. */
    ferrompi_op_drop_closure(handle);
    /* Step 3: reclaim the slot (also overwrites op_table[handle] with MPI_OP_NULL). */
    free_op_slot(handle);
    return ret;
}

The order is MPI’s operation first, then the closure, through a call back into Rust, then the slot. If MPI_Op_free fails, MPI may still call the function, so the closure and the slot stay. ADR 0005 covers the design, and chapter 12 the Rust side.

Finalize

ferrompi_finalize empties the tables before it calls MPI_Finalize, in an order that frees each object before the ones it may refer to:

TableAt finalize
requestsfrees each inactive persistent request, the only kind that can be left, and clears every bit
user operationsfrees each with ferrompi_op_free, which drops its closure
groupsMPI_Group_free on each
datatypesMPI_Type_free on each
windowsnothing: Mpi skips finalize while one is alive
communicatorsMPI_Comm_free on each but slot 0

The user operations’ loop calls the same function a dropped UserOp does:

    // Free every live user op: frees the MPI op and drops the Rust closure
    // through the same path as OpRegistration's Drop; a failed MPI_Op_free keeps both.
    for (int i = 0; i < MAX_OPS; i++) {
        if (atomic_load_explicit(&op_used[i], memory_order_acquire)) {
            ferrompi_op_free(i);
        }
    }

A slot still in use at finalize belongs to a Rust value that is still alive, such as a communicator kept after the Mpi handle was dropped. The sweep frees its MPI object, and its own drop, later, makes no MPI call: the guard skips every MPI call in a drop once finalizing has begun.

Rules for the C layer

A change to csrc/ferrompi.c keeps these, most of them listed in the architecture guide’s FFI and ABI invariants:

  • Only fixed-width integers and addresses cross. A new kind of MPI object gets a table, or crosses by value behind a size assertion, as MPI_Message does.
  • Every function that can fail returns an int: an MPI code or a negative ferrompi code that src/error.rs knows.
  • A value MPI does not fix, such as MPI_UNDEFINED, a wildcard or a mode flag, is translated in C, never written as a number in Rust.
  • The switches accept every value a Rust enum can hold, whatever Cargo features are on.
  • A new communicator gets MPI_ERRORS_RETURN before Rust sees it.
  • The tables take no lock, and the one mutex is held around a single local group call, never across a collective or blocking call.
  • An MPI 4.0 call compiles under the version test, with a fallback that returns MPI_ERR_COUNT or ferrompi’s code for an unsupported call.
  • build.rs compiles the file with the C compiler’s warnings and extra warnings on, and CI’s clippy and test jobs build it against MPICH and Open MPI.

Chapter 14 follows one MPI call that was added, from the header to the test, and what a reviewer checks in each place.

Summary

  • The C layer exists so that Rust never sees an MPI type: handle types and the set of functions change from one library and version to the next, and user operations need C functions of their own.
  • csrc/ferrompi.h is the contract: fixed-width integers and addresses in, an int code out. The status struct is checked on both sides at compile time; the other shared numbers rely on a comment naming their mirror.
  • Six fixed tables hold MPI’s handles, and Rust holds slot numbers. MPI_COMM_WORLD and MPI_GROUP_EMPTY have handle 0. Only a matched message crosses by value.
  • The request table tracks slots in bits and gives each handle a generation, so a handle kept past its request’s completion is refused instead of acting on another request.
  • Slots are claimed with a compare-and-swap or a fetch_or, freed with a release store, and looked up with an acquire load. The tables take no lock; the one mutex is for MPI’s group calls.
  • A full table returns ResourceExhausted after MPI has done its part: a nonblocking operation has completed, and a communicator or a window is left behind on every process that made it.
  • Sixteen generated functions let MPI call sixteen Rust closures, and finalize frees what is left in each table before MPI_Finalize. A C program can link libferrompi.a and call the C layer with no Rust in between.
