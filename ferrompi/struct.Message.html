Struct Message

A message that a matched probe took out of the receive queue and that has not been received yet.

Communicator::mprobe and Communicator::improbe return it with the message’s Status. Only mrecv on this handle receives the message: no other probe or receive, on any thread, can take it. That makes probe-then-receive correct when several threads receive on one communicator, where probe followed by recv can receive a message other than the one that was probed.

§Example

let (message, status) = world.mprobe::<f64>(Source::Any, Tag::Any)?;
let mut buf = vec![0.0f64; status.count.expect("whole number of f64")];
message.mrecv(&mut buf)?;

§Dropping

MPI requires every matched message to be received (MPI-4.1 §3.8.2, p.98), so dropping a Message receives it into a scratch buffer and throws the data away. The scratch receive uses MPI_BYTE whatever type the message was sent with. That strictly breaks MPI’s type-matching rule (MPI-4.1 §3.3.1, p.46), under which a send and its receive name the same type, but MPICH and Open MPI accept the receive.

  • The drop is an MPI call. On a thread that may not call MPI at the provided thread level, it makes no MPI call and does not abort: the message stays matched and unreceived for the rest of the process.
  • A drop whose receive fails, whose scratch buffer cannot be allocated, or whose message has a length MPI could not report (for example more than i32::MAX bytes on a library without the large-count calls) is treated the same way: the message counts as unreceived for the rest of the process.
  • While a Message is unreceived, whatever thread holds it, dropping Mpi skips MPI_Finalize (see Mpi): finalizing with a matched message pending is erroneous (MPI-4.1 §11.2.2, p.489). The message can still be received or dropped afterwards.

§Compile-time guarantees

A message is received at most once. mrecv takes the handle by value:

ⓘ
let (message, _) = world.mprobe::<u64>(1, 9)?;
let mut first = [0u64; 4];
let mut second = [0u64; 4];
message.mrecv(&mut first)?;
message.mrecv(&mut second)?;
let (message, _) = world.mprobe::<u64>(1, 9)?;
let mut first = [0u64; 4];
message.mrecv(&mut first)?;

and the handle cannot be copied:

ⓘ
let (message, _) = world.mprobe::<u64>(1, 9)?;
let copy = message.clone();
let (message, _) = world.mprobe::<u64>(1, 9)?;
let moved = message;

impl Message

pub fn mrecv<T: MpiDatatype>(self, buf: &mut [T]) -> Result<Status>

Receive the matched message into buf.

Returns the receive’s Status, as recv does: the matched source and tag, and the number of T elements received. A message matched from Source::ProcNull returns at once with Source::ProcNull, Tag::Any and Some(0), and leaves buf untouched.

buf may be longer than the message. With an MPI library that has no large-count calls, MPI is told of at most i32::MAX elements of room, so a longer buf is accepted here, where every other call returns class MpiErrorClass::Count for a count above i32::MAX.

§Errors

Returns Error::Mpi with class MpiErrorClass::Truncate if the message does not fit in buf. A receive that MPI ran consumes the message whatever it returned, so the message is then gone.

A call rejected before reaching MPI (Error::ThreadLevelViolation on a thread that may not call MPI, or, in a debug build at Serialized, while another thread’s call is in progress) receives nothing; the message is then dropped as described under Dropping.

Source§

fn drop(&mut self)

Receives an unreceived message into a scratch buffer, as MPI_BYTE.

The token is released only once that receive succeeded. On every other path it is forgotten, so the message keeps counting and Mpi’s drop skips MPI_Finalize: a refused call (wrong thread, or Mpi already finalized), a failed receive, an unknown length, or a scratch buffer that could not be allocated.
