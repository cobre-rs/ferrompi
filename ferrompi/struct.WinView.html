Struct WinView

Expand description

A view of a region of an RMA window: a pointer and a length borrowed from a Win or from one of its epoch handles.

Win::local, ActiveEpoch::local and PassiveEpoch::local return one of this process’s own region, and Win::remote, ActiveEpoch::remote and PassiveEpoch::remote one of a peer’s region of a shared window. The memory of a window can change while the view lives, because a peer’s put or accumulate writes it, a peer stores into it through a shared window, or a fence lands remote writes in it. A &[T] over it would promise the compiler that it does not, so the view hands out elements by value instead. The unsafe methods as_slice and as_mut_slice give a slice to a caller that can meet the contract their # Safety sections state.

§Access

Every access is one Relaxed atomic load or store of the element, so a concurrent write by a peer, by MPI or by another view in this process never makes an access undefined behaviour. The elements are those of MpiDatatype: each fits its atomic on every supported target, and the build fails on a target where one does not.

What a load returns is set by MPI’s memory model (MPI-4.1 §12.7). In the unified model, a load of a location that a put or accumulate is updating is valid and returns an implementation-dependent value, and MPI gives no atomicity when the update writes more than one byte (rule U2, p.608): poll for a change from zero to nonzero or for a particular value, not for a relative magnitude. A store while a peer reads the location is valid (rule U3, p.609). A store while a put or accumulate to the same location is in progress leaves the location without a defined value (rule U5, p.609; MPI-4.1 §12.3, p.566). None of these is undefined behaviour in Rust, because every bit pattern is a valid element. A Relaxed access orders nothing against other locations: the epoch’s synchronization calls do, as that section describes.

A process that only polls makes no MPI progress: a peer’s put or accumulate may not reach it until it calls MPI, and a peer that stores must do so before any MPI call that can wait for it (MPI-4.1 §12.7.3, p.615-616; Example 12.13, p.617).

The view claims no exclusivity, so two views of one region coexist, and write takes &self. The bulk copies, copy_to_slice and copy_from_slice, go element by element: each element is one atomic access, so accesses through views never tear one another, and the copy as a whole is not atomic.

§Panics

The view is the one ferrompi API that panics on caller input: an out-of-range index or a length mismatch panics, as slice indexing and <[T]>::copy_from_slice do, while every other call returns an Error.

§Lifetimes

A view from Win::local or Win::remote borrows the window, so it cannot be held across an epoch, which borrows the window mutably, and the window cannot be freed while the view lives. A view from an epoch handle borrows the handle, so it cannot leave the epoch’s closure. The # Compile-time guarantees section of Win shows each as a program that does not compile.

§Thread safety

WinView is neither Send nor Sync. It follows its window, which is neither, so every access to the window’s memory stays in the program order of the thread that issues the window’s MPI calls. That order is what places a store before sync (see PassiveEpoch::local).

pub unsafe fn as_slice(&self) -> &[T]

A shared slice over the whole viewed region, for bulk reads that need no atomic access per element.

The slice borrows the view, so it cannot outlive it. Taken from a view held in a local variable, it cannot be the origin of an RMA call on its own window either, which borrows its origin for the whole epoch.

§Safety

No process writes the region by store, put or accumulate while the slice lives, and the writes it must observe were published before it was created, either by a fence or MPI_Win_wait at this process that completed them, or by process synchronization after they completed, then MPI_Win_sync at this process inside a passive-target epoch.

A store through any view of the region counts, this view’s write and copy_from_slice included: the borrow checker does not stop them while the slice lives.

Why the obligation exists. A slice lets the compiler keep a value in a register for as long as it lives, so a write that lands in the region meanwhile breaks what the compiler assumed, which is undefined behaviour in Rust. In the unified model, MPI allows part of what the contract forbids: a load that races a put or accumulate is valid but returns an implementation-dependent value (MPI-4.1 §12.7, rule U2, p.608), which the view’s atomic reads tolerate and a slice cannot. Conflicting updates leave MPI’s behaviour undefined: a store against a put or accumulate, and one RMA update against another except concurrent accumulates of one predefined datatype (MPI-4.1 §12.7, rules U4 and U5, p.609).

What publication means. A closing fence, or MPI_Win_wait at this process, makes the writes it completed visible here (MPI-4.1 §12.7, rules 2, 3 and 6, p.606; §12.5.1, p.591; §12.5.2, p.595). A writer completes a put or accumulate by its unlock or flush (MPI-4.1 §12.7, rule 4, p.606), and a store by its own MPI_Win_sync (Example 12.23). This process’s own earlier stores need no publication. Under passive-target synchronization, MPI_Win_sync at this process after the process synchronization orders its loads after the stores another process made before that synchronization (MPI-4.1 §12.5.4, p.603; the advice to users after rule U5, MPI-4.1 §12.7, p.609). Example 12.23 (p.622) shows the sequence: lock_all; store; MPI_Win_sync; send and receive; MPI_Win_sync; load. MPI defines no semantics for direct access to shared window memory outside the unified memory model (MPI-4.1 §12.2.3, p.558).

A peer’s region. For a slice of a Win::remote view, MPI_Win_wait at this process never applies: it completes the exposure epoch of this process’s own region. A fence publishes because it is collective and completes the writes at the region’s owner (MPI-4.1 §12.5.1, p.591): writes made before the previous fence are visible once a fence without MPI_MODE_NOPRECEDE returns here (p.592). Otherwise the passive-target route above is the one a remote reader needs: the writer’s MPI_Win_sync after its stores, or its unlock or flush after its puts and accumulates, then process synchronization, then MPI_Win_sync at this process.

pub unsafe fn as_mut_slice(&mut self) -> &mut [T]

An exclusive slice over the whole viewed region.

§Safety

No process writes the region by store, put or accumulate while the slice lives, and the writes it must observe were published before it was created, either by a fence or MPI_Win_wait at this process that completed them, or by process synchronization after they completed, then MPI_Win_sync at this process inside a passive-target epoch. No other access to the region, read or write, happens while the slice lives: by any process, by MPI on this process’s behalf, or by any other view or slice in this process, including remote(own rank), which aliases local().

The reasons are those of as_slice, and a &mut [T] must also be unique. Writes through the slice itself, including by an MPI call it is lent to, are the one exception to the first sentence. &mut self enforces uniqueness only against the view it is taken from: another view of the region, or an RMA call that targets this process, is not stopped by it.
