Expand description

The handle a passive-target epoch gives its closure.

Win::lock and Win::lock_all open an epoch, run a closure with this handle, and end the epoch with MPI_Win_unlock or MPI_Win_unlock_all when the closure returns, whether it returned Ok or Err, and also when it panics. The epoch is open exactly while the closure runs, and the window is mutably borrowed for that time.

The handle carries the calls MPI allows only inside a passive-target epoch: the synchronization calls flush, flush_all, flush_local, flush_local_all and sync, and the request-based transfers rput, rget and raccumulate (MPI-4.1 §12.3.5). The epoch owns the requests those return: before it unlocks it completes every one still pending, also when the closure returned an error or panicked.

§Lifetimes

The handle carries the invariant lifetimes of Scope: 's is the epoch, and 'env outlives it. put, get, accumulate, get_accumulate, fetch_and_op, compare_and_swap, rput, rget and raccumulate borrow their buffers for 's, so a buffer outlives the unlock, which is when MPI stops using it, and cannot be dropped or written before then, even after a flush or after a request completed. A buffer MPI writes (a get or rget destination or a result) cannot be read before then either. These nine methods reject a buffer declared inside the closure, because it is freed before then. Declare buffers before the call to lock or lock_all. local and remote return views that borrow the handle, so they cannot leave the closure.

§Access set

A transfer’s target_rank must be a rank the epoch gives access to: the locked rank for Win::lock, any rank of the window’s communicator for Win::lock_all. Any other rank returns Error::InvalidArgument with arg: "target_rank" and makes no MPI call, because MPI-4.1 §12.5 makes such a transfer erroneous and the unlock would not complete it. flush and flush_local accept any rank of the window’s communicator.

§Completion

An operation is complete at the origin, where a get or rget destination or a result then holds its values, once a flush of its target_rank returns (flush, flush_all, flush_local or flush_local_all), and at the target once flush or flush_all returns for it. Every operation is complete at both ends at the latest when the unlock returns.

§Thread safety

PassiveEpoch is neither Send nor Sync: it borrows a Win, which is neither.

pub fn local(&self) -> WinView<'_, T>

A view of this process’s window memory, as Win::local, taken through the handle: the window itself is borrowed mutably while the closure runs.

The view borrows the handle, so it cannot leave the closure. Inside a Win::lock_all closure it combines with sync, which is MPI_Win_sync (MPI-4.1 §12.5.4), into the shared-memory pattern: store through the view, sync, synchronize the processes (for example with a barrier), sync, load (MPI-4.1 §12.7, p.609; Example 12.23, p.622).

§Example
use ferrompi::{Mpi, Win};

let mpi = Mpi::init().unwrap();
let world = mpi.world();
let mut win = Win::<u64>::allocate(&world, 4).unwrap();
win.lock_all(|e| {
    e.local().write(0, 7);
    e.sync()?;
    world.barrier()?;
    e.sync()?;
    let _seen = e.local().read(0);
    Ok(())
})
.unwrap();

pub fn remote(&self, rank: i32) -> Result<WinView<'_, T>>

A view of rank’s region of a shared window, as Win::remote, taken through the handle: the window itself is borrowed mutably while the closure runs.

The view borrows the handle, so it cannot leave the closure. It makes no MPI call, and the epoch’s access set does not restrict it: loads and stores of shared memory need no access epoch to that rank. Inside a Win::lock_all closure it completes the pattern of local: the peer stores through its own view and calls sync, the processes synchronize, this process calls sync, then loads through remote. That is the passive-target route described under Win::remote’s # Publication, and Win::allocate_shared shows the pattern. Under lock(_, r), loads and stores through remote(r) are lock-protected (MPI-4.1 §12.5.3, p.597); remote of any other rank is not.

§Errors

As Win::remote.

pub fn rput( &'s self, origin: &'s [T], target_rank: i32, target_disp: i64, ) -> Result<Request<'s>>

Request-returning one-sided write, as put, with a Request for its local completion.

Wraps MPI_Rput. The request completes locally (MPI-4.1 §12.3.5): once Request::wait, Request::test or a batch call reports it complete, MPI no longer reads origin. The target holds the data once the write is complete there (see the type’s # Completion section). A request that was not waited is completed by the epoch before it unlocks, so dropping or forgetting it makes no MPI call. origin stays borrowed until the unlock returns, even after the request completed.

Request::cancel on the returned request returns Error::NotSupported without calling MPI: MPI_Cancel is defined only for point-to-point requests, and MPICH and Open MPI reject it for RMA requests. The request stays pending; complete it with wait as usual.

The count is origin.len(); pass a sub-slice for a shorter transfer.

§Arguments
  • origin — Local source buffer (read-only).
  • target_rank — Destination rank, in the epoch’s access set.
  • target_disp — Displacement at the target, measured in units of disp_unit (i.e., multiples of size_of::<T>()).
§Errors
  • Error::InvalidArgument — if target_rank is not a rank of the window’s communicator (including -1) or of the epoch’s access set (arg: "target_rank"), target_disp is negative, or the access does not fit in the target rank’s window; no MPI call is made.
  • Error::Finalized — once Mpi is being dropped.
  • Error::ResourceExhausted with resource ResourceKind::Request — if the internal request table is full.
  • Error::Mpi — if MPI_Rput fails; on MPI before 4.0 this includes class Count for an origin of more than i32::MAX elements.
§Example
use ferrompi::{LockType, Mpi, Win};

let mpi = Mpi::init().unwrap();
let world = mpi.world();
let mut win = Win::<i32>::allocate(&world, 4).unwrap();
let buf = [10i32, 20, 30, 40];

if world.rank() == 0 {
    // `buf` is declared before the epoch: it stays borrowed until the
    // unlock, which is when rank 1 holds the data
    win.lock(LockType::Exclusive, 1, |e| {
        let req = e.rput(&buf, 1, 0)?;
        req.wait()?; // MPI no longer reads `buf`
        Ok(())
    })
    .unwrap();
}

pub fn rget( &'s self, origin: &'s mut [T], target_rank: i32, target_disp: i64, ) -> Result<Request<'s>>

Request-returning one-sided read, as get, with a Request for its local completion.

Wraps MPI_Rget. When Request::wait, Request::test or a batch call reports the request complete, origin holds the data read from target_rank (MPI-4.1 §12.3.5). A request that was not waited is completed by the epoch before it unlocks. origin stays mutably borrowed until the unlock returns, even after the request completed, so read it after the closure returns.

Request::cancel on the returned request returns Error::NotSupported without calling MPI, as for rput.

The count is origin.len(); pass a sub-slice for a shorter transfer.

§Arguments
  • origin — Local destination buffer filled by the remote read.
  • target_rank — Source rank, in the epoch’s access set.
  • target_disp — Displacement at the target, measured in units of disp_unit (i.e., multiples of size_of::<T>()).
§Errors
  • Error::InvalidArgument — if target_rank is not a rank of the window’s communicator (including -1) or of the epoch’s access set (arg: "target_rank"), target_disp is negative, or the access does not fit in the target rank’s window; no MPI call is made.
  • Error::Finalized — once Mpi is being dropped.
  • Error::ResourceExhausted with resource ResourceKind::Request — if the internal request table is full.
  • Error::Mpi — if MPI_Rget fails; on MPI before 4.0 this includes class Count for an origin of more than i32::MAX elements.
§Example
use ferrompi::{LockType, Mpi, Win};

let mpi = Mpi::init().unwrap();
let world = mpi.world();
let mut win = Win::<i32>::allocate(&world, 4).unwrap();
let mut buf = [0i32; 4];

if world.rank() == 0 {
    // `buf` is declared before the epoch and read after it
    win.lock(LockType::Shared, 1, |e| {
        let req = e.rget(&mut buf, 1, 0)?;
        req.wait()?; // `buf` holds the data, and stays borrowed
        Ok(())
    })
    .unwrap();
    println!("{buf:?}");
}

pub fn raccumulate( &'s self, origin: &'s [T], target_rank: i32, target_disp: i64, op: impl Into<AccumulateOp>, ) -> Result<Request<'s>>

Request-returning one-sided reduce-accumulate, as accumulate, with a Request for its local completion.

Wraps MPI_Raccumulate. The request completes locally: once Request::wait, Request::test or a batch call reports it complete, MPI no longer reads origin. The update is visible at the target once it is complete there (see the type’s # Completion section). A request that was not waited is completed by the epoch before it unlocks. origin stays borrowed until the unlock returns, even after the request completed.

op is as for ActiveEpoch::accumulate, with AccumulateOp::REPLACE like MPI_Rput, but element-wise atomic; a user op is not accepted (MPI-4.1 §12.3.4). Concurrent accumulates to one target location must use the same op or MPI_NO_OP, as there (MPI-4.1 §12.2.1).

Request::cancel on the returned request returns Error::NotSupported without calling MPI, as for rput.

The count is origin.len(); pass a sub-slice for a shorter transfer.

§Arguments
  • origin — Local source buffer (read-only).
  • target_rank — Destination rank, in the epoch’s access set.
  • target_disp — Displacement at the target, measured in units of disp_unit (i.e., multiples of size_of::<T>()).
  • op — Reduction operation to apply.
§Errors
  • Error::InvalidArgument with arg: "op" — if op is a predefined op MPI does not define on T (a bitwise or logical op on f32/f64); no MPI call is made.
  • Error::InvalidArgument — if target_rank is not a rank of the window’s communicator (including -1) or of the epoch’s access set (arg: "target_rank"), target_disp is negative, or the access does not fit in the target rank’s window; no MPI call is made.
  • Error::Finalized — once Mpi is being dropped.
  • Error::ResourceExhausted with resource ResourceKind::Request — if the internal request table is full.
  • Error::Mpi — if MPI_Raccumulate fails for any other reason; on MPI before 4.0 this includes class Count for an origin of more than i32::MAX elements.
§Example
use ferrompi::{LockType, Mpi, ReduceOp, Win};

let mpi = Mpi::init().unwrap();
let world = mpi.world();
let mut win = Win::<i32>::allocate(&world, 4).unwrap();
let buf = [10i32, 20, 30, 40];

if world.rank() == 0 {
    // `buf` is declared before the epoch: it stays borrowed until the
    // unlock, which is when the update is complete at rank 1
    win.lock(LockType::Exclusive, 1, |e| {
        let req = e.raccumulate(&buf, 1, 0, ReduceOp::Sum)?;
        req.wait()?; // MPI no longer reads `buf`
        Ok(())
    })
    .unwrap();
}

pub fn flush(&self, rank: i32) -> Result<()>

Complete the epoch’s pending RMA operations to rank, at the origin and at the target.

Wraps MPI_Win_flush. When it returns, every operation this rank issued to rank in the epoch is complete at both ends, and the epoch stays open.

§Arguments
  • rank - The target rank to flush (0-based, within the window’s communicator). It need not be in the epoch’s access set: in a Win::lock epoch only the locked rank has operations to complete, and a flush of another rank completes nothing.
§Errors
  • Error::InvalidArgument with arg: "rank" if rank is outside the window’s communicator; no MPI call is made.
  • Error::Finalized once Mpi is being dropped.
  • Error::Mpi with operation: Some("win_flush") if MPI reports an error.
Source

pub fn flush_all(&self) -> Result<()>

Complete the epoch’s pending RMA operations to every rank, at the origin and at the targets.

Wraps MPI_Win_flush_all. When it returns, every operation this rank issued in the epoch is complete at both ends, and the epoch stays open.

§Errors
  • Error::Finalized once Mpi is being dropped.
  • Error::Mpi with operation: Some("win_flush_all") if MPI reports an error.

pub fn flush_local(&self, rank: i32) -> Result<()>

Complete the epoch’s pending RMA operations to rank at the origin only.

Wraps MPI_Win_flush_local. When it returns, the origin buffers of every operation this rank issued to rank in the epoch are safe to reuse, but the target may not have observed the writes yet.

§Arguments
  • rank - The target rank whose pending operations are locally completed (0-based, within the window’s communicator). As for flush, it need not be in the epoch’s access set.
§Errors
  • Error::InvalidArgument with arg: "rank" if rank is outside the window’s communicator; no MPI call is made.
  • Error::Finalized once Mpi is being dropped.
  • Error::Mpi with operation: Some("win_flush_local") if MPI reports an error.

pub fn sync(&self) -> Result<()>

Synchronize the public and private copies of this window’s local memory.

Wraps MPI_Win_sync, a local memory barrier: it does not communicate and does not complete pending RMA operations. MPI allows it only inside a passive-target epoch (MPI-4.1 §12.5.4), which this handle guarantees; MPICH rejects it elsewhere.

§Errors
  • Error::Finalized once Mpi is being dropped.
  • Error::Mpi with operation: Some("win_sync") if MPI reports an error.
