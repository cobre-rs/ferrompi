A persistent MPI request that owns its buffers.

A persistent request is initialized once and then started and completed many times, so one setup serves a whole loop of iterations. The *_init constructors take the buffers by value and the request keeps them until it is freed: MPI holds a pointer into each allocation, so no safe call can resize or free one behind MPI’s back. Reach the buffer with buffer and buffer_mut while the request is inactive, or take it back with into_buffer.

A collective with separate send and receive buffers owns both. buffer and buffer_mut reach the receive buffer, send_buffer_mut reaches the send buffer, and into_buffers returns both. A request that owns one buffer (a point-to-point request, a broadcast or an in-place collective) has an empty send buffer.

Communicator::barrier_init returns a PersistentRequest<()>, which owns no data. start_all and wait_all take requests of one element type, so a barrier request is started and completed on its own, not in one slice with requests of another type.

Creating a persistent collective is itself a collective call. Every process of the communicator makes the same *_init call, ordered with its other collective calls on that communicator, and the call can block until the others make it (MPI-4.1 §6.13). The starts are not ordered: persistent collectives can be started in any order, and the order can differ between processes.

§Lifecycle

  1. Create with comm.send_init(vec, ..), comm.recv_init(vec, ..) or another *_init, which takes the buffers by value.
  2. Update the buffer through buffer_mut() (or send_buffer_mut()). The accessors work only while the request is inactive and return Error::InvalidState otherwise.
  3. Start with start() or start_all().
  4. Wait for completion with wait(), then read the result through buffer().
  5. Repeat steps 2-4 as needed.
  6. Free on drop, or take the buffer back with into_buffer() or into_buffers().

§Example

use ferrompi::Mpi;

let mpi = Mpi::init()?;
let world = mpi.world();
let rank = world.rank();

// Initialize a self-send pair once; each request owns its buffer.
let mut send = world.send_init(vec![0.0f64; 1000], rank, 0)?;
let mut recv = world.recv_init(vec![0.0f64; 1000], rank, 0)?;

for iter in 0..1000 {
    for (i, x) in send.buffer_mut()?.iter_mut().enumerate() {
        *x = (iter * 1000 + i) as f64;
    }

    recv.start()?;
    send.start()?;
    send.wait()?;
    recv.wait()?;

    assert_eq!(recv.buffer()?[0], (iter * 1000) as f64);
}

// Cleanup happens automatically on drop.

§Ownership

MPI keeps a pointer into each buffer from the *_init call until the request is freed, so safe code must have no way to resize or free a buffer while the request exists, or to touch it while the request is active. The constructors take each buffer by value, the accessors hand out slices that cannot be resized, and while the request is active they return Error::InvalidState instead of a slice. Each program below does not compile, and is followed by the same program made correct.

The Vec a constructor consumed cannot be resized afterwards, so its allocation cannot move while MPI holds a pointer into it:

ⓘ
let mut data = vec![0u64; 4];
let _p = world.recv_init(data, 1, 9)?;
data.reserve(4096);
let mut data = world.recv_init(vec![0u64; 4], 1, 9)?.into_buffer()?;
data.reserve(4096);

Nor can the buffer be resized through an accessor, which returns a slice:

ⓘ
let mut p = world.recv_init(vec![0u64; 4], 1, 9)?;
p.buffer_mut()?.reserve(4096);
let mut p = world.recv_init(vec![0u64; 4], 1, 9)?;
p.buffer_mut()?.copy_from_slice(&[1, 2, 3, 4]);

A slice an accessor returned cannot be held across start, because the slice borrows the request and start borrows it mutably:

ⓘ
let mut p = world.send_init(vec![0u64; 4], 1, 9)?;
let b = p.buffer_mut()?;
p.start()?;
b[0] = 1;
let mut p = world.send_init(vec![0u64; 4], 1, 9)?;
p.buffer_mut()?[0] = 1;
p.start()?;
p.wait()?;

The test_persistent_ownership example checks the rest at run time: the accessors fail with Error::InvalidState while the request is active, into_buffer on an active request waits for it, a request dropped while active completes before its buffer is freed, a request forgotten while active leaks its buffer instead of freeing it, and a loop that rewrites the buffers between iterations allocates nothing per iteration.

§Dropping

Dropping an active request completes it (MPI_Wait, which blocks until the peer operation completes), then frees it (MPI_Request_free, which MPI does not allow on an active collective request), and only then frees the buffers, and after them the user op, which MPI may invoke at every start.

  • At Single/Funneled, drop it on the thread that initialized MPI; another thread aborts the process.
  • At Serialized and Multiple, the drop is an MPI call, which the program serializes like any other.
  • Once Mpi is being dropped, or after it was dropped, the drop makes no MPI call. It leaks the request handle and, when the request is active, the send and receive buffers, the copy of a v-collective’s count and displacement arrays, and the user op, because MPI may still use them. The buffers of an inactive request are freed normally.
  • A drop on another thread while Mpi is being dropped either completes before MPI_Finalize, because it holds a per-call count the finalizer waits for, or makes no MPI call and leaks as above. A drop that is blocked in MPI_Wait for a peer that never arrives blocks Mpi’s drop the same way a blocked wait() does. MPI requires every call in flight to complete before MPI_Finalize (MPI-4.1 §11.2.2 and §11.6.2 p.516).
  • Dropping Mpi while the request is active skips MPI_Finalize, whatever thread holds the request (see Mpi). The request can still be completed with wait or test afterwards; dropping it then makes no MPI call, as above.
  • The drop does not assume that a failed wait completed the request (MPI-4.1 §9.4). If completing an active request fails, it makes no further MPI call and leaks the request handle, the buffers and the user op, which the request keeps alive (see UserOp). The request also keeps counting as active, so a later Mpi drop skips MPI_Finalize.

pub fn start(&mut self) -> Result<()>

Start the persistent operation.

This initiates the communication. You must call wait() before starting again or reaching the buffer.

§Errors

Returns Error::InvalidState if the operation is already active, Error::Finalized once Mpi is being dropped, Error::ThreadLevelViolation on a thread other than the one that initialized MPI at Single/Funneled, or the error of a failed start.

Source

pub fn wait(&mut self) -> Result<Status>

Wait for the operation to complete.

This blocks until the communication started by start() is finished. After this returns, the buffer can be reached with buffer and buffer_mut, and the operation can be started again.

For a request made by recv_init the returned Status holds the matched source, tag and element count of that start (Source::ProcNull for a receive from ProcNull). For every send-side or collective request the Status is the empty status, and so is an inactive request, as MPI_Wait returns for one; only error has meaning, and these calls leave it None.

§Errors

Returns an error if the wait fails. A wait that MPI ran leaves the request inactive either way: MPI completed it with that error. This assumes that a request MPI reported an error for is complete, as MPICH and Open MPI leave it; MPI-4.1 §9.4 (p.460) says an operation that raised an error may not have satisfied its specification, so the standard does not promise it. The same assumption holds for test and wait_all; only Drop does not make it. A call rejected before reaching MPI (wrong thread, after finalize, or, in a debug build at Serialized, overlapping another thread’s call) leaves the request active.

Source

pub fn test(&mut self) -> Result<Option<Status>>

Test if the operation has completed without blocking.

Returns Some(Status) if complete, None if still in progress. The Status is the one wait returns: the matched source, tag and element count for a recv_init request, the empty status for every other request, and the empty status for an inactive request. A failed test that MPI completed also leaves the request inactive, on the assumption described under wait.

Source

pub fn buffer(&self) -> Result<&[T]>

The request’s buffer, while the request is inactive.

This is the send data of a send request, and the received data of a receive request after its wait(). For a collective with separate send and receive buffers it is the receive buffer; reach the send buffer with send_buffer_mut. The slice cannot be resized, because MPI holds a pointer into the allocation.

§Errors

Returns Error::InvalidState while the request is active: MPI owns the buffer from start() until wait(), wait_all(), or a test() that reports completion, returns.

Source

pub fn buffer_mut(&mut self) -> Result<&mut [T]>

The request’s buffer for writing, while the request is inactive: the buffer buffer reads.

Write the next iteration’s input here between wait() and the next start().

§Errors

Returns Error::InvalidState while the request is active.

Source

pub fn send_buffer_mut(&mut self) -> Result<&mut [T]>

The send buffer of a collective with separate send and receive buffers, for writing, while the request is inactive.

Write the next iteration’s input here between wait() and the next start(). The slice is empty for a request that owns one buffer: a point-to-point request, a broadcast or an in-place collective.

§Errors

Returns Error::InvalidState while the request is active.

Source

pub fn into_buffer(self) -> Result<Vec<T>>

Complete the request if it is active, free it, and return its buffer.

The request is freed before this returns. Freeing a request is an MPI call, so Drop’s thread rule applies: at Single/Funneled, on a thread other than the one that initialized MPI, the process aborts.

For a collective with separate send and receive buffers this returns the receive buffer and drops the send buffer after the free; use into_buffers to keep both.

It discards the final Status: a recv_init caller that needs the received count or source calls wait first, which returns it, and then into_buffer. The same holds for into_buffers.

§Errors

Returns the error of wait if completing an active request fails. The request is then dropped as Drop does, and the buffer is not returned.

Source

pub fn into_buffers(self) -> Result<(Vec<T>, Vec<T>)>

Complete the request if it is active, free it, and return its send and receive buffers as (send, buffer).

The send buffer is empty for a request that owns one buffer. Otherwise this behaves as into_buffer.

§Errors

Returns the error of wait if completing an active request fails. The request is then dropped as Drop does, and the buffers are not returned.

Source

pub fn start_all(requests: &mut [PersistentRequest<T>]) -> Result<()>

Start multiple persistent operations.

This is more efficient than starting each operation individually.

§Errors

Returns Err(Error::InvalidState) without calling MPI if any request is already active, and Error::Finalized or Error::ThreadLevelViolation as start does. If MPI reports an error, it may have started some of the requests; every request is then marked active, so wait, wait_all or Drop completes whichever did start.

Source

pub fn wait_all(requests: &mut [PersistentRequest<T>]) -> Result<()>

Wait for all persistent operations to complete.

Whatever the result, every request MPI completed is marked inactive in place; the others stay active. This is the same policy Request::wait_all applies. Inactive requests are skipped, so a request whose earlier wait or test failed can stay in the slice.

On a failed request, the returned error carries that request’s own class and code, and its message ends with (request N), N being its index in requests.

This returns no status, like Request::wait_all. A request it completed is inactive, so a later wait on it returns the empty status; to read a receive’s Status, complete that request with wait or test instead.
